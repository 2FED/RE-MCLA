Read-only analysis by an Opus subagent on 2026-11-07 of the five l77 KI-074 experiment sessions against the earlier l75/l76/Locked runs (15 sessions); accepted by the primary agent.

Read-only analysis by an Opus subagent. Profile 7d6ff1dd..., Unlocked, Arcade "South Central Tour", 1920x1080
render target (scale 2), RTX 5060 Laptop, one run per arm. Sources: session `mcla.log` (dev-override lines,
`MCLA timer:`, `guest vblank:`, `menu state:`, `timer scale:`, `frame pacing/min`, `gpu busy/min`,
`MCLA_PERF_SPLIT`, `MCLA_VRAM`, `MCLA_LIVERY_DIAG2 kind=minute`, `MCLA_PURSUIT dt=`), package `state.json`
(`guest_ki026.timer_step/timer_scale/paused`) and `frame.bmp`. Comparison: l76 steady 31689c39/c959447b,
l76 steady-ensure cd91c47a/4c6a2e31, l75 steady c8a6754d/7352bf89, l75 base b632bc55, Locked base 286da14f,
Locked steady 83a92753/53486a5f. Python isolated (-I); nothing built or launched.

Notes on fields: `gpu%` = PERF_SPLIT `gpu_busy_ms / wall_ms` (race minutes). PERF_SPLIT windows restart at
each F10, so per-frame values are used. `PURSUIT dt` is the game's own per-frame dt printed by the pursuit
probe (direct evidence of the dt the game used). No texture eviction/creation counter exists in any log
line (SDK texture cache does not log evictions; `MCLA_VRAM` carries limits, usage and budget only).

Reading:
- **dt is excluded for the flicker.** rawoff ran stock 1/30 s and flickered at the usual spot; cap44 ran the
  same 25 ms dt as the l76 flicker runs and did not flicker. Both directions agree.
- Flicker appears only in the uncapped GPU-saturated runs (gpu >= ~90 %, 40-42 fps, CP running ahead of a GPU
  that never idles). Every run at <= 87 % GPU busy, whether capped, CP-bound (base) or Locked, is clean.
- fps and GPU saturation cannot be separated by these data: GPU busy per frame is a near constant 22-23 ms,
  so gpu% ~= fps x 22.5 ms by construction. The boundary lies between 38-39 fps / 87 % (cap44, clean) and
  40-41 fps / 91-94 % (flicker). Frame quantisation in cap44 also gives the GPU a drain point most frames.
- Caveat: one run per l77 arm. The uncapped steady arms flickered in 7 of 7 runs (1-5 episodes each), so a
  single clean cap44 run is suggestive, not conclusive.

## 3. Texture budget / cache

Per-minute `MCLA_VRAM` (all 15 sessions):

- `tex_soft_mb=2048 tex_hard_mb=5595 tex_floor_mb=2048 steps=on near_budget_steps=0 near_budget_s=0` in
  **every** line of every session. No `near budget ... hard limit now` line anywhere. The l70 side finding
  (5595 -> 3291 MB after a garage/unfocused budget dip) did not recur: these runs had no garage/unfocused phase.
- Local usage rises with the route in all arms alike: ~3.9 GB (menu) -> 4.1-4.3 (+30 s) -> 4.4-4.7 ->
  5.0-5.3 GB at the finish. At the flicker F10s 4.9-5.2 GB (rawoff 4906/5156, l76 5146-5171, l75 5076-5319);
  at the clean-run F10s at the same stretch 5.1-5.3 GB (cap40 5306, cap44 5131, base-cap36 5156). No difference.
- The DXGI budget dips mid-race from 7131 to 5.9-6.6 GB in **all** sessions (flicker and clean, Locked
  included: min 5913 l75 s1, 6086 l76 s1, 6161 rawoff, 6264 cap40, 6304 cap44, 6354 cap36, 6456 Locked base),
  but usage + headroom stays under it, so no step. Not a discriminator.

- Per-frame churn is the same in every arm; per-minute churn scales linearly with fps (tracked render-target
  texture loads ~60 per frame, invalidations ~56 per frame, reloads without invalidation ~3.6 per frame).
  `tex_gen_bumps` per minute is fps-independent (time/route driven).
- The flicker stretch is an upload burst (+25-45 % bytes per frame) in **every** arm, clean ones included
  (cap44 13.8 MB/f, base-cap36 14.1 MB/f, cap40 13.9 MB/f vs rawoff 15.9, l76 16.5-16.9, l75 17.3). The
  burst is a route property; what differs is whether the GPU has idle time to absorb it.
- So: no evidence for a hard-limit or budget effect; the "more fps = more uploads per second" correlation is
  trivially true and does not separate flicker from clean runs. What cannot be checked: evictions and the
  2048 MB soft cap (the cache could be evicting at the soft cap during the burst; nothing logs it).

## 4. "Cars vanish at the results screen"

- The finish sequence is identical in all arms: `timer scale` ramp 0.61 -> 0.1 over ~0.25 s (slow-motion
  finish camera), then `menu state: game paused (sim 1 ...)`, UI cap forced, 60 Hz, then the REWARDS screen
  on East Adams. F10 frames at that moment exist for cap40 (#2 slow-mo, #3 rewards), rawoff (#5, #6),
  base-cap36 (#4 rewards) and l76 ensure2 (#8 slow-mo): all show the same composition and **no traffic on
  the street** in any of them, including the earlier l76 run. No l75/Locked/base run has a results-screen
  F10, so no direct same-moment comparison exists.
- base-cap36 (33 fps, CP-bound, raw dt 30 ms like any base run, no exemption) shows the same vanish. The
  symptom is therefore not tied to the steady exemption, the >36 fps regime or the dt size. Most likely the
  game's normal finish cut (sim paused, ambient population reset/cull for the results camera), which the
  owner noticed now because he was watching for despawns. Unconfirmed: needs one Locked run with attention
  (or an F10 pair just before/after the slow-mo) at the finish.
- base-cap36 mid-race despawn (owner's F10 #2, race clock 1:50.68, 122 mph): frame shows normal distant
  traffic; nothing anomalous visible. A disappearing distant car at speed in a 33 fps base run fits ordinary
  ambient LOD/cull distance, not KI-074.
- The floating car (l76 s1) and mid-race despawns in the uncapped arms are a separate question from the
  flicker; no l77 arm reproduced a floating car.

## 5. Conclusion and next experiment

Ranking given the new data:

1. **GPU-saturated pacing on the host side (texture cache / upload / resolve timing)** - now the leading
   mechanism for the texture flicker. Flicker follows "uncapped and GPU >= ~90 % busy" and is located at the
   route's heaviest upload stretch. Candidates: soft-cap eviction during the burst, upload/reuse keyed on GPU
   completion that a never-idle GPU stretches (KI-038 family, which also appeared GPU-bound at 37-40 fps on
   l49 before any read-back wait existed).
2. **Frame-count logic in the game at > ~39 fps** - still possible: fps and GPU saturation co-vary in every
   run so far.
3. **dt size** - excluded for the flicker (rawoff stock dt flickered; cap44 at 25 ms dt did not). Remains
   only as a candidate for the floating car/traffic issues, which l77 did not reproduce.

Decisive next runs (flags only unless noted; one value per session, same route and save):

1. **E3 (decouples fps from GPU saturation).** (a) steady uncapped at 720p render target (scale 1): CP-bound,
   GPU well below 90 %, 45+ fps. (b) base or steady at 1440p: GPU-saturated at < 36 fps. Flicker only in (b)
   -> host-side GPU-saturation effect; only in (a) -> game frame-rate logic.
2. **Texture-cache arm.** Steady uncapped with `mcla_texture_budget_soft_cap_off=true` (soft cap 3565 MB
   instead of 2048; the dev key already exists). Flicker gone -> soft-cap eviction during the Coliseum burst.
   Pinning the hard limit is pointless here (it never moved). Small host/SDK build: add per-minute and per-F10
   texture cache counters (creations, evictions by soft/hard limit, bytes evicted, textures evicted and
   re-created within N frames) so the next flicker press shows whether a just-evicted texture was drawn.
3. Repeat cap44 once or twice (single clean run so far) to firm up the 38-39 vs 40-41 boundary.
4. E4 (stripped-printf hook on ambient spawn-failure / sector paging + per-frame timer ring) stays for the
   floating-car/despawn branch; it is not needed to decide the flicker mechanism.
5. One Locked run watching the finish (or F10 just before and after the slow-mo) to settle whether the
   results-screen vanish is normal game behaviour.
