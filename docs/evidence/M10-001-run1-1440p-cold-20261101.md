## 3. Limiter per segment (harness verdict rule)

| Segment | Verdict | Reason |
|---|---|---|
| Stationary | **GPU** | GPU busy 99.0% of wall, 25.76 ms against a 26.01 ms interval (within 1%). The CP spends 8.9 ms/frame in the submission fence wait and the render thread 35% of its CPU spinning in sub_82411E98: both are waiting behind the GPU. |
| Lap 1 | **GPU** | 98.5%, 25.87 against 26.25 ms. Second wall: render thread work 20.5 ms/frame (78% of the interval), then CP work 19.2 ms/frame (73%). |
| Lap 2a / 2b | **GPU** | 98.6% in both, 25.67/25.44 against 26.02/25.80 ms. |

The CP rule does not fire (GPU above 85%; CP busy is above 90% only because it includes
the GPU fence wait), the render-thread rule does not fire (work 64-78% of the interval),
read-back is under 15% of CP busy, and WAIT_REG_MEM register waits are zero. The chain is
consistent: GPU busy at the wall, so the CP blocks in the fence, so the render thread
spins on the CP read pointer. If the GPU got about 25% faster, the render thread
(lap 1: about 49 fps) and then the CP (about 52 fps) would be next. At 1440p on the
RTX 5060 the first M10 targets are therefore GPU-side: 56 read-back resolves per
frame each cost a downscale dispatch and a GPU copy whether or not the CPU copy is
made (75% are deferred and never used), plus the scene at scale 2. The 720p arm is
needed before any CPU-side conclusion.

Pre segment (minute 1, cold, loading, menu and hand-off mixed): 30.8 fps, GPU 50.7% of
wall, CP 42.8% busy with 18.5 ms/frame in WAIT_REG_MEM (memory) waits, render thread
99% CPU with 66% spin. This minute is pacing/loading and not comparable.

**Cold-store effect:** minute 1 had 448 pipeline waits (434 ms, longest 28 ms; the split
reports `pso_wait_ms=439.69`), 0 timeouts and **0 skipped draws**; frame pacing p99
65 ms, max 746 ms, 6 frames over 100 ms. Later minutes: 17, 23, 32, 24, 3, 1 waits

## 6. KI-047: remaining mechanisms, ranked (first pass; superseded by section 8.3)

Observations so far. Broken: l49 session 1 (2160p, empty store, launcher), l49 session 2
(1440p, +94 pipelines, launcher), **l53 run 1 (1440p, cold store, launcher, always-on wait,
0 skips; police car seen about 5 minutes into play, in gameplay)**. Clean: l49 sessions 3-4
(launcher, 1080p 960x540 guest with +133 pipelines and 720p), the warm launcher 1440p
session, two direct 1440p runs (`full`, `some`), two direct runs with an empty per-run
cache, l50 runs 1 (cold) and 2 (warm), l51 three runs (cold, warm, no-wait). Every broken
case is a launcher session on a cold or partly cold store at 1280x720 guest and scale 2-3;
direct cold runs are 0 of 4. With about 3 broken among about 10 cold-ish sessions and 0 of
about 10 warm ones, the cold correlation is still only suggestive (about 10% by chance);
the launcher association is weaker (the cold launcher 1080p session 3 was clean). Defect
content differs per occurrence (sparse ticks, blue streaks, dense black bars): it depends
on history.

1. **Stale `some` read-back of a re-used composite range (H2, shared-key variant). Medium.**
   Source (`IssueCopy_ReadbackResolvePath`, l53 SDK lines 3600-3880): read-back buffers are
   keyed by (address, length), evicted only after 60 frames unused; a resolve to a key that
   is still alive is not a miss, so it is copied only every 4th time and otherwise leaves
   guest memory as it was (75% of all resolves in this session were deferred), and when it
   is copied it copies the previous same-key slot. If the game composites every car's
   livery in one scratch target and resolves it to one scratch address (same key), a car
   whose composite comes less than 60 frames (1.6 s at 38 fps) after another car's gets the
   other car's composite, or an older one, baked into its atlas. Mapped through a different
   car's atlas layout, that would look like streaks in columns, and blue would be another
   car's paint. It is history- and phase-dependent (random per session), persistent for
   the car's life, independent of draw skips, and decals stay intact if they are separate
   textures. Two sub-cases make true garbage: a copied slot whose GPU copy has not run yet
   (`prev_age=0`, the same open submission; l50 saw such reads on depth tiles) and, on a
   newly created slot, the readback heap is `CreateNotZeroed`, so it holds recycled VRAM.
   Against it: l50 found every one-shot candidate resolve to be a fenced miss, but only in
   the windows its budget covered; the existing diagnostics **cannot see this case**,
   because a resolve line is written only for a fresh key (quiet for 120 frames, longer
   than the 60-frame eviction) or after skips, so a deferred same-key resolve is never
   logged. Does not explain the cold correlation by itself.
2. **Texture-cache staleness of the car's atlas (upload racing the guest CPU writer, or a
   missed invalidation). Medium-low.** The game builds the BC3 atlas on the CPU from the
   read-back. If the texture cache uploads that range while a guest thread is still writing
   it, and the watch is armed after the writes, or an invalidation is lost, the GPU keeps
   the previous content of that memory (another texture or another car's atlas: foreign
   and structured) for the car's life. Timing-dependent, so cold-store CP stalls (pipeline
   waits, synchronous shader translation on the CP thread) can change the odds, and the
   launcher/direct difference could be timing too. No direct signal in this session
   (watch counters normal, no protection failures). Not testable without texture-side
   logging.
3. **CP lag against an unsynchronized guest read. Low-medium.** If the game reads the
   read-back memory a fixed time or number of frames after issuing the composite instead
   of waiting on a fence, any CP stall at that moment (cold store: pipeline waits up to
   28 ms, shader translation) means it reads the scratch memory before the CP has done
   the resolve and copy, and bakes the previous content. This is the only candidate that
   explains "cold only" directly with 0 skips. Against it: the CP read pointer written back
   to the guest is updated only after a batch is executed (`command_processor.cpp` 369-375),
   and the render thread visibly waits on it, so the game does synchronise on CP progress
   at least for ring space.
4. **EDRAM aliasing / render-target ownership transfer at scale > 1. Low.** The composite
   target shares EDRAM tiles with targets of other formats in the same frame; an
   incomplete or wrong transfer at scale 2-3 would leave foreign tiles in the composite.
   That would be deterministic for the same content, so warm sessions should break too,
   and they have not.
5. **H1 (pending-pipeline skip). Excluded for this occurrence** (0 skips, 0 timeouts,
   0 no-op draws in the whole session). Still a possible cause for the l49 cases, which ran
   without the always-on wait.
6. **Excluded earlier:** H3 shifted scaled copy (0 of about 135k in l50), VRAM eviction
   (no pressure here, 5.1 of 7.1 GB), LOD or mip blur (full mesh, crisp decals), genuine
   livery.

## 7. Next decisive step (first pass; section 8.4 has the updated proposal)

A plain rerun with `--d3d12_livery_diag=true` is **not enough on its own**:

- The defect appears in perhaps one cold session in three and on whichever police car
  spawns; a direct cold run has been clean 4 of 4 times.
- The current diag logs a resolve only for a fresh key or after draw skips. With the
  always-on wait there are no skips, so it would log fresh keys only. The leading
  candidate (a deferred or previous-slot copy of a re-used scratch key) is exactly the
  case it does not log, and texture-side staleness (candidate 2) is not covered at all.
  A broken run would at best show the livery resolve as a fresh fenced miss (which would
  exclude H2 and point at the texture side), or show nothing.

Recommended: **one small SDK change first, then make every owner cold run a trap.**

1. **Diag v2 in the l53 SDK branch (owner-internal l54 = l53 + this):**
   - Resolve line for every read-back resolve of a **sporadic key** (the previous resolve
     of the same key was 2 or more frames ago, or never), whatever the decision; this drops
     the per-frame main-scene, shadow and bloom tiles that used up the old budget. Fields as
     now plus `frames_since_prev_same_key`, `frames_since_last_copy`, `copied`,
     `read=this|prev`, `prev_age`, `prev_known_complete`, and whether the slot was created
     in this call (NotZeroed).
   - Overlap line when a resolve writes a range that overlaps a different live key
     (shared scratch with another length or format).
   - Texture-side line: when the texture cache loads (uploads) a texture whose range
     overlaps a read-back destination of the last 600 frames, or any 1024x1024 BC3/DXT5
     or 2048x2048 RGBA8 texture: frame, base, size, format, and later the frame of its
     first write-watch invalidation (an invalidation within a few frames after the load
     means the upload raced the CPU writer; no invalidation while the CPU rewrote the
     range means a missed invalidation).
   - Pipeline waits of 5 ms or more: frame, draw, rt0 base (to line up CP stalls with
     composites, candidate 3).
   - Separate budgets per line kind (for example 256 per minute each) and a per-minute
     count of everything, as now.
2. **Default the diag on in that owner-internal build** (host sets the cvar unless the user
   set it, as l53 already does for `d3d12_perf_split`), so every remaining M10 cold BENCH
   run through the launcher also traps KI-047 with no extra owner effort; the owner
   presses F10 the moment a police car looks wrong, as today. The broken run then names
   the mechanism: livery-sized sporadic resolve `copied=0` or `read=prev` with
   `prev_age=0` points to candidate 1; a fresh fenced miss followed by an atlas texture
   load before the CPU writes finished points to candidate 2; a long pipeline wait right
   before the composite resolve and a clean resolve points to candidate 3.
3. **If no build is wanted now:** the existing l50 script can be adapted for l53
   (`BUILDDIR=private\l53-internal\build`, a fresh BENCH copy or the empty per-run cache
   variant for a cold l53 store, the same 1440p arguments plus `--d3d12_livery_diag=true`).
   Ask the owner to toggle fullscreen by double-click as in the launcher sessions, to remove
   that difference. It is worth running only as a lottery ticket: a clean result says
   nothing, and a broken one is readable only if the livery resolve is a fresh key.
4. Optional cheap side test for candidate 1, no build: a cold launcher-equivalent run with
   `--readback_resolve=full` (about 20 fps). Only a **broken** result is informative
   (it would exclude candidate 1); a clean one is expected anyway.

Also update the KI-047 row: l53 cold 1440p launcher session broken with 0 pending-pipeline
skips, so the l51 always-on wait does not fix it; status back to open/investigating.

### 8.3 Cold-only mechanisms other than pending-pipeline skips (l53 SDK source)

1. **A draw proceeding with an untranslated or placeholder shader: not possible here.**
   With `async_shader_compilation` on, `ConfigurePipeline` (`pipeline_cache.cpp` 952-1110)
   defers *translation* as well as PSO creation to the creation threads on a cold store (warm:
   translated from storage at startup). The draw waits; the creation thread translates the
   queued shaders and creates the PSO (`PrepareRuntimeDescriptionForQueuedCreation`,
   3262-3325); only afterwards does `IssueDraw` call `RequestTextures` with the translated
   texture mask and `UpdateBindings` (`command_processor.cpp` 2978-3070). Timeout or failure
   takes the counted skip path (0 here). One real cold-only oddity: `IssueDraw` keeps the root
   signature that `ConfigurePipeline` returned *before* the wait, which in placeholder mode is
   built without the pixel shader's texture/sampler counts, while the creation thread later
   stores the right one. **Harmless on this PC**: resource binding tier 3 is logged and
   `d3d12_bindless` defaults to true, so both are the one bindless root signature. It would
   matter only with bindless off (tier 1 hardware, possibly some vkd3d setups): worth a small
   SDK fix (reload `pipeline->root_signature` after a successful wait), not KI-047 here. Ucode
   analysis always runs on the CP thread before queueing and translation is serialised by
   `translation_request_lock_`; no analysis/translation race found.
2. **The CP thread stalls while a composite is in flight (timing, cold only). Now rank 1,
   medium.** On a cold store the CP thread blocks in pipeline waits (up to 28 ms in minute 1,
   up to 19 ms in the minute before the catch) while creation threads and the driver compile on
   other cores. With skips excluded, that is the only store-dependent difference left. It
   breaks the livery if a consumer is not ordered behind the CP: (a) a guest thread reading the
   read-back composite or building the atlas on a fixed frame budget instead of a fence;
   (b) the texture cache uploading the atlas range while a guest thread is still writing it,
   with the watch armed after the writes (stale GPU copy for the car's life); (c) a non-miss
   `some` read of the previous slot while its GPU copy is still in flight (l50: 58% of
   previous-slot reads not known complete), which tears the copy; on a newly created slot the
   `CreateNotZeroed` readback heap holds recycled VRAM. All three are races whose window
   widens when the CP falls behind the guest, and all fit "cold only, rare, history-dependent
   content, decals intact, persistent".
3. **Stale `some` copy of a re-used composite key (section 6 item 1). Medium-low.** Real and
   invisible to the current diagnostics, but not store-dependent by itself; it explains
   cold-only only together with item 2.
4. **First resolve into a freshly allocated render target or EDRAM tiles. Low.** Render
   targets, EDRAM ownership, readback buffers and textures are per-process in both runs, so
   the composite target is "first use" in every session, warm or cold; this cannot separate the
   arms without the timing of item 2.
5. **Logic gated on `shader_count`/`pso_count > 0`: none found** in the draw path apart from
   the wait itself; the counters are audit-only.
6. **Excluded for this occurrence:** pending-pipeline skip (0 in both runs), shifted scaled
   copy (l50), VRAM pressure.

### 8.4 Updated next step

The question moves from "was a draw dropped" to "was the composite or atlas consumed before
the CP/GPU work for it was complete". The existing `d3d12_livery_diag` cannot answer it (no
skips to key on; deferred and non-fresh resolves are not logged; nothing on the texture side).

1. **Diag v2 (section 7 item 1) plus cold-specific fields, defaulted on in the next
   owner-internal measurement build**, so every cold BENCH run is a trap:
   - every pipeline wait of 1 ms or more: frame, draw index, rt0 base and size, and the
     frame/draw of the next read-back resolve from the same EDRAM base;
   - on every sporadic livery-sized read-back resolve: `prev_known_complete`, `prev_age`,
     `copied`, slot newly created, and CP wait milliseconds in the last 5 frames;
   - texture side: frame of the first upload of each 1024x1024 BC3 and 2048x2048 RGBA8
     texture and of each later write-watch invalidation of its range (an invalidation after
     the upload within a few frames means the upload raced the guest writer).

   thread: CP stalls kept, creation-thread concurrency removed). Informative only if broken
