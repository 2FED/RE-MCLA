## 2. S3: why two F10 captures had different sizes, and the fix

- The F10 package first reads back the guest output (`src/mcla_diagnostics.cpp` `CaptureGuestFrame`,
  provider in `src/mcla_app.cpp`), i.e. the presenter's guest-output texture at render-target size
  (1920x1080 at the 1080p setting). If that fails it falls back to a GDI BitBlt of the window client
  area (3840x2160 in fullscreen on the 4K display).
- The SDK's `D3D12Presenter::CaptureGuestOutput` (`src/ui/d3d12/d3d12_presenter.cpp` :326-331)
  refuses the newest mailbox frame when it has not been presented yet (sequence above the presented
  watermark). The producer runs ahead of the present, so an F10 at the wrong moment fell back to the
  window capture: a timing race, not force_hidef or the run's settings. The manifest records it
  (`capture.frame_signal.source`: `guest-output-readback` or `win32-client-bitblt`), and the log shows
  `guest frame readback failed; using window capture`.
- Fix (host only): the provider retries `CaptureGuestOutput` up to `kGuestFrameCaptureAttempts` = 40
  times, `kGuestFrameCaptureRetryDelay` = 16 ms apart (`src/mcla_diagnostics.h`), well inside the
  worker's 1500 ms bound (`static_assert` in `src/mcla_diagnostics.cpp`). The watermark catches up
  within about a frame, so captures are the guest output at render-target size. The window fallback
  stays for real failures (for example a hung GPU).
