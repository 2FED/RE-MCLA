## 3. Race-start lag attribution (16:53:40-16:56:47)

- Onset 16:53:40 during free-roam driving to the championship marker (F10 #5 frame, before the race
  warp at 16:54:14); end abruptly at 16:56:47 (10 s fps 23 -> 38) at race clock about 2:20, with no log
  event at either edge. Duration about 3 min 7 s; the owner's "eased after about 2.5 minutes" matches
  the race portion.
- Not pipelines (0 ms waits, pso_count 0), not streaming (0 stalls), not VRAM (5.40 of 6.67-6.73 GB,
  no near-budget steps), not read-back/fence waits (unchanged per frame), not the GPU (GPU busy
  22.5-26 ms per frame at 20 fps, about 50% utilisation; GPU clock and temperature actually dropped).
- The frame was produced slowly, not snapped late: audit cpu/gpu frame work p50 49-52 ms (vs 23-29 ms in
  other audits), so this is a different shape from the "Hitch attribution" jitter of the previous
  analysis (where work was 23-38 ms and intervals snapped to vblank multiples).
- The bottleneck was the GPU-command (CP) thread: CP busy 37-55 ms per frame (normally 19-27) at the
  same workload (draws per frame 5.7-8.5k, request calls 10-15k per frame, both normal for races).
  **Every host-side unit cost rose by about 1.6-2x simultaneously:** CP CPU per draw 2.2-2.8 -> 4.4-5.1 us,
  every draw phase (setup, prim, rt, pso, tex, bind, vb, record), upload memcpy throughput 3.7-4.3 ->
  2.2-2.5 GB/s, watch arm/disarm 0.53-0.65 -> 0.99-1.44 us per VirtualProtect call, watch lock wait
  32 -> 87 ms per minute, CP kernel time 2 -> 6-8 ms per frame. The guest worker threads XThread4A88 and
  XThread8914 show more non-idle samples (idle-function share 65% -> 45-50%) with the same functions,
  i.e. the same work taking longer.
- A uniform slowdown of all CPU work (user code, syscalls, memcpy) at unchanged workload points to the
  host CPU running slower for those three minutes (laptop CPU clock/power limit, or contention from
  something outside the game), not to a game or emulator code path. We log GPU clocks/temps but no CPU
  clock, temperature or system load, so the external cause cannot be confirmed from this session.
- Why it eased: the per-call costs returned to normal at 16:56:47 (1.1 us/arm in the partial minute,
  0.69 us by 16:58) with nothing changing in the game; the next two races in the same area ran at
  35-39 fps. Not "warm-up" of the store or caches (no compiles, no streaming stalls before or after).
- Suggested telemetry: add CPU effective MHz (CallNtPowerInformation ProcessorInformation or a TSC vs
  APERF/MPERF-style ratio), CPU package temperature if available, and system-wide CPU load to the minute
  line, so the next such episode can be attributed directly.

and camera smoothing) better than the Deck's steady-15-fps AI explanation. The steady-low-rate case
would be the championship race 1 lag (17-23 fps sustained), and the owner pressed F10 there for
stutters, not for traffic.
