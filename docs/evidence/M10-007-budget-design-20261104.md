# M10-007 / KI-048 video-memory budget: design for M11

Read-only design by an Opus subagent on 2026-11-04 (host src/mcla_texture_budget_win.cpp, SDK v0.20.0.8 source, the l67 30-minute session); accepted by the primary agent. Key corrections: the budget monitor is host code; 1080p and 1440p are both render scale 2 (same footprint), only 720p (scale 1) saves video memory.

Status: design only (read-only analysis). Sources: `docs/known-issues.md` KI-048 and KI-047 rows,
`docs/evidence/M10-l67-pc-30min-ki035-20261104.md` sections 2-3, `docs/M10-priorities.md` M10-007,
`docs/evidence/M10-002-readback-design-20261101.md`, host `src/mcla_texture_budget_win.cpp`,
`src/mcla_render_target_policy.h`, and the SDK at v0.20.0.8 (l67 SDK worktree). Line numbers are
from that SDK tree. Nothing was built or run; every size below is derived from code, and the split
of the measured 6.9 GB between components is an inference until the step-0 census exists.

Key facts used throughout:

- Launcher targets (`mcla_render_target_policy.h`): 720p = 1280x720 guest at scale 1;
  **1080p = 960x540 guest at scale 2; 1440p = 1280x720 guest at scale 2**; 2160p = 1280x720 at
  scale 3. 1080p and 1440p therefore share the same scale-dependent fixed footprint (section 1);
  only guest-resolution-dependent resolve extents differ.
- The budget logic is in the **host**, not the SDK: `src/mcla_texture_budget_win.cpp` sets the
  SDK cvars `texture_cache_memory_limit_soft/hard` at start-up from
  `IDXGIAdapter3::QueryVideoMemoryInfo(LOCAL)` and runs a 1 s monitor thread. The SDK has no
  QueryVideoMemoryInfo call and no residency management (`SetResidencyPriority`, `Evict`,
  `MakeResident` are never used).

## 1. Footprint inventory (from code)

LOCAL (VRAM) segment only. READBACK and UPLOAD heaps are system memory (NON_LOCAL segment) and do
not count against the LOCAL budget the monitor reads.

Effective cache limits as the SDK applies them: `limit = cvar + 24 MB x (scale^2 - 1)`
(`texture_cache_memory_limit_render_to_texture`): +72 MB at scale 2, +192 MB at scale 3.

Host start-up sizing (`ApplyTextureCacheBudget`): `hard = clamp(min(0.8 x budget, budget - 1536))`,
`soft = clamp(budget / 2, 384, 4096)`. l67: budget 7,131 MB gives soft 3,565 / hard 5,595 MB.

### Reading the l67 numbers against the code

The process sat at 6,906-6,916 MB for 68 minutes, a flat plateau. A flat plateau is what the
soft-limit equilibrium produces: the cache grows with city streaming (new texture keys; old keys at
reused addresses stay until 30 s unused) until it reaches soft + 72 = 3,637 MB, and the 30-second
LRU then holds it there. If so, the cache is about 3.6 GB and the remaining about 3.3 GB is
non-texture: shared memory (up to 0.5), EDRAM (0.04), scaled-resolve heaps (0.2-1+ GB), render
targets (about 40 MiB each, so 1-2 GB for 25-50 keys), presenter and driver. This is consistent
but **not measured**: the cache total exists only as a profiler counter
(`COUNT_profile_set("gpu/texture_cache/total_host_memory_usage_mb")`) that is never logged, the
same for `scaled_resolve_buffer_used_mb`, and RT count/size and shared-memory residency have no
counter at all.

What the logs can show today: LOCAL usage/peak/budget every 60 s and at exit, every near-budget
step, the start-up limits, GPU ms per frame (`MCLA_PERF_SPLIT`), read-back sync statistics
(`MCLA_READBACK_SYNC`, max single wait per minute). What they cannot show: texture cache total and
count, textures destroyed/created per minute, scaled-resolve MB, RT count/MB, shared-memory
resident MB, NON_LOCAL usage (demotion of our allocations to system memory), paging traffic, GPU
clocks, temperature or power.

At scale 3 (2160p) the code alone predicts over-commit on 8 GB: soft about 3.3 GB plus about
90 MiB per RT key plus scaled-resolve heaps (up to 4.5 GiB address space, committed as touched)
plus 0.5 GB shared memory. The l41 measurement (peak about 7,350 against 6,740 MB) fits. On
12/16 GB cards soft and hard scale with the budget (budget/2), so the cache again fills to half of
it: a 2160p run on the 3080 Ti/6800 XT shows the true fixed footprint only if the census separates
the cache from the rest.

## 2. Why the cache cannot get back under budget

1. **The floor is the starting soft limit** (`floor_mb_ = soft_mb` in `Monitor::Start`). The
   monitor only ever lowers the **hard** limit, 256 MB per 10 s, down to that floor.
2. With the cache held at the soft limit by the 30-s LRU, lowering hard from 5,595 to 3,565 MB
   **cannot evict anything**: the cache never exceeds soft + 72 MB by more than a transient. That
   is why the eight steps were "harmless": they were almost certainly no-ops. The evidence wording
   "the cache cannot get back under" is better put as "the monitor has no lever left: its floor
   equals the level at which the cache already sits".
3. Nothing else is ever trimmed: RTs, scaled-resolve heaps and shared memory only grow, and none of
   them is visible to the monitor.
4. The OS budget moves (5,936-7,131 MB across sessions; 7,131 to 6,466-6,721 MB within l67), and
   a soft limit fixed from the first budget reading never follows it down.

### Correct behaviour

- **Steer the soft limit, not the hard limit.** Soft eviction removes only textures unused for
  30 s whose last submission completed, the safe kind (the l17 garage hang came from ratcheting
  the hard limit every second and destroying textures a scene still needed). Target:
  `cache_target = budget - non_texture - headroom`, with `non_texture = LOCAL usage - cache total`
  (needs the SDK cache total, step S0). Step soft down 256 MB per 10 s while over target, floor
  about 1,024 MB (2.7x the SDK default 384 MB, which M8-001 found churny), and step it back up
  with hysteresis (headroom above 1 GB for 60 s) so the moving budget is followed both ways. Keep
  hard = soft + 512 or more as a backstop only.
- **Scale-aware start values** until the census exists: at scale >= 2 on budgets below 10 GB,
  soft = min(budget/2, 2,048) (see the short-term mitigation). The dynamic soft control is the
  actual fix, because the budget moves.
- **Eviction below the floor under sustained over-commit** is acceptable only as soft (lifetime)
  eviction; hard-limit eviction below the floor would bring back the l17 failure class.
- **Cap non-texture growth**: RT trim (release RTs that own no EDRAM range and were unused for N s,
  after their last submission completed; the owner-range selection already exists in
  `RenderTargetCache::ClearCache`, but the existing path relies on a full queue drain before it
  runs, so the trim must use deferred release). Scaled-resolve heap release later and only if the
  census shows it is large (needs tile-mapping updates and proof that no texture or read-back key
  references the range; higher risk).
- **Residency priorities**: mark EDRAM, shared memory, scaled-resolve heaps and RTs HIGH and
  textures NORMAL (`ID3D12Device1::SetResidencyPriority`), so that under over-commit VidMm demotes
  cold textures first. Does not prevent over-commit; should shorten the paging stalls on hot
  resources. Cheap.

## 3. Hitch mechanism and options to bound the wait

Mechanism: a resolve matched by the KI-047 sync rules (composite family, scope 0) is forced:
`AwaitReadbackCopySubmission` (`d3d12/command_processor.cpp:3000-3018`) ends the open submission
and `CheckSubmissionFence` waits on its fence with `WaitForSingleObject(..., INFINITE)` (`:4558`).
The wait covers the backlog in that submission (kicks at 512 draws keep it short normally). Under
over-commit VidMm pages our allocations around the submission, the fence completes 0.3-1.0 s late,
and the CP thread (hence the frame) blocks for exactly that time: the minute's max frame equals
`max_wait_ms` within about 15 ms in 25+ minutes. `forced_wait_failed=0`, `fallbacks_to_full=0`:
correct, just slow.

| Option | What | KI-047 risk | Cost | Verdict |
|---|---|---|---|---|
| H1 Avoid over-commit | soft-limit control, RT trim, residency priorities | none (sync logic untouched) | low-medium | **primary** |
| H2 Timeout, then read the previous slot or skip the CPU copy | `WaitForSingleObject(ev, T)`; on timeout behave like plain `some` | **high**: forced keys are by construction one-off composites (rule c, base 0) or keys last resolved 8+ frames ago (rule b); their previous slot is exactly the stale data behind KI-047 (l54: `decision=deferred read=prev` 25 s before a catch) | trivial | **reject** as a default; at most a dev-only measurement cvar |
| H3 Timeout, skip only if the key will be re-resolved soon | skip when the key had a steady cadence in the last N frames | medium-high: rule-matched keys rarely have a steady cadence, so the gain is small and the classifier sits on the KI-047 failure surface | low | not worth it |
| H4 Timeout, then complete lazily behind a read trap | after T ms return without the memcpy, protect the destination guest pages no-access (the watch machinery already arms protections), finish the memcpy from the own slot when the fence is seen complete (frame end / `CompletedSubmissionUpdated`) or when a guest or host access faults (the handler waits on the fence) | low if every CPU reader goes through the protected view (guest code and host HLE both fault); GPU consumers unaffected (queue order) | high: read faults, multi-threaded handler, fault cost under Wine (write faults already 2.2-2.9 s/min) | **M11 stretch**, only if H1 leaves >250 ms waits; would also remove most of the 10-17 s/min wait and help the Deck |
| H5 Isolate the forced copy | end the submission before recording the forced copy so it sits alone | none | low | does not help under paging (the queue is in order) |

A behaviour-neutral addition for every option: per-minute counts of forced waits over
100/250/500 ms with their rule bit and `gpu_busy`, plus NON_LOCAL usage at that moment, so each
hitch is tied to paging (or not) without changing behaviour.

## 4. Measurement additions (per-minute `MCLA_VRAM v=1` line, host + SDK)

Host (already owns the DXGI adapter and the 60 s report):
- LOCAL usage/budget (present), **NON_LOCAL usage/budget** (`DXGI_MEMORY_SEGMENT_GROUP_NON_LOCAL`):
  rising non-local usage at a constant total footprint is the signature of demotion.
- Budget changes in the minute (`RegisterVideoMemoryBudgetChangeNotificationEvent`, or min/max of
  the 1 Hz samples).
- **GPU clock, temperature, power without NVAPI**: `D3DKMTOpenAdapterFromLuid` (DXGI adapter LUID),
  then `D3DKMTQueryAdapterInfo` with `KMTQAITYPE_NODEPERFDATA` (`D3DKMT_NODE_PERFDATA`: Frequency,
  MaxFrequency, Voltage) for the 3D node and `KMTQAITYPE_ADAPTERPERFDATA`
  (`D3DKMT_ADAPTER_PERFDATA`: MemoryFrequency, Power, Temperature in deci-degrees C, FanRPM). This
  is the WDDM 2.4+ source Task Manager uses; drivers may leave fields at 0, which must be logged
  as `n/a`. Sample at 1 Hz, report min/avg/max per minute. Skip under Wine.
- Optional paging counter: `D3DKMTQueryStatistics` segment statistics (bytes resident/committed,
  paging transfer bytes) as per-minute deltas. Verify the structure fields against the WDK
  `d3dkmthk.h` before relying on them; best effort.

SDK (read-only accessors, no behaviour change):
- texture cache: total MB, count, destroyed/created per minute (soft vs hard reason);
- scaled-resolve heaps: `scaled_resolve_heap_count_ x 16 MiB`;
- shared memory: `buffer_tiled_heaps_.size() x 4 MiB` (or 512 MiB when not tiled);
- render targets: count and summed `GetResourceAllocationInfo` bytes split colour/depth/host-depth,
  plus EDRAM buffer MB;
- PSO count; residual = LOCAL usage - the sum above (driver, presenter, PSOs).

Reading rule: GPU ms per frame up with node frequency down and temperature at its limit = thermal;
up with clocks flat and NON_LOCAL usage or paging bytes up = paging. The static pause menu (constant
content: 23.9-29 ms early vs 32.5 ms late on l67) is the cleanest comparison window.

## 5. Step plan for M11

Each step is one owner A/B on the same 1080p Unlocked route on the 8 GB RTX 5060 laptop (30+ min,
same pause-menu and freeway segments), plus the 2160p census on the 3080 Ti/6800 XT when available.
A step is accepted on evidence, not on implementation.

| Step | Change (cvar, default) | A/B | Accept when |
|---|---|---|---|
| S0 census | host `mcla_vram_census` (on in owner builds), SDK size accessors; no behaviour change | one 1080p and one 1440p session (same scale, separates guest-resolution effects), one 720p control; 2160p on a 12/16 GB card | inventory filled; cache total confirmed near 3.6 GB (or not); thermal vs paging decided from clocks and NON_LOCAL |
| S1 soft-limit control | host `mcla_texture_budget_mode=soft` (legacy `hard`), `mcla_texture_soft_floor_mb=1024`, `mcla_texture_headroom_mb=512` | soft vs legacy on the route | LOCAL usage <= budget after 10 min and stays there; texture re-creates per minute low; no new >50 ms clusters at step times; KI-047 composite counters unchanged |
| S2 residency priority | SDK `d3d12_residency_priority` (off) | S1 off with S2 on vs both off (deliberate over-commit) | max forced read-back wait and >250 ms frames per minute drop |
| S3 RT trim | SDK `d3d12_render_target_trim_seconds` (0 off; try 60), deferred release after the last-use submission | on vs off with S1 on | RT MB falls; no RT re-create hitches; no ownership/transfer corruption (F10 audits, KI-038/032 signs) |
| S4 bounded wait (conditional) | SDK `d3d12_readback_sync_lazy_ms` (0 off), option H4 | only if waits >250 ms remain after S1-S3 | no waits over T; KI-047 police livery on cold stores (about 3 in 10 cold sessions broke before the sync, so 10 cold sessions) |
| S5 2160p | S0-S3 at scale 3 on 12/16 GB; 8 GB recommendation text | census | documented 2160p recommendation for 8 GB |

M10-007 closes when the 30-minute 1080p session stays under budget with no >50 ms frames from
budget control, and 2160p shows the true footprint.

## Short-term mitigation for a volunteer build

Safe, host-only, no SDK change, does not touch the KI-047 sync:

1. In `ApplyTextureCacheBudget`, at scale >= 2 on budgets under 10 GB, start the **soft** limit at
   `min(budget/2, 2048)` MB and set the monitor floor to the same value (hard unchanged at
   `min(0.8 x budget, budget - 1.5 GB)`). On the 8 GB laptop that frees about 1.5 GB of the
   presumed 3.6 GB cache, enough to stay under a 6.47 GB budget if the non-texture part is about
   3.3 GB. Soft eviction only removes textures unused for 30 s, so the l17 hang mechanism is not
   reintroduced; the risk is more texture re-creation when revisiting areas (still about 5x the
   SDK default soft limit), visible in the existing frame-time lines. The user-override path
   (`HasNonDefaultValue`) stays, and the start-up line already logs the limits, so a volunteer can
   be told how to restore the old values. If S0 shows the cache is far below 3.6 GB, this change
   is a no-op; it cannot make things worse.
2. Launcher/tester-guide note: on GPUs with 8 GB or less, prefer 720p (scale 1: RTs about 10 MiB
   each, no scaled-resolve heaps) for long sessions. 1080p and 1440p are both scale 2 and share the
   same fixed footprint, so 1440p is not lighter on memory than 1080p (the existing "prefer 1440p"
   workaround in KI-048 should be revisited). 2160p is not recommended on 8 GB.
