# M11 l104 owner build (2026-11-15): the l103 levers and low latency as build defaults

**Headline.** l104 = main c45d81a (the l103 host commit 59c6c22 plus docs-only commits) plus a
host-only diff that turns the owner's 2026-11-15 decisions into build defaults through the m10
defaults (`src/mcla_m10_defaults.h`): **A.** the three per-draw levers ON
(`d3d12_fetch_identity_v2`, `d3d12_rt_update_memo`, `cp_reg_write_skip_unchanged`); **B.** low
latency from one vendor-independent cvar set (`d3d12_low_latency_mode=auto`,
`d3d12_low_latency_auto_antilag2=true`, `d3d12_frame_lead_strict_low_latency=1`), which the
unchanged SDK resolves to: NVIDIA Reflex replacing the strict frame lead bound only while its sleep
is active (stale-sleep fallback and lead-2 guard at the normal latch action), AMD Anti-Lag 2 with
the strict bound kept on, Intel and Wine/Deck no backend and no change. Six new control keys (139
keys, 43 conflict pairs). **No SDK change**: built against `private/l101-sdk-install` (a49e511);
the three SDK DLLs are byte-identical to l101-l103 (asserted). Built and unit-tested only; not
signed, not run. Spark not used (no bounded extraction or triage task in this build step; the SDK
proof below was read directly from the source).

## Proof from the SDK source (a49e511, `private/l101-sdk-wt`)

Common path: `d3d12_low_latency_mode` and `d3d12_low_latency_auto_antilag2` are read once in
`Activate()` (`src/ui/low_latency.cpp:559-567`), which calls
`SelectBackend(mode, g_vendor, wine, d3d12_low_latency_allow_wine, d3d12_low_latency_auto_antilag2)`
(`:566`) with `wine = rex::content_log::RunningUnderWine()` (`:562`); with a backend the state is 2
(`:591`), without one 1 (`:583`). At every guest frame open (`src/graphics/d3d12/command_processor.cpp:6960-6980`)
the configured `d3d12_frame_lead_strict` (1) is replaced by `ll.effective` only when
`d3d12_frame_lead_strict_low_latency` is on (`:6967-6970`) and `EvaluateLeadActive(QueryLeadState(),
d3d12_frame_lead_strict_low_latency_antilag2)` (`:6973`) returns `kActive` (`:6977`);
`FrameLeadEffectiveStrictMode` returns the configured mode when `!active || latched`
(`include/rex/graphics/util/frame_lead_limit.h:308`). The init line is logged for every mode but
off (`low_latency.cpp:576`).

1. **NVIDIA (vendor 0x10DE, `low_latency.h:43`), Windows**: `SelectBackend` case `kAuto` returns
   `{kReflex, "selected"}` (`low_latency.cpp:122-124`). `EvaluateLeadActive` returns `kActive`
   only when init succeeded (`:169`), not Wine (`:172`), the backend is Reflex (`:179`), not markers
   only (`:182`), a sleep was recorded, the sleep is on (`:188`), the last sleep succeeded (`:191`)
   and it is fresh for the current or previous guest swap (`LeadSleepFresh`, `low_latency.h:106`;
   otherwise `kStaleSleep`, `low_latency.cpp:195`): strict is replaced (effective 0) only on those
   frames, the configured strict 1 applies on every other frame (the stale-sleep fallback).
   Guard at its default action 0 = `kLatch` (`command_processor.cpp:363`, `frame_lead_limit.h:386`,
   `FrameLeadGuardActionFromCvar` default `:401`): more than 80 lead-2 frames among the last 2700
   relaxed frames (`frame_lead_limit.h:298-299`, `:547`) set `latched = true` (`:566`), one
   `MCLA_LEAD_LL kind=guard_trip` line (`command_processor.cpp:7340`); once latched, only action 2
   can unlatch (`frame_lead_limit.h:524-526`), so with action 0 the latch holds for the rest of
   the session and every frame runs the configured strict 1.
2. **AMD (vendor 0x1002, `low_latency.h:44`), Windows**: case `kAuto` returns
   `auto_antilag2 ? {kAntiLag2, "selected"} : {kNone, "auto_antilag2"}` (`low_latency.cpp:126-128`);
   with the default true: Anti-Lag 2. `EvaluateLeadActive` with
   `d3d12_frame_lead_strict_low_latency_antilag2=false` returns `kAntiLag2` for an Anti-Lag 2
   backend (`:175-177`), never `kActive`, so every frame keeps the configured strict 1 (state line
   `active=0`, `lead_ll_active_frames=0`). The guard window only counts relaxed frames, so it never
   trips on AMD.
3. **Intel and any other vendor, Windows**: case `kAuto` falls through to `{kNone, "vendor"}`
   (`low_latency.cpp:130`): no backend, state 1 (`:583`), `QueryLeadState` reports `init_ok=false`
   (`:667-668`), `EvaluateLeadActive` returns `kInit` (`:169`): strict 1 on every frame. Only the
   `MCLA_LOWLAT kind=init ... backend=none result=vendor` line and one `MCLA_LEAD_LL kind=state
   active=0` line are new.
4. **Wine/Proton (Deck)**: `if (under_wine && (!allow_wine || mode == Mode::kAuto))` returns
   `{kNone, "wine"}` (`low_latency.cpp:112`): auto is off under Wine whatever
   `d3d12_low_latency_allow_wine` says; no backend, `kInit`, strict 1 on every frame. New lines:
   `MCLA_LOWLAT kind=init mode=auto vendor=0x1002 backend=none result=wine ... wine=1` and one
   state line with `active=0`.

Guard margin: the l100 pc/auto-noguard soak's worst 2700-frame window was about 63-67 lead-2
frames against the 81 trip point (78-83 % of it), and the l98 pc/auto soak tripped the same l97
guard after 5 minutes. A trip in normal play is therefore possible. Its cost: the session falls
back to the configured strict 1 for its rest (exactly the l103 default, safe), and Reflex keeps
sleeping; one `guard_trip` line and `lead_ll_latched=1` in the minute lines show it.

Verify keys with the levers on (verify wins in the SDK): `cp_reg_write_skip_verify` - a write the
skip would drop takes the normal path when verify is on (`include/rex/graphics/command_processor.h:305`);
`d3d12_rt_update_memo_verify` - a memo hit returns early only `if (hit && !options.verify)`
(`command_processor.cpp:2480`); `d3d12_fetch_identity_verify` checks every memo v2 hit
(`:2392`, cvar text `:201-206`). The verify keys write other cvars than the defaults, so the m10
defaults never treat them as an arm (unit-tested).

## Risks and limits

- The levers were verified on the PC (RTX 5060) only; on the Deck and on AMD they never ran.
  The checklist sends the owner to deck/verify-all at any glitch.
- The guard can trip in normal play (see above); the cost is strict for the rest of the session.
- The m10 defaults also act in volunteer builds (`MCLA_M10_SPEEDUP_DEFAULTS`): a volunteer build
  from this host with an SDK that registers these cvars (the l95/l97/l100/l101 SDK work) gets the
  levers and low latency auto; an SDK without them (e.g. the gate SDK v0.20.0.8) logs each entry
  as `unavailable`. Which SDK the next volunteer build uses is a coordinator decision.
- Not run: no physical PASS is claimed. The owner runs, signing and staging are pending.
