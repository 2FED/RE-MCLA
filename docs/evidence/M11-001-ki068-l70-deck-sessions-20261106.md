# KI-068 "storage device removed" on the Deck: l70 session analysis

Read-only analysis by an Opus subagent on 2026-11-06 of the owner's two l70 Deck sessions (two consecutive saves; then a restart check) and the generated save-manager code; accepted by the primary agent. It supersedes the ghost-handle hypothesis of the preparation note.

Read-only analysis, 2026-11-06. Inputs: the two l70 owner sessions (save session `2902c412...`,
check session `f49b7b47...`), SDK v0.20.0.8 source (`c63895c`), generated guest code
(`generated/default`). No build, launch or git write was made.

## 0. Bottom line

- **The ghost-handle hypothesis is not supported.** The save session logged no `[content]` line at
  all. That means no 145/5/32 delete, Recover or Begin failure, and no XamContentCreate/Close
  failure (even probes log). The F10 save copy at the dialog found 4 files and no `.rex*` entries,
  and the SDK transaction indicator read 0.
- **New leading hypothesis (about 80%): the game's own save-file identity check fails.** Before
  every save, MCLA re-opens `mc4.sav` and compares the file's **creation time** with the value it
  remembered after the previous save or load. If they differ, it routes the UI to the same state
  (24) that it uses for "device not connected / storage devices changed".
  - The SDK caches the creation time **at the moment it creates the empty file**:
    `HostPathEntry::CreateEntryInternal` -> `GetInfo` straight after `fopen "wb"`.
  - On a later re-mount, the SDK reads the creation time back from the host (`ListFiles`).
    - On Windows NTFS the creation time is stable, so the two values match.
    - Under Wine on a Linux filesystem, `ftCreationTime` is not a stable birth time. As recalled,
      Wine falls back to st_ctime/st_mtime when the stat has no birth time; this must be confirmed.
      That value moves when the 537 KB save is written, so the two values differ.
    - Every call succeeds, so nothing is logged.
- **This explains the owner's pattern exactly.**
  1. The 1st save passes: the remembered value came from the boot load, which also read the host
     value.
  2. The 2nd save fails: the remembered value is the SDK's cached creation-moment value from save 1.
  3. "CHANGE STORAGE DEVICE" frees the game's remembered-time table, so the next check finds no
     entry and passes. The save after that fails again.
  4. Windows is never affected.

## 3. Success-path and uninstrumented decisions that reach the dialog, mapped to guest code

### Guest save platform layer

The per-user slot array is at `0x82905C20`, 168 bytes per slot, with the slot index at `+10100` of
the save manager:

- `+0`: op state; `+4`: sub-state; `+56`: device id; `+68`: the file path `<root>:\mc4.sav`;
- `+100`: file handle; `+104/+108`: buffer and length;
- `+112`: verify/ok flag; `+113`: create-always flag; `+114`: "file existed" flag;
- `+124`: **a hash table filename -> FILETIME (creation time)**;
- `+160`: XNotify listener.

The functions involved:

- `sub_82450058`, `sub_82450188`: XContentCreateEx wrappers. A saved-game content type ORs flag
  0x10.
- `sub_82616D38`: save start, op state 6, `XamContentCreateEx` flags `0x12` = CREATE_ALWAYS.
- `sub_82616F00`: load start, op 8, OPEN_EXISTING.
- `sub_826170B8`: **verify start, op 12**: OPEN_EXISTING (flags 3) on the same file.
- `sub_82617C70`: save state machine.
  - sub-state 1: `CreateFile(GENERIC_WRITE, share 7, CREATE_ALWAYS or CREATE_NEW,
    FILE_FLAG_WRITE_THROUGH)`, then `WriteFile` (overlapped).
  - sub-state 2: `ok = bytes == length`, `CloseHandle`, `sub_82617AE0`, then `XamContentClose`.
  - sub-state 3: report the result.
- `sub_82617F98`: load state machine. It also calls `sub_82617AE0` after opening the file.
- `sub_82617AE0` (**record**): `CreateFile(GENERIC_READ, OPEN_EXISTING)`, then `GetFileTime`.
  `sub_8275CDB0` = NtQueryInformationFile class 34, FileNetworkOpenInformation; it keeps only
  `CreationTime`. It stores the value in the `+124` table under the file name.
- `sub_82617300` (op 12) + `sub_82617228` (**compare**): opens the file read-only, calls
  `GetFileTime`, and sets `+112 = (stored.CreationTime == current.CreationTime)`. If there is no
  stored entry, `+112 = 1`. If the open fails, `+112` stays 0. It then calls `XamContentClose`; op
  13 reports `+112`.
- `sub_822013E0` (save-manager update, op 13):
  - verify ok: posts message `[+172]`, which sets the device and proceeds to the save;
  - verify failed and a time is remembered for the file (`sub_82617838`): posts message `[+176]`;
  - otherwise posts `[+124]`.
  - `sub_82202640` maps `[+176]` -> **UI state 24**.
- `sub_822003A8` uses the same **UI state 24** when `XamContentGetDeviceState == 0x48F` or a
  `XN_SYS_STORAGEDEVICESCHANGED` notification is pending (`sub_826177A8`, `sub_82617750`).
  So state 24 is the "storage device removed/changed" screen.
- `sub_822012E8` (device-selector flow, op 3): `sub_826181F8` -> `sub_82617BE8` **frees the whole
  `+124` table**. This is the "CHANGE STORAGE DEVICE" reset.

(I did not decode the message text from the string table. The xex image is not decrypted in the
tree. The equivalence of state 24 with the device-not-connected / notification path comes from the
code above.)

## 4. Ranking and the decisive l71 instrumentation

1. **(~80%) Creation-time identity check mismatch (Wine timestamps + SDK caching).**
   1. Boot load: `ListFiles` -> host creation time Th0. `sub_82617AE0` records Th0.
   2. Save 1 verify: re-mount -> Th0 == Th0 -> pass.
   3. CREATE_ALWAYS recreates the package, the game creates `mc4.sav`, and the SDK caches
      `T0 = GetInfo` straight after `fopen "wb"` (empty file). The 537 KB write follows (host
      ctime/mtime -> T1). Record = **T0** (cached).
   4. Save 2 verify: re-mount -> `ListFiles` -> Wine `ftCreationTime` = T1 (or later), and
      T1 != T0. The result is `[+176]` -> state 24, the dialog. No call fails, so nothing is logged.
   5. Reselect frees the table -> the next verify finds no entry -> pass -> that save records the
      cached value again -> the save after it fails.

   - **Prediction:** a Windows PC reproduces it if the save file's creation time changes between
     two saves. For example, set `(Get-Item ...\mc4.sav\mc4.sav).CreationTime` from PowerShell after
     save 1 while the game runs (on a copy profile), then save again: the dialog should appear.
     This is non-destructive and checks the mechanism without the Deck. FAT32/exFAT would NOT
     reproduce it, because creation time is stable there; this reverses the earlier "FAT
     reproduces" prediction.
2. **(~7%)** The verify fails for another reason: the read-open in op 12 fails (it would log
   `[NtCreateFile] FAILED`, which is absent), or `GetFileTime` fails (class 34 is always
   implemented). Unlikely.
3. **(~5%)** Device id field zeroed in-process (`sub_82617700` returns "no device" without an XAM
   call). No writer of 0 was found on the save path.
4. **(~3%)** Save-write short count. It would not reach state 24.
5. **(~5%)** Something not yet decoded in the UI layer (message `[+124]` path, list re-verify loop
   `sub_8262CB88`).
6. **Excluded:** ghost handle + deferred delete (rank 1 of the prep doc), GetDeviceState 0x48F,
   XNotify 0xB, any XamContentCreate/Close failure.

**Instrumentation for l71 (INFO level; content devices only; rate-limited; no host paths).**

1. **Decisive SDK line**, at the two places a content entry's creation time is set:
   `[content] entry timestamp: path='mc4.sav' source=create|list creation=0x%016llx write=0x%016llx`.
   - `source=create`: in `HostPathEntry::CreateEntryInternal`, after `GetInfo`.
   - `source=list`: in `HostPathDevice::PopulateEntry`/`Initialize` for `\Device\Content\` mounts.
   - Expected on the Deck: save 1's `create` value differs from save 2's `list` value. Expected on
     Windows: they are equal.
2. **What the game compares:** in `NtQueryInformationFile` class 34 (and class 4,
   FileBasicInformation) on content files:
   `[content] query times: path='mc4.sav' class=34 creation=0x... write=0x...`.
3. **Optional, game-side and fully decisive:** an MCLA host hook at guest `0x82617228` (compare) and
   `0x82617AE0` (record):
   - `MCLA save verify: file='mc4.sav' stored=0x... current=0x... match=0|1|no-entry`;
   - `MCLA save record: file='mc4.sav' creation=0x...`;
   - plus a line when the save manager posts `[+176]` / enters UI state 24.
4. **For completeness (cheap):**
   - successful `XamContentCreateEx`: `flags=0x.. disposition=N result=0`;
   - successful `XamContentClose`: `root`;
   - `XamShowDeviceSelectorUI`: called, result, device id;
   - successful `XamContentGetDeviceState/Data`: `device_id`, and free bytes for Data;
   - `BroadcastNotification` promoted to INFO for id 0xB only, which should never appear.

   These rule out the residual candidates in the same run.

**Fix options (for the primary to choose).**

- **(a) SDK, general; no behaviour change on Windows.** Keep a process-wide registry
  `host path -> creation time` for files the SDK creates (`CreateEntryInternal`, including
  OVERWRITE recreate). When it builds entries from `ListFiles`/`GetInfo` and the path is in the
  registry, use the registered value. This gives NTFS-like stable creation times within a process.
  Across restarts both the load and the verify read the host value, so they stay consistent. Gate it
  with a cvar for an A/B run.
- **(b) Game-specific host hook.** Force the `sub_82617228` result to "match", or skip the record.
  This disables a memory-unit-swap guard that has no meaning with one dummy HDD.

Either is low risk. The acceptance test is two (or three) consecutive saves in one Deck session with
no dialog, plus the PC CreationTime-touch repro turning negative.

## 5. Status of the ghost-handle hypothesis and the fix in progress

- The ghost-handle hypothesis predicted the `DeleteContent failed: stage=remove-package ...
  win32=145` / `Recover failed` / `XamContentCreateEx failed: stage=delete-existing` sequence on the
  2nd save. **None of it appeared.**
  - Under the new reading, the 2nd save never reached `XamContentCreateEx(CREATE_ALWAYS)`: the
    verify failed first, and the owner then chose to continue without saving.
  - F10 #2 at the dialog saw no `.rex*` entries and transaction indicator 0.
  - The after-snapshot is clean.
  - The hypothesis is **effectively dead** as the KI-068 cause.
- **"Close host handles on unmount"** is harmless hygiene: it matches console semantics and may
  still be worth keeping. But it does **not** touch creation timestamps and should not be expected
  to fix KI-068 or be claimed as its fix. If it ships in l71, ship it together with the timestamp
  instrumentation above, and preferably with fix (a) or (b) behind a toggle. The owner's l71 run can
  then settle the cause and the fix in one pass.
- **Cheap extra check from existing data:** if the owner can send the two F10 packages
  (`live-20261106T095241Z-492-1` and `-2`, under the profile's `diagnostics/<session>/live`), compare
  the `mc4.sav` hash in each. Package 2 should equal package 1 and the after-snapshot (C862E9E7...)
  if save 2 never wrote. Also, `save-metadata.json` in each package may record file timestamps.

The Wine detail (what `ftCreationTime` is on ext4 under Proton) is from memory, not checked against
Wine source. Instrumentation line 1 settles it directly.
