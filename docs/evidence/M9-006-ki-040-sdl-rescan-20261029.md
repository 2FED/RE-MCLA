## (a) Exact hot-remove / hot-add code path

Threads: the UI thread runs `SDL_WaitEvent` (`windowed_app_context_sdl.cpp:67-77`). That pumps SDL events, which calls `SDL_UpdateJoysticks` (`SDL_events.c:1482-1483`, polling interval `:1562-1570`). Guest polls also queue a `SDL_PumpEvents` onto the UI thread (`sdl_input_driver.cpp:1530-1540`). The SDL Windows backend starts its own `SDL_joystick` thread with a message-only window (`SDL_windowsjoystick.c:347-351`, `221-265`). `SDL_HINT_JOYSTICK_THREAD` defaults to true.

1. **OS notification.**
   - The `SDL_joystick` thread's window registers for `GUID_DEVINTERFACE_HID` interface arrival and removal only (`SDL_windowsjoystick.c:150-191`, GUID at `:62`). On `DBT_DEVICEARRIVAL`/`REMOVECOMPLETE` it arms 300 ms and 2 s timers, which call `SetWindowsDeviceChanged()` (`:96-117`).
   - In parallel, `WIN_InitDeviceNotification` (`core/windows/SDL_hid.c:205-245`) stamps `s_LastDeviceNotification` from `CM_Register_Notification`, again for the HID interface class only.
2. **Rescan gate.** `SDL_UpdateJoysticks` calls every driver's `Detect()` after the per-joystick updates (`SDL_joystick.c:2818-2820`). `WINDOWS_JoystickDetect` returns immediately unless `WindowsDeviceChanged()` is true (`SDL_windowsjoystick.c:388-396`, `:67-75`). When it rescans, DirectInput enumerates first and then XInput, via `XInputGetCapabilities` on users 0-3 (`:406-410`, `SDL_xinputjoystick.c:214-230`). Entries that are gone produce `SDL_PrivateJoystickRemoved`, and new entries get a new instance ID and `SDL_PrivateJoystickAdded` (`SDL_windowsjoystick.c:415-450`, `:296-302`).
3. **The XInput polling fallback is dead code in normal operation.** The 1 s `XInputGetCapabilities` poll (`SDL_windowsjoystick.c:240-256`) runs only when `SDL_WaitForDeviceNotification` returns false. That happens only when there is no message window or `GetMessage` fails (`:193-212`).
4. **Stale XInput joystick behaviour.** `SDL_XINPUT_JoystickUpdate` silently returns when `XInputGetState` reports `ERROR_DEVICE_NOT_CONNECTED` (`SDL_xinputjoystick.c:389-392`). It sends no removal, and the last state stays frozen.
5. **DirectInput hides XInput-class pads.** DirectInput skips any device whose path contains `IG_` or whose VID/PID maps to Xbox 360/One, while XInput or RawInput is enabled (`SDL_dinputjoystick.c:236-265`, `:504`).
   - In this SDL version RawInput is off by default (`SDL_rawinputjoystick.c:1025`), WGI is off (`SDL_windows_gaming_input.c:589`), and GameInput is off on desktop (`SDL_gameinputjoystick.cpp:30-35`, `:325`). XInput is on (`SDL_xinputjoystick.c:49`).
   - An XInput pad that Windows cannot give one of the four XInput user indices is therefore **invisible to SDL**. Windows also has no fifth XInput index.
6. **Event delivery to the SDK.**
   - SDL pushes `JOYSTICK_ADDED`/`GAMEPAD_ADDED`. Event watchers run before queueing (`SDL_events.c:1802-1811`).
   - The driver's watch, registered at `sdl_input_driver.cpp:203-223` for the 0x600-0x6FF range, only buffers into `pending_events_` (`HandleEvent`, `:802-820`).
   - Buffered events are processed on the **guest thread**, inside `DrainAndLock` (`:822-833`), during the next `GetState`, `GetCapabilities`, `SetState` or `GetKeystroke` (`:320-396`, `:650-800`). The dispatch is `ProcessEventLocked` (`:835-869`).
7. **Remove.** `OnControllerDeviceRemovedLocked` (`:997-1018`) runs on both `JOYSTICK_REMOVED` and `GAMEPAD_REMOVED`. The second event is ignored at debug level.
   - It finds the slot by instance ID (`:1258-1271`), closes the device, and calls `CloseController` (`:1340-1366`). That zeroes the slot state, so the slot is freed.
   - If the removed slot was active, it resets `active_controller_index_` and calls `SelectFallbackControllerLocked` (`:1443-1459`). With no other pad, that resets `slot_zero_state_source_` and logs `physical_slot=none`.
8. **Add.** `OnControllerDeviceAddedLocked` (`:937-995`):
   - `SDL_OpenGamepad(new id)`.
   - `ChooseControllerSlot` (`slot_mapping.h:20-37`) returns 0 for an empty mask.
   - `state = {}`, `state_changed = true`, then `SelectActiveControllerLocked(0, "first-connected")` (`:1400-1427`).
9. **Guest read path.**
   - `XamInputGetState` (`xam_input.cpp:97-122`, user 0xFF goes to 0) calls `InputSystem::GetState` (`input_system.cpp:86-160`). That bumps the merged packet number on `!was_connected`.
   - `SDLInputDriver::GetState(0)` (`:345-396`) resolves logical 0 to the active physical slot (`ResolveLogicalControllerSlot`, `slot_mapping.h:43-59`). It bumps `slot_zero_state_.packet_number` on `source_changed`.
   - Button and axis events for the new instance ID resolve through `GetControllerIndexFromInstanceID` (`:1172-1256`, `:1020-1074`).

**Verified conclusion for open question 1:** after a hot re-add with a new SDL instance ID, the SDK re-routes guest user 0 to the new device. The physical slot is freed on remove and re-selected on add, and both packet counters advance. I found no host-side mapping bug on this path. The l33 log matches this exactly: removed, `physical_slot=none`, re-added at index 0, `first-connected`.

**Verified conclusion for open question 2:**
- A device that Windows cannot place at XInput user index 0-3 is not visible to SDL with the current defaults. XInput cannot report it, and DirectInput deliberately skips XInput-class devices.
- Separately, SDL re-scans XInput **only** after a HID device-interface notification, plus timers 300 ms and 2 s after it. An XInput connect, disconnect or index change that happens without such a notification, or more than 2 s after the last one, is never detected while the game runs.

## (b) Ranked root causes

1. **SDL missed the XInput change. Most likely for "no SDL event on the manual reconnect".**
   - *Verified in source:* points 1-3 above. Detection depends on HID-class PnP notifications, the 300 ms/2 s retries are the only retries, and XInput polling is disabled whenever notifications work.
   - *Hypothesis:* the 8BitDo 2.4 GHz dongle stays USB-enumerated while the pad re-pairs, so no HID interface arrival fires. Or the pad finishes pairing and gets its XInput index more than 2 s after the dongle's notification. Either way SDL never calls `XInputGetCapabilities` again, so no add event is possible. This matches the KI-040 note that the manual reconnect produced no SDL event at all.
2. **Stale XInput joystick after a re-add. Plausible for "re-added at index 0 but input dead".**
   - *Verified:* the SDL XInput backend keeps an open joystick whose user index returns `ERROR_DEVICE_NOT_CONNECTED`, with no removal and frozen or neutral state (point 4). The SDK keeps treating the slot as connected, so guest user 0 reads a dead or neutral pad, and `GetState` still returns `SUCCESS`.
   - *Hypothesis:* the automatic re-add enumerated XInput #1 at T+0.3 s or T+2 s, during the dongle's reconnect. The link then flapped again, or the pad settled at a different XInput user index, with no further HID notification. SDL then kept the stale userid 0 joystick.
   - The l33 session shows repeated drops (14:02:48, 14:03:22), and nothing was re-added after the last drop for 95 s. That fits a link that flaps faster than notifications arrive.
3. **The pad returned outside XInput 0-3, or as a non-standard device ("slot 7").**
   - *Verified:* such a device is invisible to SDL with the current defaults (point 5).
   - *Hypothesis:* "slot 7" is most likely a DirectInput, WinMM or Windows device-list position rather than an XInput index. XInput has only four indices. Possible reasons for an XInput-class pad to be unreachable:
     - Other real or virtual XInput pads (Steam Input, ViGEm/DS4Windows, vJoy-XInput) hold indices 0-3.
     - XInput has not released the old index yet.
     - The 8BitDo re-paired in a different mode (D-input or Switch PID).
   - In the third case DirectInput or HIDAPI would see it, but only after a rescan, so cause 1 also applies.
4. **Guest-side reaction to the disconnect. Lower likelihood, not excluded.**
   - *Verified:* the SDK never broadcasts an input-device-changed XNotification. The only notifications are 0x9 and 0xA (`xam_ui.cpp`, `xam_user.cpp:989-992`). There is no `XN_SYS_INPUTDEVICESCHANGED` (0x12).
   - *Hypothesis:* if MCLA's "controller disconnected" pause relies on that notification, or waits for START from a re-signed port, the re-added pad would be read but ignored.
   - The l33 log has no `SDL_ACTIVE_CONTROLLER ... reason=button-down` after the re-add, but that line is only logged when the active slot changes, so it proves nothing either way. The F10 controller-matrix/input-slot audit after a drop can settle this.
5. **Load or timing interaction from the unlocked builds. Unlikely.** The SDL detection runs on the UI and SDL joystick threads, independent of guest vblank. Event draining only needs the guest to poll. I found no code path that stops pumping during menus or pause. The `is_active` callback (`rex_app.cpp:257-261`) only masks state while an ImGui overlay captures the mouse, and the UI loop keeps pumping regardless.

## (c) Minimal fix proposal (see `ki-040-proposal.diff`)

1. **Vendored SDL (`SDL_windowsjoystick.c`).** Add `WINDOWS_PollXInputHotplug()`, called at the top of `WINDOWS_JoystickDetect`.
   - At most once per second it reads `XInputGetCapabilities` for users 0-3 and compares the connected mask with the cached one.
   - On any change it calls `SetWindowsDeviceChanged()`, which runs the normal full DirectInput+XInput rescan. That emits a removal for the stale userid joystick and an add, with a new instance ID, at the real userid.
   - This restores what SDL2 and SDL3's notification-less path already do, without changing device ownership. Cost: four `XInputGetCapabilities` calls per second on the thread that pumps SDL, already under the joystick lock.
   - Review note: also reset `s_xinputConnectedMaskValid` in `WINDOWS_JoystickQuit` if the subsystem can be re-initialised.
2. **SDK driver, opt-in.** Add a `hid_sdl_rawinput` cvar, default off, that sets `SDL_HINT_JOYSTICK_RAWINPUT=1` before `SDL_InitSubSystem(SDL_INIT_GAMEPAD)`. This is an escape hatch for volunteers whose pad cannot get an XInput index (cause 3). It is not a default.
3. **SDK driver, diagnostics.** Extend the `OnControllerDeviceAdded` log with the instance ID and `SDL_GetGamepadPath` (for example `XInput#0`), so the next owner log shows the backend, user index and instance ID directly.

The host-side slot re-binding by instance ID is already correct (point 8), so no change is proposed there. If cause 4 is confirmed later, the follow-up is to broadcast `XN_SYS_INPUTDEVICESCHANGED` (0x12) from the driver on connect and disconnect. That needs a kernel-state hook and is outside this minimal diff.

## (d) Test approach

- **Unit, no hardware:**
  - The slot logic is already covered by `tests/unit/input/sdl_slot_mapping_test.cpp`. Add a remove/re-add sequence: `ChooseControllerSlot(..., 0) == 0` after a remove, `ResolveLogicalControllerSlot(0, 0, 0x1) == 0`, and a fallback to none on an empty mask.
  - **SDL virtual joystick fixture:** use `SDL_AttachVirtualJoystick` (SDL3 `SDL_VirtualJoystickDesc`, type `SDL_JOYSTICK_TYPE_GAMEPAD`, VID 0x045E, PID 0x028E). Attach, detach, then re-attach to get a new instance ID. Then `SDL_SetJoystickVirtualButton` plus `SDL_UpdateJoysticks`, and assert that `SDLInputDriver::GetState(0)` returns `SUCCESS` with `A` set and an advanced packet number. Also assert that `GetState(0)` returns `DEVICE_NOT_CONNECTED` between the detach and the re-attach.
  - This needs a small seam, because `QueueControllerUpdate` dereferences `attached_window_->app_context()` (`:1530-1540`) and initialisation happens in `OnWindowAvailable`. A test-only constructor or init path that skips the window would cover this. It proves the SDK re-bind path, not the Windows XInput detection.
- **The SDL patch** cannot be exercised by virtual joysticks, which bypass the Windows backend. Options:
  - (i) A tiny standalone SDL test program (not the game) that logs `SDL_EVENT_GAMEPAD_ADDED/REMOVED` with the path while the owner toggles the pad, run before and after the patch.
  - (ii) ViGEmBus, if it is already installed: plug and unplug a virtual X360 target. That covers the PnP path only, not the "no notification" path.
- **Manual owner repro**, non-destructive, no saves touched:
  1. Close other controller tools (Steam Big Picture, DS4Windows), keep only the 8BitDo dongle plugged, and start the patched build.
  2. In a menu, switch the pad off for 10 s, then on. Expect within about 1 s in the log: `removed from physical slot 0`, then `Added at index N ... Path("XInput#M")`, then input works. Press F10.
  3. Repeat with the pad left off for 30 s, which is past the 2 s retry window.
  4. Unplug the dongle for 5 s, then plug it back in. Expect the same add/remove pattern.
  5. Optional: at the same time, run this read-only PowerShell XInput monitor to correlate Windows XInput indices with the SDL log:
     ```powershell
     Add-Type -Namespace X -Name I -MemberDefinition '[DllImport("xinput1_4.dll")] public static extern int XInputGetCapabilities(int u,int f,byte[] c);'
     while ($true) { $m = 0..3 | % { if ([X.I]::XInputGetCapabilities($_,1,(New-Object byte[] 20)) -eq 0) { $_ } }
       "{0:HH:mm:ss.fff} xinput users: {1}" -f (Get-Date), ($m -join ',') ; Start-Sleep -Milliseconds 500 }
     ```
     If the monitor shows a user index appear or change while the unpatched build logs nothing, that confirms cause 1 or 2. If the monitor shows no index at all, that is cause 3, so retry with `--hid_sdl_rawinput=true`.

## (e) Risks

- **Device churn.** A forced rescan re-enumerates DirectInput too, but SDL matches existing entries, so unchanged wheels and pads are not removed and re-added. The rescan only runs when the XInput mask changes. The T300 wheel stays on the DirectInput/raw-joystick path. XInput vibration is untouched, because it uses the same XInput userid after the rescan.
- **Cost.** `XInputGetCapabilities` on empty user slots is relatively slow, though below a millisecond in typical reports. Four calls per second on the UI pump thread is negligible, but it runs inside `SDL_LockJoysticks`.
- **Rescan feedback loop.** A flapping link would now produce real remove/add pairs, about one per second at most. The SDK handles these correctly: it stops rumble, re-selects slot 0 and resets keystroke states. Wheel force-feedback effects are recreated by the guest.
- **RawInput opt-in.** Pads may appear twice if correlation fails, triggers may merge into one axis without XInput/WGI correlation, rumble may go missing for uncorrelated devices, and names change. The T300 is not XInput, so DirectInput still owns it, but `IsSupportedWheel` should be re-checked with RawInput on. Keep it default off and label it experimental for volunteers.
- **Upstream divergence.** This patches vendored SDL in the SDK fork. Record it in the SDK patch list, and consider reporting it upstream after the owner confirms the fix (read-only duplicate search first, per AGENTS.md).
- **Not proven.** None of the causes is physically confirmed for the owner's session, and that session's log was not available. Cause 4 (the guest ignoring a re-added pad) remains open until an F10 audit after a drop shows guest `GetState` returning `SUCCESS` with live buttons.
