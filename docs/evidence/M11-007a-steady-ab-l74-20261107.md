### What the keys are

- `05368000` chain = **the player-car livery composite** (KI-047 family, PC counterpart of the Deck's `050A0000`):
  the same base also carries a 1024x1024 fmt 6 key (`len=4194304`, draws 3-5) with an 8-key mip chain up to
  `054BF000` (`kind=overlap ... overlapping_keys=8`, rules `ac`), mips laid out back to back (512 at +0, 256 at
  +1 MB, 128 at +1.25 MB, 64 at +1.31 MB), resolved only in the pre-race showcase (base and steady frames
  ~817-1516), never during the race; one GPU `tex_load` of the 512 level (mip_max 7). In base it is forced every
  time (rule c, plus a/b on the 1024 overlap and after gaps); in base 1 its 512 level ran at least frames
  1438-1516 consecutively, so it would also have been exempt there. This breaks the design assumption ("livery keys
  run at most 3 consecutive frames", Deck): on the PC the showcase composites the livery every frame for 30-80+
  frames. It is a CPU-read composite (the atlas builder) and must never be exempt. No livery defect was seen,
  most likely because only one stale resolve per key slipped through and the later forced resolves overwrote it.
- `039CA000` 256x256 = the per-frame start-of-frame resolve (draw 26 in menus, 34 in the race; Deck `03702000`).
  The GPU samples it in the same frame from the GPU-written shared memory (`tex_load base=039CA000 ...
  scaled_resolve=1 rb_copied=1`, `tex_inval by_gpu=1 frames_since_load=1` every frame in both arms); the texture
  cache counters per frame are identical between arms (tex_reloads_without_inval ~3.0/frame, invals 100 % by GPU).
  So the exemption does not change what the GPU samples; it only changes the guest-RAM copy, which under `some`
  is now refreshed every 4th resolve from the previous slot (tex_load lines show `rb_copy_frames_ago` 0-3 in steady
  vs 0 in base). The only way the exemption can change the picture is therefore a **guest CPU reader of
  `039CA000`** (not excluded: no read detection in the SDK).
- Base: rules a/b never matched `039CA000` (all 1,955 / 1,760 sampled composite lines are `sync_rules=c`,
  since_prev=1) and set-B matched_a = 0, matched_b 61-165 (other sporadic keys) in both arms; forced_c dropped
  6,419/4,093 -> 23/68, forced_b unchanged per frame (0.03 / 0.017 base vs 0.025 / 0.024 steady).

## 5. Attribution and rule recommendation

- The livery chain exemption is a real KI-047 exposure (must be closed) but **cannot explain the second-half
  flicker**: it was exempt for one resolve before the race start and never again.
- During the race the arms differ by exactly one thing: `039CA000` not forced (plus +16 % fps). So either (a)
  `039CA000` has a guest CPU reader that reacts to 1-4-frame-stale content (texture streaming / visibility /
  LOD feedback would fit "buildings, billboards and road signs"; KI-038's billboard/sign placeholder reports all
  predate the l55 composite sync that started forcing this key), or (b) a game-side effect of the higher frame
  rate (KI-041-like). 2 of 2 steady runs vs 0 of 2 base runs favours (a) but does not prove it.
- Consequence: **no narrowing rule removes the flicker if (a) holds**, because every option keeps `039CA000`
  exempt (it is the whole gain). Options, with the share of the ~6 ms kept:

| option | chain (livery) excluded? | `039CA000` kept | gain kept | note |
|---|---|---|---|---|
| sticky exclusion (ever a/b -> never again) | no: the first exemption (frame 1433) precedes the first rule-b hit (1446) | yes | ~100 % | only blocks later re-entries |
| shape filter (no adjacent half/double-size rule-c key: next level at base+len with w/2, or previous level ending at base with 2w, live in the last few frames; or any rule-a overlap ever) | yes (512->256->128->64 contiguous, 1024 overlap) | yes (`039BA000` 128x128 ends at `039CA000` but is half size below, not a chain level; define the check by level layout, not by mere adjacency) | ~100 % | general, no constants |
| allowlist 256x256 fmt 6 src_base 0 | **no**: the chain's `05468000` level is also 256x256 fmt 6 src_base 0 | yes | ~100 % | unsafe alone |
| GPU-consumption proof (`tex_load` of the exact range this frame) | **no**: the livery 512 level is also GPU-loaded (mip_max 7) | yes | ~100 % | the signal exists only in the livery diag (budgeted lines; `tex_loads_rb_overlap` counter), and it does not separate CPU readers |
| combination: rule c alone, run >= 30, never a/b this session (sticky), no chain neighbour/overlap (shape), plus a single-key cap (more than one exempt key in a frame -> exempt none) | yes | yes | ~100 % (-5-10 ms per session for the chain) | recommended rule |

- **Recommended rule (M11-007b)**: the combination above. It keeps the full ~6 ms (the chain contributes only ~4
  forced waits per session) and closes the livery exposure.
- **Before any volunteer default, settle the flicker** (owner, PC, same race, F10 at the flicker):
  1. steady arm with an added per-key "fast" delivery for exempt keys (copy the previous slot on every exempt
     resolve, i.e. guest RAM at most one frame old instead of 1-4 frames; cost ~256 KB memcpy per frame, keeps
     ~all of the gain). Flicker gone -> the 4-frame `some` cadence was the cause; ship exemption + fast delivery.
  2. If it still flickers: the CPU reader needs same-frame data -> `039CA000` cannot be exempted without the
     M11-007 step-2 read trap; keep forcing it (base behaviour) and close M11-007a as not shippable.
  3. Control for the frame-rate explanation: base arm with a frame cap is not available, so instead repeat one base
     and one steady run blind (owner does not know the arm) and record flicker yes/no; a flicker in base, or none in
     steady, points to (b).
- Deck: not affected by this decision yet; the same chain risk exists there if the Deck showcase also composites
  for 30+ frames.
