# KI-046 performance regression analysis (read-only, 2026-10-29)

Read-only analysis by an Opus subagent on 2026-10-29 (owner session logs, launcher source, build caches), reviewed and accepted as evidence by the primary agent. Conclusion is a ranked hypothesis, not a closure; the owner A/B below decides.

Scope: l41 owner candidate (host `dd7cca7`, l41 SDK = a239b83 + 259d0b2, 9ad1c11,
d968f59, 8b10d62) against the old daily builds l31-s30 / l33-sunc. Sources:
launch receipts, capability gates, CMake caches, SDK diff, and the per-minute
counters plus `REX_PERF_AUDIT_SAMPLE` windows in the owner's managed session
logs. No saves were opened, nothing was built or launched. Profile and session
ids are shortened.

## Verdict

No code or build regression found. In every comparable session the GPU is
saturated: `gpu busy/min` is 56-60 s out of 60 s. Per pixel, the l41 frame
cost matches the l34-sunc frame cost; l34-sunc has the same source as l33-sunc.
The 2160p baseline the owner remembers has no recorded session behind it. The
launcher refused 2160p for l31-s30 and l33-sunc, and the only earlier 2160p
session on record, l7 on 2026-10-11, ran at 16-21 fps, the same as l41. One
real effect is new to look at, but it is not new in the code: at 2160p the
GPU goes over its DXGI video-memory budget.

`mcla.exe`, and carry no arguments (WScript.Shell resolution). Every old and
new launch goes through a launcher that builds the command line itself:

- "MCLA Launcher": the l12 launcher.
- The l31/l33 shortcuts: the Build folder that gets pasted into Setup.

The startup logs confirm identical runtime state in l34-sunc (1440p) and l41

- `video-memory budget 7131 MB; texture cache limits 3565/5595 MB`;
- `light render-to-texture CPU readback`;
- `invalidation widening 64 pages`;
- `raw measured time`;
- `presentation tearing disabled`;

- the same UI-cap on/off behaviour.

The exact l33-sunc 1440p session logged `fast` instead of `light` readback.
That is only the log string; M9-001 recorded the rename.

## 3. New per-frame code since l33, ranked by plausible cost

The ranking is moot while the GPU, not the CPU, is the limit.

1. **SDK `d3d12_async_pipeline_wait` (8b10d62).** Per draw it adds one
   `REXCVAR_GET` and a `PendingWaitEpisode::Observe` call. The wait itself runs
   only while the KI-037 photo window is open: 2 windows in the 4K session,
   2.7 s and 4.3 s. Cost: negligible, the same class as the existing
   `REXCVAR_GET(async_shader_compilation)` per draw. No extra GPU work.
2. **M9-007 `sub_822D29E8` (menu state).** Two `cvar::Query` by-name lookups
   per call, and `SetFlagByName` only on transitions (5 + 4 log lines in the
   4K session). Cost: microseconds per frame.
3. **KI-037 `sub_8263EAA8` / `sub_8263D120` / `sub_8263D1E0`.** Window state
   machine; cvar set only on open and close. Negligible.
4. **KI-026 `sub_82130000` (about 2,100 call sites) and the edge hooks.**
   `ProbeOn()` is a function-local `static const bool`: one guard load and
   then a branch. With the probe off there is no lock and no formatting.
   Negligible.
5. **SDL event observer / KI-040 XInput hotplug poll.** These run on the event
   pump. The frame-pacing tails show no periodic hitch. At 720p on l41:
   `>100ms` 0-1 per minute, p99 34-52 ms, which matches l36 (old SDK). A
   once-per-second stall would add about 60 `>50ms` frames per minute; it is
   absent.
6. **F10 guest-output readback (KI-042) and the per-minute export parser.**
   They run only on F10.

The SDK graphics diff a239b83..8b10d62 touches only the pipeline wait. No
render-target, resolve, texture-cache or memory code changed. The host
texture-budget code is unchanged since M8-001 (`31a40db`).

`REX_PERF_AUDIT` windows, 300 frames each:

- l41 2160p: 15.7 / 18.0 / 16.1 fps, GPU p50 about 60-62 ms, CPU p50 14-31 ms.
- l41 1440p: 34.7 / 30.2 fps, GPU p50 27-31 ms.
- l17 1440p (10-25): 29.9 fps stock, GPU p50 33 ms.

Findings:

- **GPU-side, flat, not CPU-side.** At 1440p and 2160p the GPU is busy
  56-60 s per minute in both old and new builds. The CPU audit time is below
  the GPU time.
- **Same GPU cost per pixel.** About 7.2 ms per megapixel at 1440p (26.4 ms,
  3.69 MP) against 7.5 ms per megapixel at 2160p (62 ms, 8.29 MP) on l41.
  l34-sunc at 1440p is 25-27 ms at fewer draws. Going over budget at 4K adds
  at most a few percent.
- **No periodic hitch pattern.**
- **2160p baseline.** l31-s30 (`901B27FA`), l33-sunc (`738BD662`) and
  l34/l35-sunc (`291487F6`) have **no 2160p session** in any managed profile.
  The l12 launcher refused 2160p for every build except `9C6BEA71` and
  `FED35A36`: the `UntestedTargetBuild` gate, present since M8-003 and still in
  `0bae39e`. KI-045 lifted that gate for the owner on l41. So "30+ at 2160p on
  l31/l33" cannot come from those builds through the launcher. The only
  earlier 2160p data, l7, is 16-21 fps, the same as l41.
- **1440p baseline.** The best recorded l33-source minute at 1440p is
  40.1 fps, GPU-saturated. "40-60 at 1440p" is not in any log. The 55-70 fps
  in the README driving note was measured at 720p, where l41 also reaches
  61 fps.
- **VRAM at 2160p (coordinator point a/b).** Eight "near budget" lines. The
  texture cache hard limit falls from 5595 to 3565 MB, and the process holds
  7.1-7.8 GB against a 6.7 GB DXGI budget on the 8 GB laptop GPU. 720p and
  1440p sessions on 10-29 stay at 1.8-4.3 GB with no pressure.
  - No old 2160p log exists with the budget code, so nothing to compare.
  - Nothing in l39-l41 adds VRAM. The SDK graphics diff has no
    allocation-related change; Tracy and the image-capture tests also exist in,
    or do not reach, the old builds.
  - The scale-3 scaled-resolve and render-target footprint (KI-038 analysis)
    is the same in the a239b83 source that l31/l33 ran.
  - Over-budget residency is a 4K problem and likely costs a few percent plus
    the `>100ms` spikes (15-28 per minute at 2160p against 0-4 at 1440p). It
    does not explain a 1440p difference, and the 1440p counters show no
    difference.

## 5. Ranked causes

1. **About 75%: no regression; baseline mismatch.** The comparison is against
   2160p numbers that were never measured on l31/l33, and against 1440p
   figures above any logged minute. The GPU is the limit in both, with the same
   per-pixel cost. The scene matters too: l41's 1440p minute had a 7.0 k draw
   p50 against 4.6-5.4 k in l34-sunc's driving minutes.
2. **About 15%: 2160p VRAM over-budget on the 8 GB GPU.** Real and worth its
   own item. It affects only 2160p and probably all builds that can render
   scale 3; it is not caused by l39-l41 code. It may deepen the 4K drop by a
   few percent and adds `>100ms` hitches.
3. **About 7%: scene or route difference** (hangout or downtown at 6-7 k draws
   against lighter routes remembered at 40+).
4. **Under 3%: a code or build effect in l41.** No mechanism found: identical
   build flags, identical command line apart from the vblank argument, and
   per-frame hooks that cost microseconds while the GPU is the limit.

## 6. Decisive A/B for the owner

Use the same save, the same route (the same downtown drive for 3 or more
minutes, no pause menus), Unlocked, vsync on, and 1440p first.

- **A:** the l41 launcher with Build folder `private\l41-internal\build`
  (Unlocked).
- **B:** the l41 launcher with Build folder `private\l33-sunc\build` (exact
  l33-sunc). Add `738BD6622754A9650A5675C8262127D47ABC632B9C604B5F1C02F4B421AD9C4E l33-sunc`
  to `owner-admitted-builds.txt`, so that Unlocked and 2160p are admitted.
  - The launcher then passes `--mcla_guest_vblank_hz=240`, which is l33's own
    built-in default.
  - Alternatively, use the l12 launcher for 1440p only.

Then repeat both at 2160p. Compare in each session log:

- `frame pacing/min` fps;
- `gpu busy/min` ms per frame;
- `draws per frame/min` p50;
- `video memory ... near budget` lines;
- the `texture cache hard limit`.

If B is within about 10% of A at matched draw counts, KI-046 is closed as
"no regression; GPU-bound". The 2160p VRAM pressure then becomes a separate S2
item; if B shows the same budget lines, it is pre-existing. Only a gap of more
than 10% at matched draws reopens the code search. In that case, a third run
of the l41 `build` with the l34 SDK DLLs would split SDK from host, but that
needs a rebuild against the matching headers and is not a launch-only test.

## 7. Fix

None is clear: no code cause was found, so no proposal diff is included. If
the 2160p budget item is pursued, it starts with measurement: log the
render-target, scaled-resolve and shared-memory allocations at scale 3, then
decide.
