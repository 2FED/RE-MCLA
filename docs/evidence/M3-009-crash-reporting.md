# M3-009 privacy-safe crash reporting

Date: 2026-08-11

Status: accepted for C++ guest exceptions

## Scope and boundary

M3-009 adds actionable metadata when a generated guest-code C++ exception
unwinds through a guest `XThread`. It does not claim generic recovery from
Windows SEH, POSIX signals, `REX_FATAL` aborts, or arbitrary native crashes.
The reported guest PC is the last instrumented function entry, basic-block
boundary, or exact `REX_UNIMPLEMENTED` site; it is not instruction-exact for
all native faults.

The report is metadata-only by default. It does not read or serialize guest
memory, guest registers, or the guest stack.

## SDK implementation

The reviewed ReXGlue fork state is:

- tag: `v0.9.0.7`
- commit: `efac376998cbb0520295d308be4703574a12a995`
- upstream report: [rexglue/rexglue-sdk#409](https://github.com/rexglue/rexglue-sdk/issues/409)

The SDK now:

- stores the last tracked guest PC, current PPC function, and static last-import
  name in `PPCContext`;
- creates an exception-aware function scope in generated prologues, restores
  caller breadcrumbs after normal returns, and retains the deepest scope while
  an exception unwinds;
- updates guest PC at generated branch labels and immediately before an
  unimplemented-instruction exception;
- records typed hooks, raw hooks, and all generic stub forms;
- catches `std::exception` and unknown C++ exceptions around guest `Execute()`
  in `XThread`;
- captures at most 16 host frames and formats only module filename,
  module-relative offset, and address;
- emits `guest_memory_included=false` explicitly.

Legacy `REX_FUNC_PROLOGUE()` call sites remain source-compatible through a
variadic generated macro; new codegen passes the function address.

## Report contract

Schema 1 requires exactly one of each reviewed field:

```text
REX_GUEST_CRASH schema=1
reason=<sanitized bounded reason>
guest_pc=0x........
ppc_function=sub_........
thread_id=0x........
last_import=<sanitized static name or none>
host_stack_count=<1..16>
host_stack[N]=<module>+0x<offset> (0x<address>)
guest_memory_included=false
```

Control characters in text fields become `?`, fields are bounded to 160 bytes,
and the project verifier caps the complete report at 16 KiB. It rejects absolute
Windows paths, user/private path fragments, guest stack or memory-dump labels,
register collections, and an enabled guest-memory flag.

## Upstream duplicate audit

Before filing #409, all open and closed issues and pull requests were searched
for `crash report`, `guest crash`, `unhandled exception`, `guest PC`, `guest_pc`,
`last import`, and `last_import`. Candidate issues #404, #381, #75, and #290
describe a bad thread memory base, ARM FP traps, missing PPC instructions, and
logging initialization respectively; none covers the missing structured
`XThread` C++ exception boundary.

## Re-evaluation and remaining risk

M3-009's acceptance criterion is satisfied: the synthetic report contains every
required context field and excludes proprietary guest memory by default.

A separate repeated-exit risk remains for M3-015. On the first probe immediately
after two large relinks, the complete report and shutdown marker were written in
about one second, but the Windows process handle was not signaled within the
20-second bound (one earlier pre-tag attempt also exceeded 60 seconds). Three
immediate subsequent tagged runs exited cleanly. This cold post-relink behavior
does not invalidate the report pipeline, but it prevents claiming repeated
launch/exit stability until M3-015 reproduces and classifies it.
