# KI-056 fix A: restore the pending new photo after an occupied hover (l72 host patch)

Implementation by an Opus subagent on 2026-11-06, for review by the primary agent. Design:
[l71 album probe analysis, section 3](M11-ki056-l71-album-probe-20261106.md). Base: main
`3895d27`. Nothing was launched; no physical result exists yet.

## Change

KI-056 (album "Choose a slot" preview shows the wrong photo) is game-side: the hover path
`sub_8263C9C8` decodes an OCCUPIED slot's JPEG into the one shared preview image (`+1140` over
`+1144`, texture `+1132`, material `+1136`) and decodes nothing for an EMPTY slot, so the
highlighted empty cell keeps the last hovered saved photo. Only the thumbnail-load path
`sub_8263E1E8` re-runs the new-photo decode `sub_8263C8B0` (gated by `+1170`).

Fix A, in the existing strong override `REX_EXTERN(sub_8263C9C8)` (`src/mcla_album_probe.cpp`),
after `__imp__sub_8263C9C8` returns, active whenever `mcla_album_preview_restore` is on (with
the album probe on or off):

- Conditions, all required (`album::DecideRestore`, pure, `src/mcla_album_probe.h`):
  1. the cvar is on;
  2. the album fields were read through the checked reader (`mcla::guest::HookReader`);
  3. `u8(album+1170) != 0`: a new photo is pending (the save chooser). The game's own gate
     (`sub_8263E1E8`: `lbz r11,1170(r31)` then `bl 0x8263c8b0`); cleared after the save by
     `sub_8263E4F0` (`bl 0x8263dcf8`, `li r11,0`, `stb r11,1170(r31)`);
  4. the hovered slot is empty by the game's rule, `album::HoverValid` false: if `+1225 == 0`,
     bit `slot` of `+860` clear (as `slw` computes it: slot >= 32 is never valid), otherwise
     `slot >= +1208`. Evaluated on the fields read before the original call (the ones the
     original used);
  5. `NewPhotoTracker::clobbered()`: an occupied hover decoded over the shared image since the
     last new-photo decode that ran. Set by `OnHover(decoded=true)`; cleared by
     `OnNewPhoto(decoded=true)` (a skipped decode, bad marker, leaves it set) and by every
     `OnRestore()`;
  6. `*(+1148)` starts with `FF D8` (the check `sub_8263C8B0` itself makes).
- Action: `ctx.r3.u64 = album; sub_8263C8B0(ctx, base);` through the hooked symbol, with a
  thread-local `t_in_restore` so the new-photo override passes it through (a restore, not a
  snapshot). `r3` and `lr` are put back afterwards (the hover callers `sub_8263DFC0`,
  `sub_8263CDC0`, `sub_8263CE88` return without reading `r3`; unit-checked for the latter two
  against the generated code). The tracker counts `OnRestore()`.
- Bound: "while dirty". Each occupied-to-empty return restores once; a second empty hover
  without a new occupied hover does nothing (`clobbered` is clear). There is no
  once-per-snapshot latch (the old `PendingRedecode`/`OnRedecode` seam and the F10
  `fix_a_precondition` field are removed).
- With the probe off and the fix on, the new-photo override reads only `+1148` and its two
  marker bytes to feed `OnNewPhoto(decoded)`; the hover override reads only the scalar fields
  (`ReadAlbumFields`: no image, CRC or texture reads) and, on a restore, two 4 KiB CRCs.
- Log, rate-limited by its own `album::Pacer` (burst 20, then 1 per 500 ms, 1000 per session):
  `MCLA_ALBUM v=1 fn=restore album=.. lr=.. slot=.. pending1170=.. jpeg1148=.. marker=..
  crc_before=.. crc_after=.. restores=.. snapshot=.. suppressed=..`. `crc_after` should equal the
  last `fn=new_photo crc4k_after`.
- F10 `state.json` `album` block: `{"probe": false}` with both switches off (unchanged);
  with the fix on, `"preview_restore": {"enabled": true, "restores": N, "no_marker": N,
  "clobbered": bool, "last": {"slot", "crc4k_before", "crc4k_after", "age_ms"}}`
  (`album::RestoreJson`, pure); with the probe on, also the existing fields plus
  `tracker.clobbered`, `tracker.restores`, `calls.thumb_load` and `last_thumb_load`.

Probe additions (probe on only): the hover line logs `pending1170=` and `cursor1180=` (read after
the call) and `clobbered=`; F10 `live` and `last_hover` add `pending1170`/`cursor1180`. A new
pass-through override `REX_EXTERN(sub_8263E1E8)` logs
`MCLA_ALBUM v=1 fn=thumb_load album=.. lr=.. slot=.. pending1170=.. cursor1180=.. mask860=..
crc4k_before=.. crc4k_after=.. snapshot=.. suppressed=.. complete=..` (its own pacer), to name the
B3A0D6BA writer. With the probe off it only calls the original.

No host write to guest memory: every read goes through `mcla::guest::Reader`; the only guest
writes are the ones the game's own `sub_8263C8B0` makes.

## Risks

- `sub_8263C8B0` stores `5` to `*(*(0x8288B9AC) + 68)` (global of unknown meaning) before its
  marker check. The game makes the same call in the same chooser context from the same main
  XThread (thumbnail-load path, 44.962 on t36732 in the l71 session), so this is not a new
  kind of write, but it now happens once per occupied-to-empty transition.
- Cost: one 1280x720 JPEG decode (about 3.6 MB written) per occupied-to-empty transition, the
  same cost as the hover decodes the game already runs, plus two 4 KiB CRC reads.
- Threading: hovers and the restore run on the main XThread; the state-4 decode runs on another
  thread but its tick is idle (state 2/0) while the chooser is up. The tracker is under the
  probe mutex; the guest call is made with the mutex released.
- Event 4 is not fired: the big panel keeps the logo placeholder for an empty slot (the game's
  own choice). Only the highlighted cell changes.
- This is a quality fix, not console accuracy: the original console very likely shows the same
  clobbered preview. Hence default off, owner key only, never a volunteer default until the
  owner accepts it.
- If a future path decodes into the shared image without passing the hover or new-photo
  overrides while `+1170` is set, `clobbered` would miss it (no restore, same as today). The
  only known such writer, `sub_8263E1E8`, restores the new photo itself.

1. Take a photo.
2. In the chooser, move to an occupied slot and back to an empty one; F10. Expected: the

3. Repeat with a second photo while the album is already loaded.
