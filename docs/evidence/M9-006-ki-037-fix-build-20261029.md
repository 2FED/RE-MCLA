## Owner Test A (input)

Owner, 2026-10-29: on a freshly staged build the first photo is broken (black
top, row-band stripes); after restarting the same build the first photo is
correct. This supports H1 of the analysis: with `async_shader_compilation`
the plugin drops draws whose D3D12 pipeline is still being created, the
pipeline set is cached per build (a fresh build has none), and the capture is
taken 1-3 frames after the capture freeze changes the render mode, so
capture-only pipelines are still compiling in exactly the captured frames.

## Design

### SDK (`private/l39-sdk-src`, branch `mcla/ki-040-xinput-rescan`)

Commit `8b10d62812df281691510303746d7eeb9217d84e` on top of `d968f59`
(package version `0.20.0.6-dev.g8b10d62`).

- New hot-reload cvar `d3d12_async_pipeline_wait` (bool, default **off**,
  category GPU/D3D12).
- `IssueDraw`: when `async_shader_compilation` is on, the pipeline state is
  still null and the cvar is on, `WaitForPendingPipeline` waits instead of
  skipping the draw. It waits only for a pipeline whose creation is pending
  (a failed pipeline is skipped as before). If the pipeline is usable after
  the wait the draw proceeds normally; otherwise it is skipped and counted in
  the render audit as before.
- `PipelineCache::AwaitPipeline(handle, timeout_ms, &elapsed_ms)`: until the
  target's `creation_complete` is set, the command processor thread creates
  queued pipelines itself, one at a time and in queue priority order
  (`CreateOneQueuedPipelineOnProcessorThread`, the body of the existing
  `CreateQueuedPipelinesOnProcessorThread`, which now loops over it); when
  the queue is empty (a worker already took the target) it yields. The same
  processor-thread creation path is used by `EndSubmission` today.
- Bounds: 2 s per wait and an 8 s total budget per episode (the span the
  cvar is observed on). After the budget is spent the remaining pending
  draws of the episode are skipped as in the default mode. A single pipeline
  creation in progress cannot be interrupted, so a wait can overrun its bound
  by one creation.
- Logging (GPU category): one `D3D12 async pipeline wait: a pipeline took N
  ms` warning per episode for the first wait of at least 500 ms or the first
  timeout, and one `D3D12 async pipeline wait: episode ended, N waits (T ms
  total, M ms max), ...` summary when the cvar is next observed off, only if
  something was waited for or skipped.
- With the cvar off the draw path costs one bool comparison per draw.
- The per-draw wait sees the pending state directly
  (`Pipeline::creation_complete`), so the alternative "wait for all draws for
  N frames" was not needed.
- Pure wait and episode logic: `include/rex/graphics/util/pending_pipeline_wait.h`
  (`AwaitPending`, `PendingWaitEpisode`), unit-tested with a fake clock in
  `tests/unit/graphics/pending_pipeline_wait_test.cpp` (5 cases, 42
  assertions). `PipelineCache` itself has no test seam (it needs a D3D12
  device and the command processor), so the D3D12 glue is covered only by
  compilation.

Why not flip `async_shader_compilation` at runtime: pipelines already queued
would be recorded with a null PSO and the deferred-list replay keeps the
previous PSO (`deferred_command_list.cpp:522-528`, `kSetPipelineStateHandle`
ignores a null state).

### Host (`claude/ki-037-photo`)

- `src/mcla_photo_capture.h`: pure, header-only `Window` state machine.
- `src/mcla_photo_capture.cpp`: strong `REX_EXTERN` overrides of three
  generated weak functions, and the cvar access through the registry
  (`rex::cvar::SetFlagByName` / `Query<bool>`, as in `mcla_menu_state.cpp`).
  - `sub_8263D120` (capture freeze): after the stock function, if the
    capture-active byte `0x8290622E` is set, open the window and set
    `d3d12_async_pipeline_wait=true`.
  - `sub_8263D1E0` (unfreeze): after the stock function, if the byte is
    clear, close the window and set the cvar back to false.
  - `sub_8263EAA8` (per-frame photo-album update, the only caller of both):
    after the stock function, a frame tick for the safety timeout.
- Safety timeout: the window closes (cvar off) after 120 frames or 5 s,
  whichever comes first; the guest reads the capture after more than 3 frozen
  frames. Host shutdown (`MclaApp::OnShutdown`) also closes it, so a later
  settings save cannot persist `true`.
- If the user already had `d3d12_async_pipeline_wait=true` when the window
  opens, the host neither writes it nor turns it off.
- New cvar `mcla_photo_pipeline_wait` (bool, default **on**, init-only,
  category MCLA): kill switch. If the GPU plugin has no
  `d3d12_async_pipeline_wait` (older SDK) the feature disables itself with
  one error line.
- Logging: at most 50 transitions per process, `MCLA photo capture: window
  open, pipeline wait on` and `MCLA photo capture: window closed|window timed
  out|shutdown after N frames (T ms), pipeline wait off`. A failed write logs
  `MCLA photo capture: could not set ...` (error).
- `CMakeLists.txt`: the new TU under `MCLA_SOURCES` (M9 host hooks block);
  `mcla_photo_capture_test` added to the M9 hook-test `foreach` under
  `MCLA_BUILD_DIAGNOSTIC_TESTS`. `src/mcla_app.cpp`: one include, one
  shutdown call.

Function identity (checked in `generated/default`, identical to the
admiring-jang worktree copy): `mcla_recomp.49.cpp` defines
`sub_8263D120` (`lbz r11,25134(r29)` with `r29 = 0x82900000`, i.e. tests
`0x8290622E`, returns if set, otherwise saves/changes the renderer masks,
calls `sub_82224E58`, stores 1 at `0x8290622E`) and `sub_8263D1E0` (returns
if `0x8290622E` is clear, otherwise calls `sub_82224E48`, restores the masks
and clears it). Both are called only from `sub_8263EAA8` (request bytes
`0x8290622D` then `0x8290622C`). `llvm-nm` on the existing
`l39-merge-build` object `mcla_recomp.49.cpp.obj`: `W sub_8263D120`,
`W sub_8263D1E0`, `W sub_8263EAA8` (weak) with `T __imp__...` bodies, the
same shape as `sub_822D29E8`, which `mcla_menu_state.cpp.obj` overrides with
`T`.
In the new build, `mcla_photo_capture.cpp.obj` has `T sub_8263D120`,
`T sub_8263D1E0`, `T sub_8263EAA8` and `U __imp__...` for all three, while
`mcla_recomp.49.cpp.obj` keeps the three `W` definitions.

## Deviations from the proposal

- SDK wait is bounded (2 s per wait, 8 s per episode) instead of an
  unbounded spin, waits only for a pending (not failed) pipeline, creates
  queued pipelines one at a time while checking the target, and logs a
  bounded warning and an episode summary.
- Pure wait/episode logic in an SDK header with unit tests.
- Host: the window logic moved into a pure header with a unit test; the
  window opens only when the freeze actually set `0x8290622E` and closes only
  when the unfreeze cleared it; a third override (`sub_8263EAA8`) drives a
  120-frame / 5 s safety timeout; shutdown closes the window; a user-set
  `d3d12_async_pipeline_wait=true` is left alone; the feature disables itself
  if the SDK lacks the cvar; at most 50 logged transitions.

## Owner check

On the l41 build, staged fresh (new build folder, so its pipeline cache is
empty), D3D12, default options:
1. Enter Photo Mode and take the **first** photo of the session. Expect a
   correct picture (no black top, no row-band stripes). A short pause at the
   shutter is expected and acceptable.
2. Take a second photo; expect it correct as before.
3. In the runtime log expect `MCLA photo capture: window open, pipeline wait
   on` at each shot and `MCLA photo capture: window closed after N frames
   (T ms), pipeline wait off` (or `window timed out`) afterwards, and on the
   first shot of a fresh build one `D3D12 async pipeline wait: episode ended,
   N waits ...` line with N > 0.
4. Optional control: the same fresh build with
   `--mcla_photo_pipeline_wait=false` should reproduce the broken first photo.

## Limits and unresolved risks

- No runtime confirmation; H1 is supported by Test A, not proven. If the
  first photo is still broken with waits logged, lead 1 (resolve ownership)
  or a guest-side cause rises.
- The freeze/unfreeze span is inferred from static analysis. If the guest
  issues the capture draws outside it, or keeps the freeze longer than the
  timeout before capturing, the wait does not cover them.
- The cvar is a plain bool written on the guest thread and read on the
  command processor thread (the existing hot-reload pattern); the write
  precedes the capture frames' submission by at least a frame.
- A fresh build may create many pipelines in the photo frames; the shutter
  pause is bounded by the 8 s episode budget. A pathological pipeline that
  exceeds 2 s is skipped as before.
- Pipelines created on the command processor thread are taken in queue
  priority order, so unrelated queued pipelines may be created before the
  target (bounded by the same limits).
- The tester-guide workaround (discard and retake) stays in place.
