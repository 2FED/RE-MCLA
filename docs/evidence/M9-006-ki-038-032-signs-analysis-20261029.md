## 1. What the "placeholder colour" is

**Image finding (new).** In the 4K KI-032 frame, every affected sign shows the
same palette in the same arrangement: horizontal **red / yellow / blue** bands,
sometimes with a dark right part. The large billboard is red with a yellow
bottom band; the FOOD MART fascia is red/yellow/blue; a small sign on the
opposite building shows the same three bands. The street-name signs (SELMA,
HIGHLAND) are fine.

In the **720p KI-038 package** (`live-20261026T115437Z-33044-1`), which the docs
record as "only a normal frame", two small distant shop signs show **the same
red/yellow/blue band pattern** (one red/yellow/blue, one yellow/blue). The
signs nearer the camera look normal. This is a window capture, so it shows
that the pattern exists at scale 1, not where it comes from.

Conclusion (medium-high confidence): the "placeholder" is **real texture content
shared by many signs**, either the game's own default/low-detail sign texture or
the earlier contents of a reused texture slot. It is **not** an emulator fallback:

- The emulator's null/fallback SRV returns **all zeros** (transparent black):
  `D3D12TextureCache` null SRV uses `FORCE_VALUE_0` for all four components
  (`src/graphics/d3d12/texture_cache.cpp:612-643`). Unbound or failed textures
  copy that descriptor (`texture_cache.cpp:853-867`; bindless `kNullTexture*`,
  `:914-922`). A null texture could only produce black or a shader constant
  colour, not the same three-band image on different signs.
- No magenta or debug fill exists in the texture load path. A failed load
  (`CommitPreparedTextureLoad` returns false: `pipeline/texture/cache.cpp:413-449`;
  scaled memory not committed/current: `d3d12/texture_cache.cpp:1114-1214`,
  `:1216-1330`; scratch buffer null: `:1702-1706`) leaves the texture outdated
  and is retried. It never substitutes another image.
- Scaled-resolve heaps are created **not zeroed** (`GetHeapFlagCreateNotZeroed`,
  `texture_cache.cpp:1188`). Unwritten scaled memory would show random garbage,
  not a clean band pattern.

So the defect is **stale or never-upgraded sign content**: the sign keeps
showing what was in its slot before (or the game's default) instead of its real
image.

## 2. How the signs get their textures

Not proven from source. The guest code is recompiled and no resolve or texture
trace exists for a sign. The evidence narrows it to two candidates:

- **(a) Streamed static textures.** The game swaps a default sign texture for
  the real one after streaming. CPU or file writes into a watched texture slot
  are coherent: `XFile::Read` triggers the physical-heap callbacks
  (`src/system/xfile.cpp:166-170`), and CPU faults invalidate textures through
  `SharedMemory::MemoryInvalidationCallback` and `FireWatches(false)`
  (`shared_memory.cpp:707-780`). This path does not depend on the scale.
- **(b) Runtime-composited textures.** Billboards or sign atlases are rendered
  into EDRAM, resolved into texture memory and then sampled (or read by the
  CPU). With scale > 1 the resolve writes **only** the scaled-resolve buffer
  (`d3d12/render_target_cache.cpp:1337-1431`; the unscaled shared memory is not
  written). The texture is then sampled through the scaled path only when
  `IsDrawResolutionScaled && key.tiled && IsScaledResolveSupportedForFormat` and
  a page in its range is marked resolved (`pipeline/texture/cache.cpp:761-781`).
  Otherwise it is loaded from shared memory, which still holds the slot's
  **previous** contents, matching the placeholder look. The CPU sees resolve
  output only through readback (`d3d12/command_processor.cpp:3176-3395`), and
  in `some` mode only on every 4th resolve to the same key
  (`:3380-3384`). That copy uses raw `TranslatePhysical` (unwatched view), so it
  does not re-invalidate textures.

The time-varying KI-032 (legible, then placeholder 13 s later while stopped) fits
(b), or an upgrade/downgrade decision in (a), better than a decode bug.

## 3. Why 4K breaks all signs and lower targets only some: ranked hypotheses

**H1. A scale-3-only scaled-resolve path. Rank 1, medium confidence.**
At 2x the scaled-resolve address space is 512 MB x 4 = 2 GB, so there is exactly
**one** 2 GB virtual buffer (`d3d12/texture_cache.h:408-426`, count =
(size-1)>>30 = 1). At 3x it is 4.5 GB, so there are **four overlapping 2 GB
buffers**. Every resolve or scaled texture load at guest physical address
>= ~114 MB then goes through `MakeScaledResolveRangeCurrent` buffer selection
plus **aliasing barriers** between reserved buffers mapped to the same tile heaps
(`d3d12/texture_cache.cpp:1216-1330`, `PushAliasingBarrier` at `:1313-1320`), and
through two-buffer tile mapping (`:1199-1213`). None of this code runs at 1x or
2x. Any coherence gap here (a resolve written through buffer N, then sampled or
read back through buffer N+1 after an aliasing barrier, or the readback
downscale SRV built on "current" buffer `:3287-3307`) would show older contents
for resolve-produced sign textures at 4K only, and would look time-varying. It
also explains why 1080p/1440p (scale 2) are mostly fine. Odd-scale details
(the readback half-pixel sample `scale>>1`, `resolve_downscale.cs.hlsl:65-71,84-92`)
are a weaker, related contributor.

**H2. Scaled readback feeding stale or wrong data to CPU consumers. Rank 2,
low-medium confidence.**
If the game reads resolve output on the CPU (to composite or upgrade a sign, or
to measure visibility), scale > 1 takes the downscale branch, which has several
**silent early returns that skip the CPU copy entirely** (bpp not 8/16/32/64,
`tile_count == 0`, no scaled length, `scaled_address < buffer base`, buffer or
descriptor failures: `command_processor.cpp:3231-3302`). The CPU memory then
keeps the old contents. A concrete defect found here: the downscale reads from
`GetCurrentScaledResolveRangeStartScaled()` (= `copy_dest_base * area`,
`:3254-3255,3297`), but writes the result at `written_address` (=
`copy_dest_extent_start`, `:3388-3391`). The unscaled branch copies from
`written_address` (`:3352-3356`). For resolves whose extent does not start at
the base, the CPU copy is **shifted** at any scale > 1. Before `678adc4`
(including l7), the 32bpp downscale layout was also wrong (`678adc4` diff).
This explains scale > 1 against scale 1, but not 2x against 3x by itself.
It may also bear on **KI-037** (first photo broken). That is untested.

**H3. Texture-cache memory pressure or eviction at 4K. Rank 3, low confidence.**
At 3x, scaled textures are 9x larger. Eviction (`pipeline/texture/cache.cpp:252-302`)
destroys only textures unused since the completed submission and resets
bindings, and evicted textures reload from the same source. That gives a
correct reload or a hitch, never a different image. KI-032 happened at l7
**before** the DXGI budget monitor existed, with a 2.1 GB working set and no
allocation errors. The budget work can make reloads more frequent, but it
cannot create the band image. It would matter only combined with H1/H2 (a
reload that picks the stale source).

**H4. Scratch buffer or `RequestScratchGPUBuffer` limits. Rank 4, low.**
A failure returns false and retries (`d3d12/texture_cache.cpp:1702-1706`). The
failure symptom is a missing or black texture, not the placeholder.

**Ruled out as root cause: the M8 CP optimisations** (bulk Type-0 writes,
`clear_memory_page_state=false`, readback `some`, DXGI budget). KI-032 was
observed at l7 on 2026-10-11, before all of them (see section 0). KI-038 is
recorded as predating l24/unlocked (`docs/known-issues.md:40`).
`clear_memory_page_state` only refreshes valid flags from GPU-written flags
(`shared_memory.cpp:241-277`) and fires no watches. `some` can make **H2**
staleness more frequent (copies 1 in 4) but is not needed for it (l7 used
`fast`, which copies the *previous* slot of the same key, `:3359-3393`).

## 5. Decisive A/B

**One A/B: same output size, change only the scale (3 against 2).** Use the
same copied MAIN save, the Selma/Highland intersection, 3840x2160 output,
stationary for 60 s.
- **A:** current 2160p (`resolution_scale=3`, `draw_resolution_scale_x/y=3`).
- **B:** identical, but `resolution_scale=2`, `draw_resolution_scale_x/y=2`
  (guest 1280x720, presenter upscales). This needs a test-launcher build or
  direct run whose 2160p row passes 2. It is non-destructive and covered by the
  standing authorisation.
- **Capture:** F10 at the sign at t of about 5 s and about 60 s in each arm,
  plus the runtime log. Note whether signs ever turn legible.
- **Reading the results:** A broken and B clean means the scale-3-only path
  (H1, multi-buffer aliasing or odd scale). Both broken at 2160p, while 1440p
  (also scale 2) is clean, points to output size, memory or VRAM (H3).
  Both clean means a timing race.
- **Optional third arm**, if A is broken and B is clean, or both are broken:
  scale 3 with `readback_resolve=full` (synchronous, copies every resolve).
  If the signs are fixed, the game consumes resolve output on the CPU (H2).
  If they are not, the GPU sampling path (H1) is confirmed.

Cheap diagnostic to add with the test build (proposal, not written): per-minute
counters in the existing diagnostics line for (1) aliasing-barrier buffer
switches in `MakeScaledResolveRangeCurrent`, (2) each silent early return in the
scaled readback branch, and (3) textures created with `key.scaled_resolve` and
scaled load failures.

## 6. Fix proposal

`ki-038-proposal.diff` (not applied): make the scaled readback read the
same guest range that it writes back (`written_address * area`, bounds-checked
against the current scaled range). This is a real scale-only CPU-visibility
defect (H2). **It is not proven to fix KI-038/KI-032.** H1 has no fix
proposal until the A/B confirms it.

## 7. Unresolved risks

- How signs are actually produced (streamed or resolve-composited) is unknown.
  A one-frame resolve log near a sign (destination address, format, and
  `IsRangeScaledResolved` result for the sign's fetch) would settle it.
- The 720p band observation comes from a downscaled window capture of distant
  signs. It may simply be the game's normal far-LOD sign texture. Console
  parity is unknown.
- The KI-032 `081347Z` "legible" frame is missing from the retained package
  set (only `081400Z` and `081410Z` remain), so the before/after comparison
  relies on the recorded observation.
- H1 is inferred from code structure (paths reachable only at scale >= 3), not
  from an observed failure.
