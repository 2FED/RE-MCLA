# KI-056 (album slot preview shows the wrong photo): l71 album probe, 720p

Read-only analysis by an Opus subagent on 2026-11-06 of the first l71 album session (720p profile, album probe on, 7 F10 packages); accepted by the primary agent.

Read-only analysis, 2026-11-06. Inputs: the l71 owner session log (39 `MCLA_ALBUM v=1`
lines), 7 F10 packages `live-20261106T134443Z-34080-1` through `-7` (state.json `album` block,
manifest, report, frame.bmp only), `src/mcla_album_probe.{h,cpp}` and the generated guest code
`generated/default/mcla_recomp.49.cpp` (`sub_8263C8B0`, `sub_8263C9C8`, `sub_8263DFC0`,
`sub_8263E1E8`, `sub_8263E4F0`, `sub_8263DCF8`). Nothing was built or launched, and no
before/after-user, save-private or dump files were opened. Times are local (UTC+2). The F10
packages are at 15:44:43, :46, :51, 15:45:13, :21, :27 and :51.

## Verdict

**The cause is in the game's own logic. The host texture cache works correctly.** The new photo
is decoded correctly every time: marker FFD8, the decode-and-bind path runs, the CRC changes,
`data_is_pixels=1`, `fetch_on_pixels=1` and `recreate92=no`. The album has one shared image
buffer, `+1140`/`+1144`, shown through texture `+1132` and material `+1136`. Hovering an
occupied slot decodes that slot's JPEG into the same buffer. Hovering an empty slot decodes
nothing. So after the cursor has passed an occupied slot, the highlighted empty cell keeps
showing that slot's photo. In save mode, nothing puts the new photo back. This is mechanism (a).
Mechanisms (b) and (c) are refuted.

## 2. Mechanism: game logic, not the host texture cache

- **(b) is refuted.** The decode writes the pixels the texture fetches from
  (`data_is_pixels=1`, `fetch_on_pixels=1`, same base E6ACC000), and the texture is never
  recreated.
- **(c) is refuted.** Every CPU rewrite of `+1144` (new_photo, hover, save; 9 content changes)
  is followed on screen by the matching content. A host invalidation miss would keep showing
  the earlier image. For example, at F10-5 the cell would show photo 2 (1F805E50) or older,
  but it shows slot 1's photo, which was written last. The KI-056 symptom is the **correct**
  display of an image that the game overwrote. This also explains why the behaviour is the
  same at 720p, 1080p and 1440p. The log has no `MCLA_WATCH` lines (census not armed). It needs
  none: the probe CRCs together with the frames are conclusive.
- **(a) is confirmed, with this guest-code detail.** The save-mode flag is `+1170`, a pending
  new photo:
  - `sub_8263DFC0(album, slot)` (cursor move, ret 8263E1DC) stores `+1180=slot`, updates the
    prompts, then always calls `sub_8263C9C8(album, slot)`.
  - `sub_8263C9C8`: a slot counts as valid when `+1225 ? slot < +1208 : (+860 >> slot) & 1`. For
    a valid slot it decodes the slot JPEG `*(+428) + slot*0x32000 + 204` into `+1140`, rebinds
    `+1136`, and fires event 4. It does not check `+1170`. For an empty slot it only sets the
    placeholder (`sub_825EE0E0(album+456 vfunc468, str 1432, 1)`), which is the logo in the
    panel, and decodes nothing.
  - The game knows the buffer is shared. `sub_8263E1E8` re-runs `sub_8263C8B0` after each
    thumbnail decode when `+1170` is set. The hover path has no such restore.
  - The highlighted empty cell in the chooser draws `+1136`/`+1132`, the "your photo goes here"
    preview. So it shows whichever image the last occupied hover decoded.
  - This would happen on the console too, unless the cursor never passes an occupied slot. That
    is consistent with the M6 run and an empty-album first open showing the new photo. It is
    also consistent with the l52 first open showing the camera icon.
- The big panel shows the logo placeholder for any empty slot, by guest choice. Neither the
  new-photo path nor the fix changes this.
- Side finding: this profile's slot 0 holds a stored photo that is entirely black. Its grid
  cell is black, and hovering it decodes 049EA761. It is probably a leftover from an older
  session. It does not cause this bug. It only makes the clobbered preview look black.

## 3. Fix A (host, game-side workaround)

Restore the pending new photo when the cursor lands on an empty slot after an occupied hover
has overwritten the shared buffer.

**Hook point:** the existing strong override `REX_EXTERN(sub_8263C9C8)` in
`src/mcla_album_probe.cpp`, after `__imp__sub_8263C9C8` returns. All three callers
(`sub_8263DFC0`, `sub_8263CDC0`, `sub_8263CE88`) tail-return immediately and do not use `r3`.
The override must run its tracker and fix logic whenever the fix cvar is on, even with the
probe off.

**Condition (all must hold):**
1. The new init-only cvar `mcla_album_preview_restore` is on. Default off. Add it to the
   dev-override table (`mcla_dev_overrides.h`, `Phase::kStartup`, next to `mcla_album_probe`)
   and to the `mcla_m10_defaults.h` list, so owner builds arm it with a key.
2. `u8(album+1170) != 0` (save chooser with a new photo pending). This flag is the game's own
   gate in `sub_8263E1E8`, and it is cleared after the save in `sub_8263E4F0`.
3. The hovered slot is empty by the guest's own predicate: if `u8(+1225)==0`, then
   `!(u32(+860) & (1u<<slot))`; otherwise `slot >= u32(+1208)`. The probe's
   `album::HoverValid` already implements this.
4. The buffer is dirty. The tracker records a valid-slot hover decode since the last
   `sub_8263C8B0` completion. This needs a new `NewPhotoTracker` flag, `clobbered_`: set in
   `OnHover(decoded=true)`, cleared in `OnNewPhoto`. Add a counter for the unhooked
   thumbnail decode as well if `sub_8263E1E8` gets a hook.
5. `*(+1148)` starts with FF D8. This is the same check `sub_8263C8B0` makes. Package 7 shows
   `+1148` reused (24D8) after the save, and conditions 2 and 5 together exclude that case.

**Call:** `ctx.r3.u32 = album; sub_8263C8B0(ctx, base);`. Call the hooked symbol, so the probe
logs it and the tracker clears `clobbered_`. Mark it as a restore (`OnRestore()`), not a new
snapshot, and log one line, e.g.
`MCLA_ALBUM v=1 fn=restore slot=N crc4k_before/after`. It takes no other arguments.

**Not "once per snapshot".** The current `PendingRedecode()` latch (`!redecoded_`) is the wrong
bound. Each occupied-to-empty return needs one restore. The correct bound is "only while dirty",
which allows at most one decode per occupied hover. The `saved_` term is unnecessary: `+1170` is
cleared by the save, and `sub_8263DCF8` decodes `+1148` itself (CRC 049EA761 -> 6F46AAAF at
56.079). **No pre-save hook is needed.** The stored photo is correct.

**Expected effect:** in this session, the restore would have run at 47.650 (slot 1) and at
18.266, 22.966, 23.299, 23.631 and 25.732. Only the first return after each dirtying hover
would decode. The highlighted empty cell would then show the new photo. The panel keeps the
logo for empty slots, which is the game's own choice. Occupied-slot hovers keep showing the
slot being overwritten, as now.

**Risks:**
- `sub_8263C8B0` also stores `5` to `*(*(0x8288B9AC)+68)`, a global of unknown meaning. The game
  itself makes this call in the same chooser context from the same main XThread, at 44.962 on
  t36732, so this is not new behaviour.
- Thread: hovers and the game's restore both run on the main XThread. The state-4 decode runs
  on another thread (t33332), but its tick is idle in state 2/0 while the chooser is up. The
  new call is no more concurrent than the game's own call.
- Cost: one 1280x720 JPEG decode (about 3.6 MB written) per occupied-to-empty transition. This
  is the same cost as the hover decodes that already run.
- Event 4 is not fired. The panel does not change, and the risk to scripts is nil. Firing
  event 4 (fix B) is not justified by this evidence, because the panel's logo for an empty slot
  is the game's own placeholder call.
- The original console may behave the same way. This is a quality fix, not an accuracy
  restoration, which is why it stays behind a default-off cvar until the owner accepts it.

**Probe additions for the test build** (cheap):
- Log `+1170` and `+1180` on the hover line.
- Hook `sub_8263E1E8` (thumbnail load) as pass-through, to name the B3A0D6BA writer.

**Owner check:**
1. Take a photo.
2. In the chooser, move to an occupied slot and back to an empty one, and press F10. Expected:
   the highlighted cell shows the new photo, and the log has an `fn=restore` line with
   `crc4k_after` equal to the snapshot CRC.
3. Repeat with a second photo while the album is already loaded (the 15:45:15 case).
4. Save the photo, then check it in view mode.
