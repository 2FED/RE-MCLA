### W1 vs Canary `aee0871dd` (equivalence)

Same trigger and same main effect: a frame whose 15-bit length starts in the last 1-14 bits of a
packet (walk stopped at a frame start with fewer than 15 bits left) is counted, so the frame before it
is no longer "last in packet" and the split-header path decodes the straddling frame. Resulting
`frame_count` is the same (Canary: walked + 1, then the XMA2 header max; ours:
`max(frame_count, walked + 1)` only when the header count does not already include it), and
`current_frame`/`current_frame_size = 0` for that offset match. Differences:

1. **Padding check.** Canary counts the tail unconditionally. W1 claims it only when the next packet
   is not yet available or `CheckSplitTail` shows a real continuation; a confirmed-padding tail keeps
   the upstream behaviour (`AdvanceAfterLastFrame`, counter `walk_split_padding`). Canary would read
   such padding through the split-header path; an all-ones length gives 0x7FFF and sets
   `error_status 4`. On real (non-padding) streams the two are equivalent.
2. **XMA1/XMA2.** Both apply to any packet type (Canary's commit removed the XMA2-only comment; W1 uses
   the trailer bit, not the header count).
3. **Extra in W1.** The dup guard (never re-decode bits before the previous frame's end in a packet,
   `walk_dup_prevented`) has no Canary counterpart.
4. **Packet with only the tail** (walked == 0): Canary counts 1 frame; ours treats it as already
   counted (upstream `frame_count 0` is "last" and size 0 also routes to split-header). Same decode.

Conclusion: W1 is a superset of `aee0871dd` with a stricter padding rule; no port needed.

## C. Timer queue blocking wait (`timer_queue_blocking_wait`, default false)

Facts: `src/core/timer_queue.cpp` runs one dispatch thread. On Windows its only user is the
KeTimeStampBundle `HighResolutionTimer` (1 ms recurring, `xboxkrnl_module.cpp`); on Linux
`threading_posix.cpp` also routes all guest timers through it. Between deadlines it waits in
`multi_threaded_claim_strategy::wait_until_published(seq, last, due)` with
`disruptorplus::spin_wait_strategy`: 10 exponential `_mm_pause` bursts, then `std::this_thread::yield()`
with a 1 ms sleep every 20th spin. With a 1 ms timer this is effectively a core of pause/yield.

Design:
- Each pass reads the cvar (the queue starts at static init, before config). With blocking on, the
  ring is polled without blocking (`last_published_after`), due timers run as before, then
  `WaitBlocking`: `PlanTimerWait(now, earliest due, spin_tail, min_block=50 us)` (pure, in
  `timer_queue_wait.h`) returns RunDue / Spin (16 pauses, back to the loop) / Block(until due -
  spin_tail) / BlockInfinite (no timer).
- Block: Windows `CreateWaitableTimerExW(CREATE_WAITABLE_TIMER_HIGH_RESOLUTION)` +
  auto-reset event; `SetWaitableTimerEx` relative (negative 100 ns units, never 0) then
  `WaitForMultipleObjects(event, timer)`. POSIX: condition variable `wait_until`.
- Wake: `QueueTimer` publishes, `atomic_thread_fence(seq_cst)`, reads `sleeping_`, and `SetEvent`s if
  set. The sleeper sets `sleeping_`, fence, re-checks the ring before waiting (Dekker handshake; the
  auto-reset event is sticky, so a wake between the re-check and the wait is not lost). The
  destructor's kick item wakes it the same way.
- No high-resolution timer (Windows before 10 1803): the spin path stays (logged once).
- Deadline accuracy: wake `timer_queue_spin_tail_us` (default 200 us since 0755836, clamp 0..5000) early and spin
  the rest, so lateness should match the spin path. CPU: for the 1 ms tick about half of the
  current spin time remained with a 500 us tail; the 200 us default leaves about a fifth.
- New always-on line `MCLA_TIMERQ v=1 kind=minute dispatches late_250us late_1ms max_late_us blocks
  queue_wakes blocking spin_tail_us` (emitted by the dispatch thread itself; suppressed once stopping)
  gives the A/B baseline in both modes.
- Not changed: disruptorplus. Its `blocking_wait_strategy` has the `wait_until(lock, pred, time)`
  argument-order bug noted in the survey (`std::condition_variable::wait_until/wait_for` take the
  time before the predicate); it is not instantiated anywhere in our tree (we use only
  `spin_wait_strategy`), so it is latent; fixing it would mean patching the submodule.

Tests: `timer_queue_wait_test.cpp` (plan table: no timer, due/overdue, inside tail, block
until due-tail, zero/negative tail, min_block, relative-due conversion) and one live test (blocking
mode: a 10 s timer puts the thread to sleep, a new +5 ms timer must fire, never early, < 200 ms late).

Expected effect: frees most of a core on 4-LP machines (with the 200 us tail about 80 % of the 1 ms tick is blocked instead of spun) (Steam Deck: KI-060 audio underruns, CP wall);
on the 16-LP PC little FPS change is expected. Risks: lateness spikes if the high-res timer
oversleeps under load (watch `late_1ms`, `max_late_us`); a lost-wake bug would show as a stalled 1 ms
tick (KeTimeStampBundle stops advancing) - the handshake is designed against it and covered by the live
test, but only a run proves it.

## B. Placed texture heaps (`d3d12_texture_placed_heaps`, default false, restart)

Facts: `D3D12TextureCache::CreateTexture` made one `CreateCommittedResource` per guest texture (one
kernel allocation, `NtGdiDdDDICreateAllocation`, on the CP thread). Destruction happens only in
`TextureCache::CompletedSubmissionUpdated` (texture's last submission completed, soft/hard cap) or
`DestroyAllTextures` (cache clear / shutdown).

Design:
- `PlacedHeapAllocator` (API-free, header-only): fixed-size blocks, each an offset-sorted free map;
  first fit over blocks then offsets with per-allocation power-of-two alignment (alignment gaps stay
  free and are reused by 4 KB resources); `Free` coalesces both neighbours and rejects double/foreign
  frees; `TakeReleasableBlocks(keep_empty)` returns empty blocks beyond the spare; `Fits` = size <=
  half a block.
- `CreateTextureResource` (used by `CreateTexture`; the rare 3D-as-2D wrapper stays committed): with
  the cvar, `CreatePlacedTextureResource` asks `GetResourceAllocationInfo` with
  `D3D12_SMALL_RESOURCE_PLACEMENT_ALIGNMENT` (falls back to 64 KB when D3D12 refuses), takes a range,
  creates a new heap when no block has room (`block_mb`, `D3D12_HEAP_TYPE_DEFAULT`,
  `ALLOW_ONLY_NON_RT_DS_TEXTURES | CreateNotZeroed`: valid on resource heap tier 1 and 2; guest
  textures have no RT/DS flags), then `CreatePlacedResource` at the offset. Oversized (> half a
  block), alignment above 64 KB, zero/unknown size, `CreateHeap` or `CreatePlacedResource` failure ->
  committed (counted).
- `D3D12Texture` records its placement; its destructor releases the resource, then returns the range.
  Reuse right away is safe because the cache only destroys textures whose last submission completed
  (or with the GPU idle); placed non-RT/DS textures need no initialisation (the next operation is the
  untiling copy into COPY_DEST). One empty heap is kept as a spare; others are released.
  `~D3D12TextureCache` destroys all textures before the heaps/allocator go away.
- Counters: new always-on line `MCLA_TEXHEAP v=1 kind=minute placed heaps used_mb reserved_mb creates
  placements fallbacks oversized heaps_created heaps_released heap_failures create_us_avg
  create_us_max heap_create_us_max`, emitted in the CP minute block next to the read-back counters.
  `create_us_*` covers both modes, so the l78-equivalent arm measures committed creation too.

Residency and budget interplay (no code change, documented):
- The texture cache's soft/hard caps (`texture_cache_memory_limit_soft/hard`, MB) count per-texture
  `GetResourceAllocationInfo` sizes; with placed heaps the device memory actually reserved is
  `reserved_mb` (whole heaps, plus fragmentation, plus up to one empty spare heap). Expect
  `reserved_mb - used_mb` of up to one block (256 MB) above what the cap sees; on the Deck (smaller
  VRAM) try `d3d12_texture_heap_block_mb = 64`.
- We call no `MakeResident`/`Evict`. Heaps are resident at creation; under memory pressure the OS
  (VidMm) pages allocations as a whole, so a 256 MB heap is paged as one unit instead of many small
  textures: fewer allocations but larger, rarer paging events. The host's own soft cap keeps eviction
  ahead of that in normal play; watch for long hitches together with high `reserved_mb` in the A/B.
- Freed ranges are reused by later textures; the eviction policy itself is unchanged, so the cache
  still frees by LRU, and heaps shrink only when a whole block empties.

Expected effect: texture creation on the CP thread drops from a kernel allocation per texture to a
sub-allocation plus `CreatePlacedResource` (the survey reports 0.19 ms -> 8-11 us and race 1 % low
50 -> 96 fps for a similar design; our numbers come from `create_us_avg/max`). Targets KI-072/KI-067
streaming drops. Risks: driver-specific placed-resource bugs (AMD/Intel/NVIDIA differ), memory
overhead above the cap, any accounting bug would show as `heap_failures`/fallbacks or corruption;
heap creation itself (first use, then rare) is a one-off hitch (`heap_create_us_max`).
