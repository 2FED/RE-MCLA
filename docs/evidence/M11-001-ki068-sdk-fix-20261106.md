## 1. The KI-068 fix: stable creation times

The root cause comes from the primary agent's re-diagnosis, not from this subagent's work. MCLA
stores the save file's creation time after each save: `sub_82617AE0`, NtQueryInformationFile class 34.
Before the next save, `sub_82617228` compares the stored value with the current one. A mismatch leads
to UI state 24, the "device removed" screen.

Why this fails on the Deck and not on the PC:

- In v0.20.0.8 the SDK copies the entry creation time from the host in two cases:
  - `HostPathEntry::Create`, from `ListFiles` at mount and on lazy lookup;
  - `CreateEntryInternal`, through `GetInfo` right after `fopen "wb"`.
- Every save mounts a fresh `HostPathDevice` (`ContentPackage` ctor, `content_manager.cpp`), so the
  entries are rebuilt from the host each time.
- NTFS keeps the creation time fixed, and tunnels it across delete + recreate. Wine on ext4 reports a
  value that moves when the file is written.

The change (cvar `xam_content_stable_creation_time`, bool, default **true**):

- `src/core/content_log.cpp` adds `StableCreationTime(key, observed, &remembered)`,
  `SetStableCreationTime` and `StableCreationTimeEnabled`.
  - This is a process-wide map. The key is the host path, lexically normalised and case-folded.
  - The key is never logged. It keys by host path rather than by device-relative path, because every
    package has a file with the same relative name. Keying by host path gives one value per real file.
- `src/filesystem/devices/host_path_entry.cpp:50` `HostPathEntry::Create`. On a content device
  (`\Device\Content\N`), the entry reports the first creation time seen in this process for that host
  file, whatever the host now says. This covers every way an entry is built:
  - `PopulateEntry` at mount;
  - the `ResolvePath` lazy lookup;
  - `CreateEntryInternal`, which passes `source="create"`.
- `host_path_entry.cpp:228` `SetCreateTimestamp`: a creation time set by the guest
  (NtSetInformationFile basic info) updates the table.
- Delete + recreate of the same file keeps the remembered value. This is like NTFS tunnelling, and
  every query within a process stays consistent. The table is in memory only; the game's own table is
  in memory too.
- Only `\Device\Content\*` devices are affected. Game data (`game:`) and other host devices are unchanged.

## 3. Hardening (not the KI-068 root cause)

- **Close host handles on unmount.** Cvar `xam_content_close_host_handles_on_unmount`, default true.
  - `content_manager.cpp:1083` `CloseOpenedFilesFromContent` still releases one guest handle per file
    object, as before. It then calls `ForceCloseHostFiles` (`:1124`), which closes the host handle of
    every file object on that device whatever its reference count:
    - `XFile::ForceCloseHost` (`xfile.cpp:55`);
    - `HostPathFile::CloseHost` (`host_path_file.cpp:34`). A `shared_mutex` serialises the close
      against in-flight I/O, and the global critical region is never taken under it.
  - Later Read/Write/SetLength, Rename and QueryDirectory return `X_STATUS_FILE_CLOSED` (0xC0000128,
    newly defined) and log a paced WARN: `[content] write on a file closed by content unmount: path='mc4.sav' status=0xc0000128`.
  - INFO `[content] close: N host handle(s) force-closed on unmount: root='save' still_referenced=K`
    is logged when N > 0.
  - With an empty symlink resolution, the old code released **every** open file of the title (empty
    prefix). It now logs a WARN and returns.
- **Move aside on delete failure.** Cvar `xam_content_move_aside_on_delete_failure`, default true only
  under Wine (`wine_get_version` in ntdll, `content_log::RunningUnderWine`).
  - `RemovePackageTree` (`content_manager.cpp:133`) is used by DeleteContent, UnmountAndDeleteContent
    and Recover.
  - When `remove_all` fails with raw Win32 145 or 5 (the system category only; sharing violation 32 is
    excluded on purpose), every remaining file is renamed to `<name>.rexdead-<session>-<n>` in the
    package parent and the removal is retried once.
  - Lines: INFO `move-aside: <op> remove failed with win32=..`, WARN per failed rename, INFO/WARN
    for the retry result.
  - `SweepDeadFiles` (`:214`) deletes earlier-session `*.rexdead-*` files, non-recursively and files
    only, in the package root. It runs at ListContent and at Recover, and logs `move-aside: swept N
    earlier-session file(s), M still in use`.

## 4. Tests

- `tests/unit/system/xam_content_unmount_test.cpp` (new):
  - **Reproduced leak.** A guest XFile over a share-delete HostPathDevice keeps its host handle after
    one reference is dropped: an exclusive CreateFileW gets a sharing violation. After
    `ForceCloseHostFiles` the handle is closed, the file and package are removed, and later I/O
    returns FILE_CLOSED.
  - Other devices and an empty prefix are not touched.
  - With the cvar off, the old behaviour stays: the handle is still open and reads work.
  - DeleteContent moves aside on a simulated 145 (fault hook). The files move to the parent,
    enumeration ignores them, and the retry succeeds.
  - The sweep deletes earlier-session files only (current session, unrelated files and directories
    are kept); enumeration sweeps too.
  - With the move-aside cvar off, a 145 returns ACCESS_DENIED, nothing is moved and the payload is intact.
  - 32 is not moved aside; 5 twice leaves the error after the move.
  - Transaction stages reach Commit.
  - **Creation time.** A file is created through the VFS and written. The host creation time is then
    shifted by one hour (SetFileTime) as a stand-in for Wine, and the test asserts that the host now
    reports the new value. A remount still reports the original value. A guest-set value persists
    across remounts. With the cvar off, the remount reports the shifted host value (the symptom).
  - Table semantics.
- `tests/unit/core/content_log_test.cpp`: AllowChanged de-duplication (change, gap, backwards clock,
  reset); the new kind names and the trace switch.

## 5. Owner Deck test

Build this SDK into an owner candidate (default cvars). Then:

1. Load a profile with an existing save.
2. Make two consecutive garage saves.
3. Quit, restart and check that the second save loaded.

Pass means both saves succeed with no dialog, and the progress survives the restart.

Expected log (`grep -n "\[content\]" mcla*.log`) around each save:

- `trace: notify: id=0x9 (XN_SYS_UI) ...` (if a UI is involved)
- `trace: XamContentCreateEx: requested=CREATE_ALWAYS ... recreate=1 result_disposition=created stages=delete-existing,create-package,write-header ... result=0x0`
- `trace: entry timestamp: path='mc4.sav' source=create creation=0xC1 ... stable=remembered` (the same C1 as the earlier `source=list` line)
- `trace: NtCreateFile: path='mc4.sav' ...`, then `trace: query times: path='mc4.sav' class=34 creation=0xC1`
- `trace: XamContentClose: root='save' result=0x0 committed=1` and `save ok: content='mc4.sav' ... stages=begin,backup,delete-existing,create-package,write-header,commit ms=..`
- Before save 2: `query times ... class=34 creation=0xC1` again.

The key check is **the same creation value at every class-34 query of the session**. Within a line,
`host_creation` should differ from `creation` on the Deck; that is the Wine drift being masked.

A/B: with `xam_content_stable_creation_time=false` the dialog should come back on save 2. That run
also shows `creation` changing between the two class-34 queries.

The l70 session had no `[content]` lines at all, which fits the re-diagnosis:

## 7. Risks

- **Creation time.** The value can differ from what the host reports, but only for content-device files
  and only within a process. Tools outside the SDK see the host value. A guest that expects a recreated
  file to get a fresh creation time would see the old one (NTFS tunnelling behaves the same within 15 s).
- **Close on unmount.** A guest that keeps using a save handle after XamContentClose now gets
  FILE_CLOSED instead of writing a file that is no longer mounted.
  - Pre-existing and not fixed here: such a file object's `entry()` points into the destroyed device.
    The new code avoids it, but other kernel paths such as NtQueryInformationFile would still touch it.
  - PC save/load regression run needed.
- **Move aside.** It runs only on Wine and only for raw 145/5. Wine's handling of a rename on a
  delete-pending file is unverified. If the rename fails, the result is the old behaviour plus WARN lines.
- **Log volume.** The trace kinds are paced at 16 lines plus 1/s each, and the device queries are
  de-duplicated. `xam_content_trace=false` turns them all off. The INFO `save ok`, `close` and
  `move-aside` lines are not gated.
- **Proven only on the PC.** The Wine creation-time drift is simulated with SetFileTime. The Deck run
  is the acceptance test.
