## Method

As in `M10-l63-pc-ab-20261102.md` (same scripts, Deck paths): segments are the `MCLA_PERF_SPLIT`
windows between consecutive F10 marks (stationary = start F10 to the ~90 s F10; laps between the next
F10s); per-frame values are segment sums / segment frames; CP work = `cp_busy - fence_wait`; render
work = `render_cpu - render_wait`. `MCLA_WATCH`/`MCLA_READBACK`/`MCLA_READBACK_SYNC`/`MCLA_WRM`
`kind=minute` lines were reduced by the marks since the previous minute line (check: corrected
`MCLA_WRM wait_ms` = perf-split `wrm_mem_ms` in every segment, e.g. 6.257 vs 6.26, 7.596 vs 7.60).
On the Deck the render thread is handle `F80004DC`; the guest polling thread is `F800068C` (`F8000690`
in run 1), the audio-side worker `F8000534`. Pacing, GPU busy, `watch protect/min`,
`MCLA_REPLAY_WAKE` and pipeline waits are per minute only. The Vulkan run has no perf split and no
`MCLA_*` counters (D3D12-only); it is compared through the shared `state.json` counters
(`runtime.guest_output_sequence`, `guest_vblank_sequence`, `graphics.command_swap_packet_count`)
between the same F10 marks; for the D3D12 runs those counters reproduce the perf-split fps to 0.01
fps (e.g. run 2 stationary: 1476 outputs / 95.4 s = 15.47 = perf split).

Comparability: runs 1, 2, 4 started the stationary segment at the same spot (draws/frame 6562 / 6563 /
6462); run 5 stood at a different spot (6014 draws/frame; the frames confirm), so its stationary fps
is not an A/B point. Laps are 122-163 s (run 1 lap 2 includes a 10 s pause, 11:32:56-11:33:06). Run 1
started with an empty shader store (section 5): its lap 2 carries 3.48 ms/frame of `pso_wait` and a
minute with 202 pipeline waits (6.3 s), so run 5 is the cleaner base for laps.

## 2. Deck verdict for "all"

**+15% fps while driving** (12.73 -> 14.67; +13% against the warm base run 5 alone), **+12%
stationary** at the same spot (13.74 -> 15.39), and a much steadier frame time (median locked at 4
vblanks; >100 ms frames down from 26-94 to 1-7 per minute). Interval -10.4 ms/frame.

Where the 10.4 ms came from (lap means; CP chain = CP busy + wrm_mem + ring idle = interval in both
arms):

Sum on the CP chain: upload -8.3, forced wait -4.1, kick/finish/submit about +2.8, wrm -0.4, pso
-1.1 (run 1's cold store, not a switch), draw +0.7 (us/draw 4.09 -> 4.15, `p_tex` 0.95-0.99 ->
1.05-1.12), rest +0.0-0.3 = about -10.4. So **on the Deck, upload-ahead is the biggest contributor
(roughly 80% of the switch-driven gain), targeted sync + elision a modest second, WRM small; bridging
and the render-thread switches help the render thread and free CPU but are not on the CP chain**.
This is the opposite of the PC ranking, as the Deck watch design predicted: under Wine one
`VirtualProtect` costs 12-17 us and a write fault 38-71 us, so fewer, larger calls win even with 3x
the upload bytes.

**First wall now: still the CP thread.** CP busy 89% + wrm 10.5% = 99.6% of wall occupied, ring
idle 0.4%; the render thread spins 23% of its CPU waiting for the CP; the GPU is 40% busy. The CPU is
still oversubscribed: top-8 threads 4.3 cores on the 4-core APU; the CP should be working (busy -
fence - stream finish = 51.6 ms/f) but is on-CPU only 44.8 ms/f: about 6.8 ms/f (10% of wall) it is
not running (base: 7.5 ms/f).

**Remaining budget**: driving frame 68.2 ms (4-5 vblanks, median 4). The next quantum is 3 vblanks
(50 ms, 20 fps): the CP chain must drop below ~48 ms with margin, i.e. **about -12 to -13 ms/frame
from CP busy 60.7** (stationary 57.2: about -9). Smaller cuts only move the 4/5-vblank mix towards a
steady 15 fps. What is left on the CP (laps, ms/frame): draw 24.6 (bind 1.09-1.14 + tex 1.05-1.12
us/draw = 13 ms), upload 14.3 (arm 8.1 at 17 us/call), forced sync 6.25 + kicks ~2.5, packets_other
8.4, copy outside the wait 3.6, read-back memcpy 1.5, resolve 1.1, submit/execute/present 1.0; plus
7.2 of vblank wait.

- **KI-062 (black player car under Vulkan) is in all four Vulkan frames**: the player car is plain
  black (with red/green rim highlights) instead of the camouflage livery it shows in every D3D12 frame
  of runs 1, 2, 4 and 5 (same car and save).
- KI-063 (Unlocked never activates under Vulkan) is irrelevant at stock 30.

**Verdict: not worth fixing for the Deck.** Vulkan is 4-7% slower than D3D12 "all" while it still
has **no** composite read-back sync; a KI-047 port adds a fence round trip per composite (on D3D12
that is 6.25 ms/f plus ~2.5 ms of kicks, and Vulkan has no elision), so a correct Vulkan build would
land at or below the D3D12 base. Its own CP overhead (binding update 12 ms/f, deferred execute
8 ms/f, swap 4 ms/f) exceeds what it saves on vkd3d translation. Three fixes (KI-063 cap, KI-047 sync
port, KI-062) for a negative return: keep Vulkan for PC diagnostics and drop it from the Deck plan
unless `vulkan_binding_update` falls by more than ~10 ms/f.

## 6. Recommendations

Deck (Proton) default set for the next volunteer build:

1. **Upload-ahead 16: ON for Proton** (CP -8.3 ms/f, the main Deck gain) and **disarm bridging: ON
   for Proton** (fault path -3.3 ms/f, frees render-thread time). Both stay OFF on Windows (net
   negative on the PC), so this needs a per-platform default (Wine detection or a launcher Deck
   profile).
2. **Targeted sync + read-back elision: ON** (net -1.3 to -1.9 ms/f here, the main PC win; zero
   failures, fallbacks and guard misses on both platforms). Police-livery visual check still owed.
3. **Native refcount, XAPI interlocked, WRM event wake, replay batched wake: ON** (render thread -5.5
   ms/f, CP chain -0.4 ms/f, 0.37 core freed; no regression in any counter).
4. Census OFF in volunteer builds.
5. Fix the Deck store seeding before shipping (run 1 shows the cold-store cost: 1-3.5 ms/f of
   `pso_wait` and 6 s pipeline-wait minutes).

Next Deck levers, ranked (ms per driving frame; target -12 to -13 for 20 fps):

1. **Hot blocks, watch step 3** (design: CP -5 to -10, faults -4 to -7). Arm is still 8.1 ms/f at
   17 us per call, the rest of upload 6.2 ms/f, write faults 7.2 ms/f; in the "all" census, pages
   validated >= 600 times per minute carry 24% of page-validations (base 5.5%) and the top 256 KB
   block alone 310k valid calls per minute: upload-ahead concentrated the traffic in hot blocks. The
   biggest remaining predicted lever.
2. **Kick tuning** (cheap dev-override A/B): kicks cost 0.23 ms each under vkd3d (2.2 ms/f plus
   stream-finish) while a targeted wait still costs 4.5 ms. A/B `kick_draws` 1024 / 2048 / off on the
   Deck; up to -2 to -2.5 ms/f.
3. **Free cores**: the polling thread `F800068C` uses ~80% of a core while driving (half of it kernel;
   `KeDelayExecutionThread` 60% of its last imports) and the audio-side `F8000534` 84% (`KfLowerIrql`
   80% of its last imports): ~1.6 cores of a 4-core APU, while the CP loses ~10% of wall off-CPU. A
   cheaper `KeDelayExecutionThread`/IRQL path under Wine helps the CP and probably KI-060.
4. **CP draw phases** (24.6 ms/f, 4.15 us/draw, ~3.3x PC): bind + tex 13 ms; long-term, or M10-006
   multi-threaded CP once cores are free.
5. Vulkan: no (section 3).

## Limits

Two runs per D3D12 arm and one Vulkan run; run 5's stationary spot differs; run 1 had a cold store
and a 10 s pause in lap 2. All switches were toggled together, so per-switch attributions come from
their own counters, not from single-switch arms (upload-ahead and bridging interact: bridging's fault
