### Verdict

- **CP time and fps: no gain.** Hot-on removes what it was meant to remove: arm calls 474 -> 275/f
  (-42%), disarm 182 -> 110/f, render write faults 172 -> 102/f; watch arm -2.7, disarm -1.2, write
  fault -2.0, upload -3.0, draw_regions -2.7 ms/f. But the CP spends it again: draw +2.0, copy +0.7,
  fence wait +0.65, forced SYNC wait +0.7 ms/f, so CP busy stays 59.6 -> 60.0 ms/f (89%) and CP work
  53.5 -> 53.2 ms/f. Render work falls only 1.0 ms/f while render spin rises 2.1 ms/f (the render
  thread waits longer on CP/GPU). Driving fps 14.94 (all) vs 14.85 (on); both runs of each arm agree
  (all 14.77-15.14, on 14.80-15.07). Normalised by draws (hot-on drove 4% heavier frames, 6151 vs
  5924 draws/f) CP busy per draw is about 3% lower (9.75 vs 10.06 us), which stock-30 vsync
  quantisation (p50 66.7 ms = 4 vblanks in every arm) does not turn into fps. Stationary: on #2
  15.39 fps at 6763 draws/f vs all 14.76/15.20 at 6732/6509; on #1 16.22 fps at a different spot
  (6173 draws/f), so no clean stationary gain either.
- **GPU/submit cost of copies between draws: large.** 2050-2180 hot copies per frame, 99.9% recorded
  after a draw in the open submission (`hot_copies_after_draw`), about 12 MB/f. Upload calls rise 5x
  (457 -> 2312/f) while upload bytes stay the same (~27 MB/f). GPU busy rises 27.1 -> 37.5 ms/f
  (+10.4 ms/f, about 5 us per copy; 41% -> 56% of wall driving, 73% in the dialog window), and the
  vkd3d replay thread rises 23% -> 31% CPU (replay 15.8 -> 21.3 ms/f); top-8 threads +0.1 core. The
  Deck GPU still has headroom at 15 fps, so this costs no fps now, but it eats most of the margin a
  faster CP would need (37.5 ms/f of GPU caps this scene at about 27 fps).
- **Shadow projection vs measured.** Shadow projected 270 saved arm calls/f driving; measured
  reduction 199/f (474 -> 275), about 74% of the projection (the probe returns each block to the
  armed path every 64 frames, and the request cap sends ~41 requests/f to the normal path).
  Projected hot requests 2335/f vs 2049 measured (88%); projected hot upload 14.0 vs 12.2 MB/f
  (87%). Projected request-cap hits (598/f) count fast-path requests and are not comparable;
  measured cap hits are 28-41/f (request cap), 0 byte-cap hits. hot_blocks_now 39-54 in both modes.
- **Flapping: the probe cycle, not churn.** Enter 619-751/min with 586-600 probe exits/min: ~45 hot
  blocks x 15 fps x 60 / 64 frames = ~630/min. Cold exits 117/min and source exits 42/min driving;
  watch exits 1/min; gpu exits 0. Shadow (no probe) shows 328 enter/min, cold 296. No enter/exit
  storm in any window, including the fine windows (enter 547-683 per window).
- **Safety: clean.** `memory_watch_protect_failures=0` in the last package of every run; READBACK
  `guard_misses=0`, SYNC `forced_wait_failed=0` and `fallbacks_to_full=0` in every window;
  `hot_gpu_whole=0` and no "whole-buffer GPU write" line in any run; `hot_exit gpu=0` (no hot block
  was GPU-written); `gap_lock_misses` 0-12 per segment (all: 0-23), `ahead_lock_misses=0`. The only
  "stale" fields are the WRM `stale_wakes` counter (all arms). Composite diagnostics
  (`MCLA_LIVERY_DIAG2`): same kinds in all runs, counts proportional to session length, no new kinds
  under hot-on. SYNC/readback misses per segment are in the all range (11-106 vs 19-88).
- **Recommendation: do not make mode 2 the Proton default; keep it as an experiment and tune.** The
  saving is real on the watch side but is re-spent in the CP draw/copy path and moved to the GPU and
  the replay thread by ~2000 small copies between draws. The tuning target is the copy shape, not
  K/N: batch the hot copies (one copy per hot block per submission, or a per-submission snapshot of
  the hot blocks before the first draw) so they no longer split render passes, then re-measure. A
  lower request cap (for example 64) would bound the GPU cost but also the saving. Shadow mode 1
  costs about nothing (shadow fps 14.97/15.10 vs all 14.94/14.98, CP busy 59.3 vs 59.6) and stays
  useful for projections.

Findings:

- **No host error at all around the save.** After startup the session logs (mcla.1.log + mcla.log)
  and the runtime log contain no warning or error line: no NtCreateFile failure on the save device,
  no VFS/XContent/STFS line, no STATUS code. The only warnings in the session are the startup set
  every run has (`t:\mc4\art\city` NtCreateFile 0xc000000f x7, read-only `game:` write probes,
  GameControllerDB, XeKeysConsolePrivateKeySign, cross-thread LeaveCriticalSection), all at
  17:20:58-17:21:25. The SDK does not log XAM content failures: `xeXamContentCreate`, the MCLA
  transaction layer (`BeginContentTransaction` / `RecoverContentTransaction` / `DeleteContent` /
  `WriteContentHeaderFile` returning X_ERROR_ACCESS_DENIED / X_ERROR_BUSY / X_ERROR_DISK_FULL),
  `XamContentClose` and NtWriteFile failures return silently; only NtCreateFile failures are logged
  (`REXKRNL_IMPORT_FAIL`). The SDK broadcasts no storage-device-change notification, so the dialog is
  the game's reaction to a failed content/file call, not to a notification.
- **Fine 1's save (or the retry) worked; the save path under Proton is not broken in general.** The
  launcher snapshots of hot-on #1 differ in 2 of the 6 file lines (lines 11 and 13; before/after 15
  lines each). The other four l66 sessions and all five sessions of the earlier Deck export
  (owner-deck-20261103) have 0 differing lines; they are also the only sessions without fines
  (`racer-off 1` events = 2, the start sequence, in each; 6 in hot-on #1). So hot-on #1 is the only
  Deck session in both exports in which the game saved, and at least one save reached disk (fine 1's
  autosave or the dialog's SAVE GAME retry at 17:32; the primary should decode the two changed names
  to confirm mc4.sav and its header). Content of the snapshots was not inspected.
- **No transaction left behind.** All seven F10 packages (including #5 at 17:26:25, with the dialog
  on screen) copied exactly 4 save files, 3815088 bytes. A pending transaction would have added
  `*.rexbackup` / `*.rexpending` files to the 545407F8 tree that the export copies, so the failed
  attempt either failed before `BeginContentTransaction` or rolled back cleanly.
- **The F10 #4 export overlaps fine 2's start; nothing else observable distinguishes the two fines.**
  Fine 1's pull-over (17:25:15) had no export running (the previous one ended 17:24:32). Fine 2's
  pull-over began at 17:26:04.075, inside the F10 #4 export (17:26:03.204-17:26:05.128), which copies
  the live save tree of the profile's user directory (`CopySaveTrees` -> `CopyStableFile` ->
  `std::filesystem::copy_file`).

Hypotheses, ranked:

1. **The F10 save copy collided with the game's fine autosave (most likely if the game saves when the
   pull-over starts).** Under Wine the export's `copy_file` holds the save file and header open for
   reading; the content transaction meanwhile copies the package to `.rexbackup`, deletes it
   (`CREATE_ALWAYS` -> `DeleteContent` -> `remove_all`) and rewrites the header. A sharing conflict
   there returns X_ERROR_ACCESS_DENIED silently, the transaction rolls back (no leftovers, as
   observed) and the game shows "storage device removed" when the pull-over scene ends
   (17:26:20.975, 0.37 s after the last racer-off cleared). Consistent with: only fine 2 overlapped an
   export; no NtCreateFile warning (the failure is in the host transaction layer, not a guest open);
   no leftover markers. Not proven: the guest save time is not logged.
2. **Silent content-layer failure unrelated to F10 (if the game saves at the end of the pull-over,
   about 17:26:20.6, 15 s after the export ended).** Candidates: X_ERROR_BUSY (fine 1's transaction
   marker still in `active_content_transactions_` because the game never closed that root; less
   likely, since F10 #3/#4 at 17:25:52/17:26:03 found no `.rexpending` file), or ACCESS_DENIED from
   `remove_all`/`copy` on the Proton filesystem because a guest handle to the save file from fine 1's
   save was still open.
3. Hot blocks: not implicated (they touch only GPU VB/IB uploads; no protect failure and no exit
   anomaly in the fine windows).
4. Launcher writer lock: not implicated (the launcher only snapshots before launch and after exit).

Confirming evidence needed (not obtainable from this export):

- One WARN line per non-success in `xeXamContentCreate` (stage: exists/begin/delete/create/header/
  open, X_RESULT, std::error_code value, path), in `XamContentClose` / `CommitContentTransaction`, and
  for NtWriteFile/NtSetInformationFile failures on the save device; plus F10 export lines "save copy
  start/end" with timestamps and per-file `copy_file` error codes. Hypothesis 1 is confirmed by an
  `ACCESS_DENIED stage=delete|header` line inside an export's save-copy window.
- Owner: which option was picked in the dialog at 17:32 (did SAVE GAME succeed?).
- Repro on the Deck: F10 exactly when a pull-over starts vs a fine without F10.
- Cheap mitigation regardless of cause: make the F10 export skip or retry the save copy while a
  content transaction is active (take the content manager lock, or copy only when
  `active_content_transactions_` is empty) and open sources with full sharing.

  - Fine 2: per-frame F10 audit samples (F10 #3, 300 frames, 17:25:53.10-17:26:10.87) cover the 11 s

  - Around both fines: WRM max wait 15.7-16.0 ms per window; forced readback SYNC max 11-13 ms; no

    probe-dominated); request-cap hits per window at the usual rate (no storm).

  max 101-119 ms (116-184 ms only in minutes with an F10 capture); >200 ms: none in any arm after

  logic (stationary next to a police car), with 67-83 ms stock-30 frames as the steady background in
  every arm. Keep KI-066 open as "not reproduced in the second hot-on run"; if it recurs, an F10
  just before the pull-over gives per-frame data.

  collision-less mode); not a spike effect and not specific to hot-on (no counter anomaly then). Same

  is needed to separate a low-rate artefact from stock game behaviour.
