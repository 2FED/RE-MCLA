# M8-001 60 FPS timebox: why the race clock runs slow in interval1

October 25, 2026. Code reading plus existing retained data only; nothing was
built or launched for this note.

## Short answer

MCLA advances game time by a **fixed 1/30 s per game update**, not by
measured wall time. Interval1 does not change that step. It only changes the
swap interval, and in our harness runs it produced *fewer* updates per second
than stock. Race clock speed is simply `updates per second / 30`:

- Oct 21 interval1 Arcade collection: 259 timer ticks in 12.0 s
  (21.5 ticks/s). Every tick added exactly 0.033333 s. The game's own timebase
  measured 12.08 s of real time, but game time advanced only 8.63 s: **0.72x**.
- Oct 18 stock/interval1/stock cohort: the HUD clock moved about 3.3 cs per
  published frame in **all three arms** (A1 442/134, B 343/104, A2 456/139).
  The per-frame step was the same; B just published fewer frames
  (about 18/s versus 23-24/s for stock).
- Even stock was below real time in those harness runs (about 0.78-0.80x),
  because it also stayed under 30 updates/s.

## The code

Timer tick `sub_821BDA90` (TU5, `generated/default/mcla_recomp.5.cpp`):

1. Reads the timebase (`mftb`), stores the raw tick difference times a
   constant as measured seconds in `+92`. A caller override `f1 >= 0` replaces
   it (`+100`/`+88`). Scaled copies go to `+96`, `+104` and `+8`.
2. `+56 != 0` (first tick after reset) branches to `0x821BDBC8`. That path
   uses `+32`, or `1/+28` when `+32` is zero, then clears `+56`.
   **This is the branch at `0x821BDB08` that Xenia's patch replaces.**
3. Normal path, fixed mode (`+58 != 0` or `+60 != 0`): the effective delta
   `+8 = +32 * scale(+84)`. The measured time is ignored. Accumulators
   `+20`/`+24` advance by that constant.
4. Normal path, raw mode (`+60 == 0`): the effective delta is the measured
   time. If a cap `+32` is configured, values above it are clamped to the cap,
   and values below it set `+52 = 1`.

Setters, both called from `sub_822D2478` (TU14):

- `sub_821BD9F8` (fixed): `+60 = 1` and `+32 = +8 = +88 = 1 / (F1 * R5)`.
  `F1 = cfg+84 / cfg+80`, `R5 = cfg+92`. It is chosen when `cfg+72 != 1`.
- `sub_821BD9B8` (raw): `+60 = 0`, optional cap. It is chosen when
  `cfg+72 == 1`.

The retained Oct 21 journal shows stock values `+28 = 30`,
`+32 = 0.0333333`, `+60 = 1` and scale 1.0. That is fixed30 mode.

Presentation selector `sub_824199B0` (TU27) maps the D3D device field
`+13596` to the swap interval: 0 or 1 give 1, 2 gives 2, 4 gives 3. Stock sets
`+13596 = 2`. The game is therefore designed as a 30 FPS lock: it swaps every
two vblanks and steps 1/30 s per frame. The interval1 candidate changes only
the literal for case 2, so the timer policy is untouched.

Xenia's "60 FPS Game Speed Fix" has two writes. It patches the interval
(`0x82419AA3`) **and** replaces the `+56` check at `0x821BDB08` with a jump
to the epilogue. The jump makes every tick use the raw measured delta, but it
also skips fixed/raw mode selection, the `+20/+24` history and the reset
handling. That fits the owner's earlier report of an accelerated splash and
turning jerk with that branch.

## Hypothesis

H1 (supported by the data above): the slow race clock in interval1 comes
from **fewer game updates per second at a fixed 1/30 s step**, not from a
wrong delta.

H2 (open): why interval1 yields fewer updates than interval2 on this host.
Candidates:

- a host present/VSync wait that happens on every swap instead of every
  other one;
- the game's GPU-completion spin (`82411E98`) aligning badly with
  single-vblank swaps;
- capture overhead.

H2 matters for frame rate, but not for correct speed.

Consequence: "60 FPS" needs two independent things:

- time that follows the wall clock at any update rate;
- a higher update rate.

Patching the interval alone can only make speed worse whenever the update
rate stays below 60.

The cleanest time fix uses the game's own raw mode, `cfg+72 == 1`. It goes
through `sub_821BD9B8` and keeps the reset and history handling, unlike the
Xenia jump. Raw deltas are still clamped to about 0.0001..0.1 s per tick. The
Oct 21 stock-config/raw/stock-config cohort on the interval1 host already
leaned this way: raw rose by 1.30x and 1.10x, against about 1.39x expected
from 0.72x. It was inconclusive only because control drift was 1.19.

### Cause

Each update takes 2 or 3 vblanks (33/50 ms), irregularly and sometimes 4.

| Run | 2 vblanks | 3 vblanks | 4+ vblanks | Mean change between successive measured steps |
| --- | ---: | ---: | ---: | ---: |

| B lean (raw) | 146 | 131 | 21 | 10.7 ms |

- **Fixed mode:** each step is a constant 33 ms. Motion is smooth but slow.
- **Raw mode:** each update applies the previous interval as its step, so
  per-frame motion and motion blur jump by up to +-25 %. That is the judder
  the owner saw.

### Fix candidate l14

Same source as l13 plus `sub_821BDA90` step smoothing.

- **What it changes:** for the main timer object `0x827D7500`, in raw mode and
  outside reset ticks, the step is measured from the timebase. The average of
  the last 8 steps, plus a quarter of the accumulated difference (clamped to
  +-25 % of the average), is passed as the tick's own caller-supplied step
  (`f1`).
- **What stays the game's:** the scale, clamps and history in the raw path.
- **Hitches:** steps above 0.1 s pass through unchanged and reset the average.
- **Switches:** `mcla_raw_timer_smoothing` (default ON) and
  `mcla_raw_timer_stats` (log every 300 updates).

### Method

- **Tooling:** no new instrumentation. The kept diagnostic host's phase census

- **Thread CPU:** a lightweight sampler read every mcla thread's CPU time once

- **Runs:** same rebuilt interval1 control host, stock fixed timer, Arcade

| Run | Guest render thread | Busiest non-guest thread | Next non-guest thread | Game thread | Process total |
| --- | ---: | ---: | ---: | ---: | ---: |
| VSync off | 99.4 | 95.4 | 24.7 | 30.9 | 312 |
| VSync on | 98.7 | 53.1 | 27.0 | 19.9 | 251 |

### Reading

1. The game is **render-bound**. The guest render scope fills 100 % of every
   frame. The game thread finishes its update in about 9 ms and then waits
   (coordinator) for render.
2. Inside a render frame, only about 13-17 ms builds the frame up to the swap.
   That part is the same with VSync on or off. **The rest, 17-31 ms, is spent
   after the swap.** Earlier profiling localized it to the guest polling the
   GPU command serial (`82411E98`). That explains the render thread's 99 % CPU:
   it spins while it waits.
3. That serial is written by the host GPU command processor. The busiest
   non-guest thread is most likely that processor, but this is not proven by
   name; the September profile showed the "GPU Commands" thread at 75 %. With
   VSync off it is **95 % busy**: about 30 ms of host CPU per 31 ms frame.
   With VSync on it is only 53 % busy, so it is blocked in presents.
4. Therefore:
   - VSync blocking in the host present path costs about 11-14 ms per frame
     (45 to 31 ms).
   - Behind that, the **host command processor's own CPU throughput, about
     24-30 ms per frame, is the real ceiling**. That is about 33-40 updates/s
     even without VSync.

### Fix candidates

| Option | Change | Expected effect | Size |
| --- | --- | --- | --- |
| (1) Decouple present from the command processor | Present on its own thread, or use a non-blocking waitable-swapchain present in the ReXGlue D3D12 presenter, so the processor never waits on VSync | about 24 to 31 updates/s with VSync still on | medium, SDK presenter |
| (2) Speed up the command processor | Profile where its ~25-30 ms/frame goes (Tracy is compiled in on-demand; or an ETW sampling profile) | needed for 60 FPS, which requires at most ~16 ms/frame, about 2x | large |
| (3) Render-thread spin | Not a cost, only a symptom of waiting | nothing on its own | none |

Recommended next step: **(1) first**. It is the cheapest measurable gain, about
+30 % updates/s without tearing, and with l15's raw timer that is real extra
smoothness. Run (2), an ETW/Tracy profile of the command-processor thread,
before any larger rewrite.
## Correction and fix: the ceiling was Windows timer resolution (l16)

### What the SDK actually does

The VSync reading above was too quick. In this SDK the host D3D12 `Present`
already does not wait for VSync. The `vsync` option controls the emulated
guest vblank:

- the "GPU VSync" thread marks vblanks at 60 Hz with VSync on, or 1 kHz with
  VSync off, and sleeps `Sleep(1 ms)` per loop;
- while a `WAIT_REG_MEM` (the swap-interval wait for the vblank count) is
  unmet, the command processor calls `rex::thread::Sleep(wait/0x100 ms)` with
  VSync on and only yields with VSync off.

Nothing in the SDK or MCLA calls `timeBeginPeriod`. The process therefore runs
at Windows 11's default timer resolution of about 15.6 ms, so each of those
sleeps can last up to a whole tick. Vblanks arrive in bursts and frames slip
to the next tick. That explains both the ~45 ms frames and the irregular
2/3-vblank cadence.

### Test

The interval1 control host (`control-hr`, run `timebox-d-vsyncon`) and the
stock interval2 host (`a-hr`, run `timebox-e-vsyncon`) were each relinked
with one static-initializer object that calls `timeBeginPeriod(1)`. Everything
else is the same: Arcade autostart, VSync on, full probes.

| Run | Render frame (med/p90) | Updates/s | Measured step sd | Mean change between successive steps | Fixed timer game/wall | Busiest non-guest thread |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| stock interval2, default resolution (A) | 45.5 / 61.6 ms | 22.3 | 25.8 ms | 15.9 ms | 0.743 | n/a |
| stock interval2, 1 ms (e) | **33.2 / 35.4 ms** | **29.5** | 4.3 ms | 3.3 ms | **0.983** | 68.5 % |
| interval1, 1 ms (d) | 33.1 / 35.2 ms | 29.6 | n/a | n/a | 0.984 | 65.2 % |

With 1 ms resolution the stock build reaches its 30 Hz cap (2 vblanks) in the
race. Even the stock fixed timer is then within 2 % of real time. The
recorded race steps would be smoothed by l14's window to 0.7 ms mean change;
l15 is smoother still. Race frames look normal, and the present path is
unchanged, so this cannot cause tearing.

### l16

`src/mcla_timer_resolution_win.cpp` (Windows only) calls `timeBeginPeriod(1)`

### What remains for 60 FPS

At 30 updates/s the guest render frame is about 14 ms building plus about
19 ms waiting for the GPU serial. The command-processor thread is 65-69 %
busy, about 22 ms per frame. 60 FPS needs interval1 and a command processor
under about 16 ms per frame, which is the profiling task in (2).

## Command-processor profiling (in progress)

### Tracy is not usable on Release builds

ReXGlue defines `REXGLUE_ENABLE_PROFILING`, and with it the Tracy zones, only
for non-Release configurations. Every MCLA build here is Release, so a Tracy
capture would be empty. A separate attempt to build the Tracy capture tool
failed anyway: clang rejected the MSVC `/MP` flag.

### Sampler

`RipSampler` (scratch, C#) suspends the thread named "GPU Commands" about
1,800 times a second, reads its instruction pointer and resumes it. Samples
are attributed to modules.

- **Waits:** samples in `ntdll` sleep/wait syscalls count as waiting.

#### Fix proposals (not implemented)

1. **Write tracking and allocations (group 1).**
   - **Re-protection:** coalesce guest page re-protection into fewer, larger
     `VirtualProtect` calls per frame.
   - **Transient memory:** pool the per-draw heap allocations and the per-frame
     D3D12 upload allocations, which the CreateAllocation/DestroyAllocation
     syscalls show being churned.
   - **Expected gain:** about 3-4 ms per frame.
   - **Callers:** memcpy is only a leaf here. Its callers (texture loads,
     shared-memory uploads, constant copies) need stack attribution first.
2. **Register write path (group 3).** Every register write calls
   `GetRegisterInfo`. A precomputed per-register flag or handler table would
   remove that lookup from the hot path. Expected gain: about 1.5-2 ms. It is
   small and isolated, and easy to A/B.
3. **Driver cost (group 2).** Fewer redundant state changes and resource
   creations. The upload pooling from (1) also lowers this group.

Even all three together likely bring the median to about 15-18 ms per frame,
borderline for 60 FPS. They clearly remove most of the 30 FPS misses (p95 31 ms
to roughly 22-24 ms).

**Recommended next step:** extend the sampler with stack unwinding
(`RtlVirtualUnwind`), so memcpy, `VirtualProtect` and heap calls are
attributed to their rexgpu callers. Then implement (2) as the first measurable
change and (1) after it.

#### Display-refresh idea (owner, for later)

Present a late frame on the next refresh of the real monitor (144/120 Hz),
not on the next emulated 60 Hz tick. A frame finished at 36 ms would then
appear at about 42 ms instead of 50. Pairs naturally with the raw timer.
#### Big hitches: GPU memory management, not command translation

The owner reported a few severe lags late in the session. No whole second
was saturated: per-second busy peaked at 87-91 %. The hitches are single
long stalls. Splitting the recording into continuous busy stretches (no wait
sample in between) gives:

- 48 stretches of at least 60 ms;
- 12 of at least 100 ms;
- the longest 336 ms, then 296, 208, 168, 166 and 161 ms.

Profile of all 48 stretches of at least 60 ms (8,433 samples):

| Activity | % of samples |
| --- | ---: |
| `D3DKMTWaitForSynchronizationObjectFromCpu` (CPU blocked until the GPU finishes) | 22.4 |
| `D3DKMTCreateAllocation` | 15.7 |
| `D3DKMTDestroyAllocation2` | 11.2 |
| NVIDIA driver | 8.2 |
| memcpy | 5.9 |
| `VirtualProtect` | 5.6 |
| everything else | each under 2.5 |

So the long stalls are caused by D3D12 resources being created and destroyed
during gameplay, with synchronous CPU waits on the GPU, typically before
destroying or reusing memory.

- **Single stall:** the one at 38 s is 80 % `DestroyAllocation2`.
- **Loading:** several of the longest stalls fall in the first ~30 s of the
  recording (it starts 20 s after launch) and are likely world loading.
- **Late in the session:** the heaviest seconds (222-257 s) show high load
  but no single stall over 100 ms. The owner's late "massive lags" may also
  involve render or GPU-side time this thread-only sampler does not see.

**Fix direction for the hitches:**

- keep and reuse D3D12 resources and upload memory (pools or placed resources
  in preallocated heaps) instead of creating and destroying them in play;
- defer destruction until the GPU fence has passed, without blocking the
  command processor.

**Which code creates them:** the next sampler step, stack unwinding, will
show the rexgpu caller of these allocations (texture cache, upload buffer
pool, render-target transfers, etc.).

Revised priority: this hitch fix first. It targets the worst felt lags. Then
the register table and write-tracking batching for the average frame cost.
The owner identifies the classic heavy lag. When a race or route starts, the
camera descends from the whole-game city map down to the player's car while
the city streams in. This lag has always been there. It fits the measured
pattern of D3D12 resource creation and destruction plus CPU-GPU waits during
streaming, and it is the primary target for the pooling fix.
**Owner priority:** the map-to-car lag happens once per game and is not a
priority. Gameplay hitches are.

**Gameplay-only re-analysis:** the first 35 s of the recording (loading) were
excluded, leaving about 258 s of driving.

- 31 continuous busy stalls of at least 60 ms, roughly one every 8 s; 4 of
  them at least 100 ms (296, 157, 123 and 108 ms).
- Their profile: `DestroyAllocation2` 20.0 %, CPU wait on GPU 15.6 %,
  `CreateAllocation` 10.4 %, NVIDIA driver 8.3 %, memcpy 5.6 %,
  `VirtualProtect` 4.5 %.

So in-game hitches have the same cause as the streaming lag: D3D12 resource
churn with synchronous GPU waits. Resource pooling and deferred destruction
remain the first fix, now justified by gameplay.
