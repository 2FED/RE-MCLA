# M8-001 60 FPS timebox: why the race clock runs slow in interval1

October 25, 2026. Code reading plus existing retained data only; nothing was
built or launched for this note.

## Short answer

MCLA advances game time by a **fixed 1/30 s per game update**, not by
measured wall time. Interval1 does not change that step. It only changes the
swap interval, and in our harness runs it produced *fewer* updates per second
than stock. Race clock speed is simply `updates per second / 30`:

- Oct 21 interval1 Arcade collection: 259 timer ticks in 12.0 s
  (21.5 ticks/s). Every tick added exactly 0.033333 s. The game's own timebase
  measured 12.08 s of real time, but game time advanced only 8.63 s: **0.72x**.
- Oct 18 stock/interval1/stock cohort: the HUD clock moved about 3.3 cs per
  published frame in **all three arms** (A1 442/134, B 343/104, A2 456/139).
  The per-frame step was the same; B just published fewer frames
  (about 18/s versus 23-24/s for stock).
- Even stock was below real time in those harness runs (about 0.78-0.80x),
  because it also stayed under 30 updates/s.

## The code

Timer tick `sub_821BDA90` (TU5, `generated/default/mcla_recomp.5.cpp`):

1. Reads the timebase (`mftb`), stores the raw tick difference times a
   constant as measured seconds in `+92`. A caller override `f1 >= 0` replaces
   it (`+100`/`+88`). Scaled copies go to `+96`, `+104` and `+8`.
2. `+56 != 0` (first tick after reset) branches to `0x821BDBC8`. That path
   uses `+32`, or `1/+28` when `+32` is zero, then clears `+56`.
   **This is the branch at `0x821BDB08` that Xenia's patch replaces.**
3. Normal path, fixed mode (`+58 != 0` or `+60 != 0`): the effective delta
   `+8 = +32 * scale(+84)`. The measured time is ignored. Accumulators
   `+20`/`+24` advance by that constant.
4. Normal path, raw mode (`+60 == 0`): the effective delta is the measured
   time. If a cap `+32` is configured, values above it are clamped to the cap,
   and values below it set `+52 = 1`.

Setters, both called from `sub_822D2478` (TU14):

- `sub_821BD9F8` (fixed): `+60 = 1` and `+32 = +8 = +88 = 1 / (F1 * R5)`.
  `F1 = cfg+84 / cfg+80`, `R5 = cfg+92`. It is chosen when `cfg+72 != 1`.
- `sub_821BD9B8` (raw): `+60 = 0`, optional cap. It is chosen when
  `cfg+72 == 1`.

The retained Oct 21 journal shows stock values `+28 = 30`,
`+32 = 0.0333333`, `+60 = 1` and scale 1.0. That is fixed30 mode.

Presentation selector `sub_824199B0` (TU27) maps the D3D device field
`+13596` to the swap interval: 0 or 1 give 1, 2 gives 2, 4 gives 3. Stock sets
`+13596 = 2`. The game is therefore designed as a 30 FPS lock: it swaps every
two vblanks and steps 1/30 s per frame. The interval1 candidate changes only
the literal for case 2, so the timer policy is untouched.

Xenia's "60 FPS Game Speed Fix" has two writes. It patches the interval
(`0x82419AA3`) **and** replaces the `+56` check at `0x821BDB08` with a jump
to the epilogue. The jump makes every tick use the raw measured delta, but it
also skips fixed/raw mode selection, the `+20/+24` history and the reset
handling. That fits the owner's earlier report of an accelerated splash and
turning jerk with that branch.

## Hypothesis

H1 (supported by the data above): the slow race clock in interval1 comes
from **fewer game updates per second at a fixed 1/30 s step**, not from a
wrong delta.

H2 (open): why interval1 yields fewer updates than interval2 on this host.
Candidates:

- a host present/VSync wait that happens on every swap instead of every
  other one;
- the game's GPU-completion spin (`82411E98`) aligning badly with
  single-vblank swaps;
- capture overhead.

H2 matters for frame rate, but not for correct speed.

Consequence: "60 FPS" needs two independent things:

- time that follows the wall clock at any update rate;
- a higher update rate.

Patching the interval alone can only make speed worse whenever the update
rate stays below 60.

The cleanest time fix uses the game's own raw mode, `cfg+72 == 1`. It goes
through `sub_821BD9B8` and keeps the reset and history handling, unlike the
Xenia jump. Raw deltas are still clamped to about 0.0001..0.1 s per tick. The
Oct 21 stock-config/raw/stock-config cohort on the interval1 host already
leaned this way: raw rose by 1.30x and 1.10x, against about 1.39x expected
from 0.72x. It was inconclusive only because control drift was 1.19.

## Proposed measurement (aggregate counters, no new mega-diagnostics)

Use the existing Arcade autostart with the timer observer, on disposable save
copies, one run per arm:

- A: stock interval2 (selector literal back to 2), fixed timer.
- B: interval1 with raw mode forced: `cfg+72 == 1` path at `0x822D2478`, cap
  0.

Read `timer-calls.json` only: ticks/s, the sum of `+8`, the sum of `+92`,
and game/wall = sum(+8) / window.

Predictions:

- A: every `+8` is 0.033333 and game/wall equals ticks/s / 30.
- B: `+8` tracks `+92` and game/wall is 0.95..1.05 at whatever ticks/s it
  reaches.

If B holds, the speed bug is understood and fixed by policy. Frame rate (H2)
then becomes its own investigation.

### What this shows

1. **Raw mode fixes speed.**
   - With the game's own raw policy, game time equals real time (12.003 s of
     12.003 s).
   - Every tick uses the measured interval.
   - No tick hit the 0.1 s upper clamp or the 0.0001 s lower clamp.
2. **The update rate on this PC is about 24/s regardless of interval.**
   - Stock interval2 and interval1 both land at 24-25 ticks/s with the same
     rebuilt objects.
   - Interval1 did not reduce the update rate here.
   - The Oct 18 "slower in interval1" HUD result is therefore not explained by
     interval-dependent update rate in this setup. The likely suspects are
     that cohort's different host build and its capture load.
   - The robust finding is that **both modes run about 19% slow under fixed
     1/30 steps**, because the harness host never reaches 30 updates/s.
   - The swap-binding probe alone costs about 9% (22.3 versus 24.5 ticks/s).
3. **Frame rate is the separate problem.** Earlier localization pointed at the
   guest's GPU-completion spin (`82411E98`). 60 FPS needs that throughput fixed
   in addition to raw time.

## Normal-play candidate l13

New `src/mcla_raw_timer.cpp` adds `mcla_raw_timer`.

- **Default:** ON. The CMake option `MCLA_RAW_TIMER_DEFAULT_ON=OFF` builds a
  fixed-default variant.
- **What it does:** it overrides `sub_822D2478` and applies the same two-word
  edit as the diagnostic experiment (`+88` 30 to 0, `+72` 0 to 1). It does so
  only when the configuration matches the exact stock fixed30 values, then runs
  the original body. It logs the chosen mode.
- **Conflict guard:** CMake leaves it out when `MCLA_TIMER_CONFIG_PROBE` owns
  the same function.

## Owner play-test of l13 and the judder fix (l14)

### Owner report (2026-10-25)

| Build | Race timer | Driving and motion |
| --- | --- | --- |
| l12, l13-fixed | slow: about 15 s of game per 20 s real (0.75x) | not reported |
| l13 | correct | car animation jerky, motion blur inconsistent |

The 0.75x figure matches the measured 0.74-0.82x. Cutscenes and traffic
speed were fine in l13.

### Cause

Each update takes 2 or 3 vblanks (33/50 ms), irregularly and sometimes 4.

| Run | 2 vblanks | 3 vblanks | 4+ vblanks | Mean change between successive measured steps |
| --- | ---: | ---: | ---: | ---: |
| A lean (fixed) | 128 | 151 | 12 | 10.8 ms |
| B lean (raw) | 146 | 131 | 21 | 10.7 ms |

- **Fixed mode:** each step is a constant 33 ms. Motion is smooth but slow.
- **Raw mode:** each update applies the previous interval as its step, so
  per-frame motion and motion blur jump by up to +-25 %. That is the judder
  the owner saw.

### Fix candidate l14

Same source as l13 plus `sub_821BDA90` step smoothing.

- **What it changes:** for the main timer object `0x827D7500`, in raw mode and
  outside reset ticks, the step is measured from the timebase. The average of
  the last 8 steps, plus a quarter of the accumulated difference (clamped to
  +-25 % of the average), is passed as the tick's own caller-supplied step
  (`f1`).
- **What stays the game's:** the scale, clamps and history in the raw path.
- **Hitches:** steps above 0.1 s pass through unchanged and reset the average.
- **Switches:** `mcla_raw_timer_smoothing` (default ON) and
  `mcla_raw_timer_stats` (log every 300 updates).

### Measurement

The same l14 binary ran 75 s on a disposable seed with stats on. l14 is a
normal player build with no internal autostart, so both runs stayed on the
PRESS START screen. These rows measure title-screen updates, not driving:

| Smoothing | Measured step mean | Change between successive steps, measured | Change between successive steps, applied | Applied vs measured total time |
| --- | ---: | ---: | ---: | --- |
| off (equals l13) | 41.6-58.1 ms | 14.9-22.5 ms | 14.9-22.5 ms | identical |
| on (l14) | 39.9-56.6 ms | 14.3-22.3 ms | 3.3-11.5 ms | within 0.2 % |

The first 300-update window includes startup hitches. Later windows show about
4x steadier per-frame steps while total game time still follows real time.

Driving feel under l14 has not been checked. It needs an owner play-test.
Display cadence stays 2-3 vblanks, so some frame pacing judder can remain.

### In-race replay of the smoother

The Arcade autostart exists only in the diagnostic host, and that host already
overrides the timer tick. To get driving data, the exact l14 `StepSmoother`
algorithm was replayed offline on the per-update steps recorded during
today's in-race runs (`timer-calls.json`). The replay script is
`scratch replay_smoother.py`. It assumes smoothing does not change the
host's update cadence.

| Run (in race) | Steps | Mean change between successive steps: measured -> smoothed | Largest change: measured -> smoothed | Smoothed vs measured game time |
| --- | ---: | --- | --- | --- |
| B lean (raw mode) | 298 | 10.7 -> 2.5 ms | 34.5 -> 9.6 ms | at most 42.5 ms apart, ends 2.7 ms apart over 12.0 s |
| A lean (fixed mode, as data source) | 292 | 10.8 -> 3.6 ms | 203.3 -> 203.3 ms (a 226 ms hitch passes through) | at most 37.9 ms apart |

So in driving cadence, l14 makes per-frame steps about 3-4x steadier while game
time stays within a few hundredths of a second of real time. Visual judder
and blur still need the owner's play-test.
