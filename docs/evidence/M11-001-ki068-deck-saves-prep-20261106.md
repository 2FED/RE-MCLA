# KI-068 prep: Deck saves fail under Proton ("storage device was removed")

Read-only preparation by an Opus subagent on 2026-11-06 (SDK v0.20.0.8 content layer, earlier Deck logs, the owner's 100% repro); accepted by the primary agent as the working hypothesis for M11-001.

Read-only analysis, 2026-11-06. SDK source: v0.20.0.8 (`c63895c`, the l67 SDK worktree), which is the SDK in l70.
Owner repro (100%): the 1st save in a session succeeds, the 2nd and later fail with the dialog;
"CHANGE STORAGE DEVICE" makes the next save succeed, and the one after it fails again.

## 0. Bottom line

The leading hypothesis (about 75%) is a **ghost host handle plus Wine's deferred delete**.

1. Save #1 leaves a host Win32 handle open on `...\00000001\mc4.sav\mc4.sav`. The SDK's own commit
   `24cc2fe` "FILE_SHARE_DELETE ... for the dumb NTFS issues with ghost handles" shows such handles
   are known. The handle stays open after XamContentClose because `CloseOpenedFilesFromContent` only
   calls `XObject::ReleaseHandle()` once. That decrements `handles_[0]`'s handle_ref_count. If the
   XFile is still referenced, the `HostPathFile` and its `CreateFileW` handle survive. Ways it can
   stay referenced: a second handle or ref, a pending async I/O or completion port, or the game itself
   still holding the handle.
2. Save #2 runs the overwrite path:
   `XamContentCreate*` -> `BeginContentTransaction` -> `DeleteContent` -> `std::filesystem::remove_all(package)`.
   The backup copy in Begin works, because the ghost was opened with share R|W|D.
   - MSVC STL `remove` = `SetFileInformationByHandle(FileDispositionInfoEx, DELETE|POSIX_SEMANTICS)`.
   - **Windows (NTFS, Win10 1709+):** POSIX delete unlinks the name at once even while other handles
     that share delete are open. The directory is then empty, `RemoveDirectory` succeeds and the save
     is recreated. This is why Windows users never see the bug.
   - **Wine/Proton:** POSIX semantics are not implemented. Wine source, as recalled, has a FIXME and
     treats the flag as delete-on-close; the log must confirm this. The file stays in the directory as
     delete-pending until the ghost closes. `RemoveDirectory` of the package then fails with
     ERROR_DIR_NOT_EMPTY (145), so `delete-existing` fails with X_ERROR_ACCESS_DENIED. The rollback's
     Recover hits the same 145, and the game shows "storage device removed".
3. "CHANGE STORAGE DEVICE" -> `XamShowDeviceSelectorUI` (headless, returns device 1) -> the game drops
   or re-mounts its storage state. This closes the old handles: the ghost closes and Wine finally
   unlinks the file. The game then re-enumerates: `XamContentCreateEnumerator` -> `ListContent` ->
   `RecoverContentTransactions`. That restores the package from `.rexbackup` and clears the marker.
   The next save runs on a clean tree, succeeds and leaves a new ghost, so the save after it fails
   again. This matches the alternation exactly.

Prediction: the same bug would appear on Windows on a volume without POSIX delete (FAT32/exFAT, for
example a USB stick) or on Windows before 1709.

Hypotheses (a) and (e) are **eliminated by the code** (section 2).

## 1. Call chain: game save to host operations

The guest is MCLA. It imports XamContentGetDeviceData/State, XamContentCreateEnumerator,
XamContentCreateEx, XamContentClose, NtCreateFile, NtWriteFile and NtSetInformationFile (M5-011).

### Device selection and state: no host access at all

- `XamShowDeviceSelectorUI` returns device id 1 (dummy HDD). It fails only with DISK_FULL, when
  `total_requested > xam_hdd_free_bytes` (a cvar, default 3 GiB; 0 means "full").
- `XamContentGetDeviceState/Data/Name` and `XamContentCreateDeviceEnumerator` read a constant table
  (HDD id 1, ODD id 2). They return DEVICE_NOT_CONNECTED (0x48f) only for any other id, and log
  `[content] XamContentGetDeviceState failed: device_id=0x.. result=0x48f`.
- `NtQueryVolumeInformationFile` (size, attributes, volume) on `\Device\Content\N` returns constants
  (128K units x 512 B, serial 0). There is no GetDiskFreeSpaceEx or volume query anywhere.
- `XamContentGetDeviceSerialNumber`, `GetDeviceVolumePath` and `GetDefaultDevice` are
  REX_EXPORT_STUB on every platform.

### Opening the save: `xeXamContentCreate` (Create, CreateEx, CreateInternal)

Any failure in this function logs:

`[content] XamContentCreateEx failed: stage=<S> flags=0x.. root='..' content='mc4.sav' type=00000001 result=0x.. hresult=0x.. probe=0|1`

| Step | Host operation | Stage name / extra line |
|---|---|---|
| disposition | CREATE_ALWAYS (2) first calls `CloseContent(root)`. All dispositions call `ContentExists`, which runs `RecoverContentTransaction` (acts only if a `.rexpending` marker exists) and then `fs::exists(package)` | `disposition`; probe=1 for 0xb7 on CREATE_NEW or 0x3 on OPEN/TRUNCATE |
| capacity (saved game, Create) | cvar compare only | `capacity`, result 0x70 |
| `BeginContentTransaction` | Recover. Then `remove_all(pkg.rexbackup)` and `remove(hdr.rexbackup)` (errors ignored). Then `fs::copy(pkg -> pkg.rexbackup, recursive)` (CopyFile2) and `copy_file(hdr -> hdr.rexbackup)`. Then `create_directories(Headers\00000001)` and `CreateFileW(hdr.header.rexpending, share 0, CREATE_ALWAYS)` | `begin-transaction`, plus `[content] Begin failed: stage=recover\|already-active(0xaa)\|backup-package\|backup-header\|create-marker-directory\|create-marker ... win32=N (text)` |
| delete-existing (CREATE_ALWAYS on an existing save, or TRUNCATE) | `DeleteContent`: refuses if a package with the same data is mounted (`content-open`); then `remove_all(package dir)` and `remove(header)` | `delete-existing`, plus `[content] DeleteContent failed: stage=content-open\|remove-package ... win32=N` |
| create-package | `fs::exists(pkg)` (package-exists, 0xb7), then `create_directories(pkg)`. Mounts `HostPathDevice("\Device\Content\N", pkg, allow_share_delete=true)` and the symlink `root:` | `create-package`, plus `CreateContent failed: stage=package-exists\|create-directory` |
| write-header | `CreateEmptyFile(hdr)` (share 0), then `_wfopen_s(hdr,"wb")` (exclusive), then fwrite/fclose | `write-header`, plus `WriteHeader failed: stage=create-directory\|open\|write` |
| open-package (Open disposition) | mounts the existing package and reads the license from the header | `open-package` |
| on failure after Begin | `RollbackContentTransaction` -> Recover: `remove_all(pkg)`, `remove(hdr)`, copy the backups back, remove the marker and backups | `Recover failed: stage=remove-package\|remove-header\|restore-package\|restore-header\|remove-marker\|remove-package-backup\|remove-header-backup`, `Rollback failed: stage=recover`, `XamContentCreateEx rollback failed after stage=<S> ... rollback=0x..` |

### Writing inside `save:` (`\Device\Content\N`)

- **`NtCreateFile`** goes through `VirtualFileSystem::OpenFile`:
  - OVERWRITE and OVERWRITE_IF: `Entry::Delete` (`fs::remove`), or `Truncate` (`_wfopen_s "wb"`) if
    the delete fails.
  - Then `CreatePath` -> `CreateEntryInternal` (`_wfopen_s "wb"`) -> `HostPathEntry::Open` ->
    `CreateFileW(OPEN_EXISTING, share R|W|D, BACKUP_SEMANTICS)`.
  - SUPERSEDE: delete, then create.
  - Failure lines:
    - `[NtCreateFile] FAILED: path='..' -> 0x..` (always WARN)
    - `[content] content file open failed: path= access= status=0xc000000f win32=N`
    - `content file create failed: parent= name= error=N`
    - `content directory create failed`
- **`NtWriteFile`** calls `WriteFile` with the offset in an OVERLAPPED. Failure lines:
  `content file write failed: ... win32=N` and `NtWriteFile failed on content file: path= length= status=`.
- **`NtSetInformationFile`**:
  - EndOfFile (class 20) and Allocation (class 19): `SetFilePointerEx` + `SetEndOfFile`.
  - Rename (class 10): `std::filesystem::rename` (MoveFileEx REPLACE_EXISTING).
  - Disposition (class 13): sets only the guest delete-on-close flag (WARN `NtSetInformationFile set deleting flag`).
  - Failure lines: `NtSetInformationFile failed on content file: path= class=N status=0x..` and
    `content file set-length failed`. A rename failure also logs `RenameEntryInternal: failed to rename`;
    that line contains host paths.

### Closing the save: `XamContentClose`

1. `CloseContent` -> `DetachPackage` -> `CloseOpenedFilesFromContent`. This calls `ReleaseHandle`
   once per XFile under `root:`. It does NOT close the host handle if the XFile is still referenced.
2. The ContentPackage is deleted, which unregisters the device.
3. `CommitContentTransaction`: `remove(marker)`, `remove_all(pkg.rexbackup)`, `remove(hdr.rexbackup)`.

Failure lines: `Commit failed: stage=remove-marker|remove-package-backup|remove-header-backup`, then
`XamContentClose failed: root='..' result=0x.. hresult=0x..`.

The game shows "storage device removed" when one of these calls returns a failure. The SDK sends no
device-change notification. The calls are:
- XamContentCreate* (any stage);
- NtCreateFile, NtWriteFile or NtSetInformationFile on `save:`;
- XamContentClose;
- in theory, a device query with an id other than 1 or 2.

## 2. Ranked hypotheses (re-ranked with the owner's 1st-OK / 2nd-fails / reselect-resets pattern)

Save #1 in a session **also** overwrites an existing package, because mc4.sav exists from earlier
sessions. So the overwrite path itself works under Wine on a clean tree. What differs at save #2 is
**state left by save #1 inside this process**. Persistent filesystem properties are therefore ruled
out: permissions, case, path length, reparse ancestors and Wine volume queries would make save #1
fail too.

exist in l66. If the l70 session shows the rank 1 lines but no later "Recover restored" line, look at

## 5. Fixes per hypothesis

### Ranks 1, 1b and 1c (ghost handle)

- **Primary fix (SDK, low to medium risk).** On content unmount (`DetachPackage`), actually close the
  host handles of every XFile whose entry belongs to that package device, whatever the
  handle_ref_count. For example, add `HostPathFile::CloseHost()` to drop the `FileHandle`; later I/O on
  that file returns `X_STATUS_FILE_CLOSED`. This matches the console, where content unmount
  invalidates those handles.
  - Risk: a guest that keeps using a stale save handle now gets an error instead of silently writing
    a deleted file. This needs the PC save/load regression run and the M5 content tests.
- **Defence in depth (SDK, low risk, changes behaviour only on Wine).** In the `remove_all` of
  `DeleteContent` and Recover: when the directory removal fails with 145 or 5, rename each remaining
  delete-pending or open file to a unique `*.rexdead-N` name in the package root's parent directory,
  then retry the directory removal. Wine allows renaming a file whose handles all share delete. Sweep
  the `*.rexdead-*` files at the next enumeration.
- **Alternative.** For a CREATE_ALWAYS recreate, keep the package directory and truncate the files in
  place instead of calling `remove_all`: open with share R|W|D, then SetEndOfFile 0. For the game this
  has the same effect as Windows POSIX delete.
  - Risk: stale extra files must still be removed.
- **Diagnostic for l71, if l70 is ambiguous.** At `CloseContent`, count the XFiles under the package
  that are still alive after `ReleaseHandle` and log
  `[content] close left N host handle(s) open: content='mc4.sav'`.

### Rank 2 (transaction state)

When `CreateContent` or `OpenContent` finds the same root still mounted, close (commit) the old mount
first for every disposition, as CREATE_ALWAYS already does. Medium risk (it changes semantics); the M5
content tests cover it.

### Rank 3 (rename over an open file)

Implement the rename as `SetFileInformationByHandle(FileRenameInfo, ReplaceIfExists)` on the
already-open handle. If that fails, fall back to moving the target aside, renaming, then deleting the
moved-aside target. Low risk.

### Rank 4 (commit side)

Make Commit's backup removal tolerant: log the failure and leave the cleanup to the next Begin, which
already removes stale backups, instead of returning ACCESS_DENIED to XamContentClose. Low risk: the
marker is already removed, so the save is committed.

### (a), (c), (d), (e), (f)

The code justifies no change. (a) and (e) do not depend on the host.

### Owner workaround until fixed

After each successful save, choose CHANGE STORAGE DEVICE once (or restart the game) before the next
save.
