## 2. Livery in the frames

- **720p (scale 1): clean.** The two-tone split is correct (black nose and rear, light doors
  and roof). The city seal, "POLICE", "19350" and the "to protect and to serve" motto are
  crisp. The door and roof paint has no foreign streaks, no blue and no tick marks. The grid
  in the rear window is the prisoner partition, part of the model.
- **1080p (scale 2, guest 960x540): clean in both frames.** The result is the same from the
  rear and from the side: no blue or black column streaks, decals in place.
- The light door panels look darker and bluer in these frames (mean RGB about 20-50) than the
  clean patches of the 1440p frame (about 80-100). Lighting, camera angle and environment
  reflection all differ, and the black panels stay about ten times darker than the doors. This
  is most likely lighting, not a paint defect (low confidence; check it on a same-angle repeat).
- For contrast, the 1440p frame `29760-1`, converted the same way, shows dense blue/black
  column streaks across the doors, rear quarter and front fender.

**Verdict:** the 720p frame does **not** show the KI-047 defect. The defect is therefore
**not shown to be scale-independent**, and the scaled-readback shift hypothesis (H1 in
part 1) is **not eliminated**: a clean 720p is what H1 predicted. The owner's "looks about
the same at both" matches the frames if it means that 1080p and 720p look the same as each
other (both normal). Confirm the wording with the owner.

New fact from 1080p: a scale-2 session with a 960x540 guest mode was also clean. In this
sample, "draw scale > 1" alone is not enough to cause the defect. So far it has been seen
only with the 1280x720 guest mode at scale 2 or 3. There is one session per configuration,
at different locations and with different car instances. The defect content depends on what
was composited earlier (part 1), so one clean session is weaker evidence than one broken
session.

## 4. A/B command (stale `some` readback versus `full`)

The launcher does not record its command line. It was reconstructed from `Start()` in
`src/mcla_launcher_controller_win.cpp` (the args vector) and the 720p session receipts.
Every flag was checked against a cvar definition. In the SDK (the `private/l48-src` clean
clone at `daa1ae5`): `game_data_root`, `user_data_root`, `cache_root`, `metadata_root`,
`update_data_root`, `log_file`, `local_user_display_name`, `d3d12_adapter`,
`resolution_scale`, `draw_resolution_scale_x/y`, `vsync`, `fullscreen`, `gpu_backend`,
`xam_user_signin_state`, `input_backend`, `mnk_mode`, `video_mode_*`,
`mcla_guest_vblank_hz` and `readback_resolve` (allowed values `none|fast|some|full`). In the
host's `mcla_app.cpp`: `mcla_diagnostics_root`, `mcla_managed_launch_config`,
`mcla_diagnostics_enabled` and `mcla_crash_reporter_dialog`. The host keeps an explicit
`readback_resolve` value (`HasNonDefaultValue` skips its `some` default), and the D3D12 path
uses it in preference to the legacy `d3d12_readback_resolve` flag.

There are two scripts under `<repo>/private/`: `ki047-readback-full-720p.cmd` and
`ki047-readback-some-720p.cmd`. They are identical except for the mode. Each one runs:

```
"<repo>\private\l49-volunteer\build\mcla.exe"
  "--game_data_root=<repo>\private\p1\game"
  "--user_data_root=<profile>\user"
  "--cache_root=<profile>\cache\2E4BB9F3BC7B222ED27A3FE99FB54E487CEFE2F61198ED4520FEA4627DEC050E"
  "--metadata_root=<profile>\metadata"
  "--update_data_root=<profile>\metadata\update"
  "--log_file=<run>\mcla.log"
  "--mcla_diagnostics_root=<run>\diagnostics"
  "--mcla_managed_launch_config=<run>\managed.toml"
  "--local_user_display_name=<profile display name, default User>"
  --d3d12_adapter=1 --resolution_scale=1 --draw_resolution_scale_x=1 --draw_resolution_scale_y=1
  --vsync=true --fullscreen=false --gpu_backend=d3d12 --xam_user_signin_state=1
  --input_backend=sdl --mnk_mode=false --video_mode_width=1280 --video_mode_height=720
  --video_mode_refresh_rate=60 --mcla_diagnostics_enabled=true --mcla_crash_reporter_dialog=true
  --mcla_guest_vblank_hz=240 --readback_resolve=full      (or =some)
```

`<profile>` is the MAIN profile root. `<run>` is a new
`<repo>\private\ki047-ab\<UTC>-720p-<mode>` folder. `--d3d12_adapter=1` is included because
the launcher passed it (receipt `adapter 1`).

These are the deliberate differences from a launcher session:

- The log, the diagnostics (F10 packages) and the sentinel config go to the run folder, not
  to new `sessions/` and `diagnostics/` entries. The sentinel is a byte copy of the session's
  55-byte file, which the host requires.
- The working directory is the run folder.
- Inherited `REX_*` variables are cleared, but the rest of the environment is inherited
  rather than allowlisted.

The scripts check that the staged exe, game root, profile tree, build cache and sentinel
exist, and refuse to run while `mcla.exe` or `MCLA-Launcher.exe` is running. No launcher
session receipt covers this run, so the scripts copy the MAIN user tree to
`<run>\user-before` before the run and to `<run>\user-after` after it. They print the full
command and also store it in `<run>\command.txt`.

### Value of the 720p A/B, and the better arm

720p is already clean with the default `some`. The 720p pair can therefore only give "both
clean" (no information) or "`full` broken" (a surprise that points at a new path). The
decisive no-build test is the same pair at **1440p**, where the defect reproduces. Its
arguments differ only in `--resolution_scale=2 --draw_resolution_scale_x=2
--draw_resolution_scale_y=2` (the guest mode stays 1280x720) and in the sentinel source
(`sessions/7d57f31c.../managed.toml`, same bytes). In this SDK, `full` goes through the same
`IssueCopy_ReadbackResolvePath` copy (same `written_address`, same scaled downscale). It only
removes the one-frame delay and the copy-every-4th-resolve sparsity. So:

- **1440p: `full` clean, `some` broken.** The delayed and sparse `some` readback is the cause
  at scale > 1. Decide between forcing a synchronous (`full`-style) copy for the vinyl/livery
  composite (cost: stalls, measurable with the existing readback-cost probe) and fixing the
  staleness itself (wait on the read slot's fence; refresh on every resolve whose
  address/length key gets new content). The clean 720p and 1080p results would then still
  need an explanation of why the stale slot only bites with the 1280x720 guest mode at 2x
  or 3x.
- **1440p: `full` broken.** Staleness is not the cause. H1 (the shifted origin of the scaled
  readback copy) stays first. Next, build the existing proposal
  (`docs/evidence/M9-006-ki-038-readback-proposal-20261029.diff`) and repeat at 1440p. Or
  first log the resolve at the vinyl composite (`copy_dest_base`, `copy_dest_extent_start`,
  `written_address`, length, scale) to confirm the offset directly.
- **720p: `full` broken (if the 720p pair is run anyway).** The cause is game-side or another
  path. The next step is the resolve log at the vinyl composite.

## Unresolved risks

- There is one session per configuration. The defect content depends on what was composited
  earlier, so a single clean session does not prove the defect is absent.
- The l49 SDK pin was not confirmed to be the same as the `daa1ae5` clone used for the cvar
  check. The cvar names have not changed for several drops.
- The launcher command line is reconstructed from the worktree source; the launcher does not
  record it. The receipts and the log agree with it (paths, adapter, scale, guest mode,
  vblank 240).
- A direct run bypasses the launcher's profile lock and session receipts. The scripts' save
  copies and process checks stand in for them. As in any launcher session, the game will
  autosave into MAIN.
