### A. Counters (always on, no behaviour change)

These fields are added to the end of every `MCLA_READBACK v=1` minute and mark line
(`FormatReadbackFencedFields`). They are reset with the minute.

| Field | Meaning |
|---|---|
| `fenced` | `d3d12_readback_fenced_delivery` now |
| `cad_copies` | Some-mode cadence copies that are due: the every-4th guest copy from the previous slot. Not a miss, not forced, not a steady fast copy, not elided |
| `cad_unfenced`, `cad_unfenced_bytes` | Cadence copies whose previous slot was written but whose submission had not completed at the polled fence. **This is the discriminator.** The poll is `GetCompletedValue` only and runs only when a cadence copy may be due; it never submits or waits |
| `cad_unf_depth/f36/k8/other` | `cad_unfenced` split by family: depth source; colour as k_32_FLOAT (36, luminance chain); k_8 (2); other |
| `cad_unwritten` | Cadence copies whose previous slot holds no recorded copy |
| `cad_unfenced_served` | Guest copies actually made from an unfenced slot. Off arm: about `cad_unfenced`. Fenced arm: 0 |
| `cad_deferred`, `cad_already` | Fenced arm only. `cad_deferred`: cadence copies not made. `cad_already`: complete cadence copies skipped because that copy was already in guest memory |
| `done_delivered`, `done_bytes`, `done_superseded`, `done_already`, `done_dropped`, `done_overflow`, `done_lat_ms_max`, `done_lat_frames_max`, `done_fifo` | The completion FIFO (below): entries delivered, superseded by a newer copy, already delivered (by the CP cadence or an ensure call), dropped (BeginResolve / Erase / Clear), removed by the 8192 cap; worst latency from record to delivery; depth now |
| `fence_before_data` | Deferred guest fence stores (queued, or immediate in the deferred mode) made while a tracked recorded copy of a non-exempt key, in the same or an earlier submission, was not yet in guest memory. Off arm: expected high. Fenced arm: must be 0 |
| `lead2_frames` | Frame ends where `cp_lead_frames >= 2` |

The completion FIFO runs in both arms. Every recorded copy of a non-exempt key that stays pending
after its resolve is tracked as {submission, key, generation}. The FIFO is ordered by submission.
In the off arm it is used only for counting: stale entries are pruned at fence stores and once per
frame end. The exempt key 039CA000 is not tracked; its delivery is the steady fast path, which the
steady counters already measure.

Not done: the design's diag2 field `prev_polled=` and `guest_regress`. A guest-memory regression is
prevented by construction (only the key's newest pending copy can be delivered), and the model test
asserts it.

### B. Fix: `d3d12_readback_fenced_delivery`

- Type: bool, default false, GPU/D3D12, hot reload (same as its neighbours).
- Scope: readback_resolve `some` only. Fast mode is not covered; MCLA does not use it.

1. **Plan.** `ReadbackPlanInput::fenced_cadence` and `previous_polled`. A cadence copy whose previous
   slot is not `kComplete` is not made (`cadence_deferred`). The cadence restarts exactly as if the
   copy had been made: `next_resolves_since_copy = 0`, and the same `record_gpu` / elision result.
   Miss, forced, full, guard and steady fast paths are unchanged.
2. **Delivery.** `ReadbackPendingTable::DeliverCompleted(completed)` delivers every live FIFO entry
   with submission <= completed, in order. It copies under the table lock, delivers only the key's
   newest pending copy, and never waits. It runs on the CP thread at these points, each guarded by
   "completed advanced":
   - in `FlushDeferredFenceWrites`, before the store loop, when the queue head is due;
   - in `DeferGuestFenceWrite`, before an immediate store;
   - in `CheckSubmissionFence`, after every fence observation.
   The memcpy time goes into `memcpy_ms` and the bytes into `bytes_cpu_copied` and the perf-split
   read-back bytes, so the A/B costs stay comparable.
3. **Complete cadence copy.** When the cadence finds a complete previous slot, it copies through
   `DeliverSlotIfPending`. If DeliverCompleted or an ensure call already delivered that copy, it is
   not copied again (`cad_already`, counted as `copies_deferred`).
4. **Deferral re-track.** A deferred cadence copy is re-tracked (sorted insert). This covers a copy
   recorded while its key was exempt.
5. **BeginResolve.** With the cvar on, a resolve that neither records nor reallocates its slot does
   not drop the pending copy in that slot. The slot is not touched, so a deferred copy that is
   waiting for its fence stays deliverable. Without this, a GPU lag of 2 or more resolves of a key
   would drop every deferred copy. Off: BeginResolve is called exactly as on c40db4b.
6. **Drops.** BeginResolve (slot rewritten), Erase (eviction) and Clear (setup, device loss,
   shutdown) drop queued entries. Clear also empties the FIFO. A live entry must match both
   generation and submission, so a key that is evicted and created again (its generations restart)
   never delivers its new copy early.

Off arm: the plan is bit-for-bit the c40db4b plan. The guest copies are the same calls with the same
bytes. The only additions are the polled `GetCompletedValue` when a cadence copy may be due, the
FIFO bookkeeping under the existing table lock, and the new line fields.

Behaviour note for the fenced arm: every tracked non-exempt recorded copy is delivered at completion.
With `d3d12_readback_elide_unread=true` (every owner arm) the only recorded copies are the ones the
cadence would read, so the memcpy volume stays about the same. With elision off it would be up to
4x the cadence copies.

## 2. Tests (SDK ctest, tags `[readback-fenced]`)

New test cases: 11 (`readback_slots_test` 4, `readback_pending_test` 5,
`deferred_fence_writes_test` 2).

- `readback_slots_test`:
  - With the cvar off, the plan equals a verbatim copy of the c40db4b planner for every combination
    of mode, state, flags and polled class (36864 cases). The `cadence` flag is exact.
  - With the cvar on:
    - no some-mode copy reads a previous slot that is not complete;
    - deferral equals the copy in `next_resolves_since_copy`, `record_gpu`, `read_index` and
      `write_index`;
    - every other path is unchanged (480 deferred cases).
  - A steady-key sequence.
  - Counter and family tests.
- `readback_pending_test`:
  - in-order prefix delivery, newest generation only, superseded, latency;
  - skip after a CP cadence or ensure delivery (`already`);
  - BeginResolve / Erase / Clear drops, and a recreated key with the same generation;
  - sorted late insert, no duplicate tracking, `delivered_own` not tracked, the 8192 cap;
  - the field format.
- `deferred_fence_writes_test`:
  - A model of the CP order of operations, 60 seeds x 6000 steps, a slow and a fast GPU: random
    resolves of 4 per-frame keys (some mode, elision on), fences, submission ends, GPU completion
    and flush points.
  - Fence store sequences are identical in both arms, so there are no waits, no submissions and no
    reordering.
  - Fenced arm: 0 reads of an incomplete slot, `fence_before_data` 0, 0 newest-copy-after-fence
    violations, 0 guest regressions.
  - Off arm: more than 100 unfenced reads and more than 100 `fence_before_data`.
  - Second case: nothing is delivered before completion; at completion the copies land before the
    fence.

  `private/l88-sdk-o`. Release build OK.
- Warnings: the normalized warning set equals l82's (219 lines, diff empty); raw `d3d12/command_processor.cpp`
  warnings 8 = l82.
- ctest: **100% passed, 0 failed of 2210 (2206 passed + 4 skipped BitStream; l82: 2195 + 4; +11
  new).** The run after install was the same.
