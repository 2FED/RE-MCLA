Implementation by an Opus subagent on 2026-10-31 from the

## 1. KI-050: Steam Deck controls not reaching the game through the launcher

**Cause (analysis, about 85%).** SDL 3.5 ignores the Steam Virtual Gamepad (28DE:11FF) unless
`SDL_GAMECONTROLLER_ALLOW_STEAM_VIRTUAL_GAMEPAD` is set. The launcher started `mcla.exe` with a
minimal environment that dropped this variable.

**Change.**
- `src/mcla_launcher_process_win.{h,cpp}`: there is a new bounded list, `kProtonPassThrough`
  (exposed as `ProtonPassThroughNames()`), with `SDL_GAMECONTROLLER_ALLOW_STEAM_VIRTUAL_GAMEPAD`,
  `SDL_GAMECONTROLLERCONFIG`, `SDL_GAMECONTROLLER_IGNORE_DEVICES`,
  `SDL_GAMECONTROLLER_IGNORE_DEVICES_EXCEPT`, `SteamVirtualGamepadInfo`, `SteamAppId`,
  `SteamGameId`, `SteamDeck`, `STEAM_COMPAT_DATA_PATH` and `WINEPREFIX`.
  `MakeOwnedEnvironment(..., under_wine, passed_through*)` keeps these names only when
  `under_wine` is true. It uses the same rules as the existing directory variables:
  - name match ignores case and the canonical spelling is written;
  - a duplicate name or an embedded NUL is rejected;
  - an empty value is left out;
  - the whole block must stay within 32767 characters;
  - the block stays sorted;
  - values are copied as they are, so an embedded `=` is kept.

  `BuildOwnedEnvironment` reads these names only when `platform::RunningUnderWine()` is true.
  `OwnedProcess::ProtonPassThroughCount()` reports how many were passed. On Windows the
  environment block is byte-for-byte the same as before (a test checks this).
- `src/mcla_launcher_controller_win.cpp` (`Start`): under Wine, after the game starts, the status
  gets ` Proton: Steam/SDL environment passed through: N variables.` and the same line goes to
  `OutputDebugStringW`, which the Proton log captures. This is not recorded in
  `launch-receipt.txt`: the export policy `Receipt()` (`src/mcla_diagnostic_export_policy.h`)
  rejects unknown keys, so a new key would break diagnostic export.
- `SDL_JOYSTICK_ALLOW_BACKGROUND_EVENTS` and `SDL_HINT_JOYSTICK_*` are not passed through. The
  codebase does not reference them.
- `src/mcla_app.cpp` (`OnPreSetup`): under Wine, if `SDL_GAMECONTROLLER_ALLOW_STEAM_VIRTUAL_GAMEPAD`
  is absent, the game logs one input line:
  `Proton: Steam virtual gamepad not allowed by environment; controllers through Steam Input will be invisible`.

## 2. KI-053: D3D12 through vkd3d instead of native Vulkan on Proton

- `src/mcla_launcher_gpu_policy.h` (new, pure): `GpuBackendArgument(under_wine)` returns
  `--gpu_backend=vulkan` under Wine and `--gpu_backend=d3d12` otherwise. The controller uses it in
  the same argument position. Every other argument is unchanged. `--d3d12_adapter=<index>` is
  still passed; the Vulkan backend ignores it.
- `src/mcla_app.cpp`: Proton is now also detected with `mcla::platform::RunningUnderWine()`. The
  `STEAM_COMPAT_DATA_PATH`, `WINEPREFIX` and `SteamDeck` checks still apply. As a result, a backend
  of `any` selects Vulkan under Wine even when the environment is stripped.
- Neither `capabilities.txt` nor `launch-receipt.txt` records the backend, so no fixture changed.

## 3. KI-051: GPU choice empty although one adapter exists

- `Adapter` now records `DXGI_ADAPTER_DESC1.DedicatedVideoMemory`.
- `DefaultAdapterName(span<const AdapterInfo>)` picks the default:
  - no adapters: none;
  - one adapter: that adapter;
  - several: the largest dedicated memory, with ties going to the first enumerated.

  `InitialGpuName(saved, adapters)` keeps a saved name exactly. Only an empty name gets the
  default.
- `View()` uses `InitialGpuName`. A saved GPU that no longer exists stays an empty selection in
  the UI. The existing test "removed draft GPU never falls back to another adapter" still passes.

1. **Controls at PRESS START.** Use the Steam Input layout as before. The Deck controls must work.
   The session `mcla.log` must show `SDL OnControllerDeviceAdded ... VendorID(0x28DE), ProductID(0x11FF)`

2. **GPU preselected.** On a fresh setup, or with the GPU never chosen, the GPU field shows the APU

3. **Launcher status after START GAME** contains `Proton: Steam/SDL environment passed through: N variables.`
   N should be at least 1. N = 0 means Steam set none of the variables for the launcher, and the pad
   will still be missing.
4. **Backend.** The log shows `selected GPU plugin 'xenos' backend='vulkan'` and no `vkd3d_*`
   threads. After F10, the package's `vulkan_*` performance counters are non-zero. Compare
   outputs/s at the title against KI-027's 19.1 baseline (M10 note).

## Limits and risks

- No device test yet. The analysis estimate for KI-050 is about 85%. If the pad is still dead with
  N >= 1 and the allow variable present, the remaining causes in the analysis (Steam Input delivery
  or admission) apply.
- The pass-through keeps the existing size rule. A very large `SDL_GAMECONTROLLERCONFIG` (more than
  about 32 KB together with the other variables) would make START GAME fail with "Child environment
  exceeds the bounded size". It is not truncated or dropped silently.
- Vulkan under Proton has not been run through the managed launcher before. Earlier Deck Vulkan
  runs used the old .sh launches. If the Vulkan backend fails to start on the Deck, the fallback is
  to revert `GpuBackendArgument` to d3d12; the KI-050 fix does not depend on it.
- On a Linux PC with several GPUs, the Vulkan backend picks its own device, and the launcher's GPU
  choice (a DXGI index) does not steer it.
- Steam Deck on-screen keyboard (KI-052) is unchanged.
- DGX Spark: not used. The work was bounded source edits plus deterministic builds and tests, and
  no part suited a separate extraction.
