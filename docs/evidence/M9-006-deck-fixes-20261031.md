Implementation by an Opus subagent on 2026-10-31 from the

## 1. KI-050: Steam Input controls not reaching the game through the launcher (Deck and Windows)

**Cause (analysis, about 85%).** SDL 3.5 ignores the Steam Virtual Gamepad (28DE:11FF) unless
`SDL_GAMECONTROLLER_ALLOW_STEAM_VIRTUAL_GAMEPAD` is set. The launcher started `mcla.exe` with a
minimal environment that dropped this variable. The same applies on Windows when the launcher
is started through Steam with Steam Input forced: the game then sees only the Steam Virtual
Gamepad, and SDL ignores it. For that reason the pass-through applies on every platform. The
first version applied it under Wine only; it was changed before any package was made.

**Change.**
- `src/mcla_launcher_process_win.{h,cpp}`: there is a new bounded list, `kSteamPassThrough`
  (exposed as `SteamPassThroughNames()`), with `SDL_GAMECONTROLLER_ALLOW_STEAM_VIRTUAL_GAMEPAD`,
  `SDL_GAMECONTROLLERCONFIG`, `SDL_GAMECONTROLLER_IGNORE_DEVICES`,
  `SDL_GAMECONTROLLER_IGNORE_DEVICES_EXCEPT`, `SteamVirtualGamepadInfo`, `SteamAppId`,
  `SteamGameId`, `SteamDeck`, `STEAM_COMPAT_DATA_PATH` and `WINEPREFIX`.
  `MakeOwnedEnvironment(source, windows, system, passed_through*)` keeps these names on every
  platform when they are present. It uses the same rules as the existing directory variables:
  - name match ignores case and the canonical spelling is written;
  - a duplicate name or an embedded NUL is rejected;
  - an empty value is left out;
  - the whole block must stay within 32767 characters;
  - the block stays sorted;
  - values are copied as they are, so an embedded `=` is kept.

  `BuildOwnedEnvironment` reads these names on every platform, and
  `OwnedProcess::SteamPassThroughCount()` reports how many were passed. When none of the names
  is present, the environment block is byte-for-byte the same as l48 (a test checks this).
- `src/mcla_launcher_controller_win.cpp` (`Start`): after the game starts, when N > 0, the
  status gets ` Steam/SDL environment passed through: N variables.` (no "Proton:" prefix). The
  line `MCLA launcher: Steam/SDL environment passed through: N variables.` always goes to
  `OutputDebugStringW`, including N = 0; the Proton log captures it. The count is not recorded in
  `launch-receipt.txt`: the export policy `Receipt()` (`src/mcla_diagnostic_export_policy.h`)
  rejects unknown keys, so a new key would break diagnostic export.
- `SDL_JOYSTICK_ALLOW_BACKGROUND_EVENTS` and `SDL_HINT_JOYSTICK_*` are not passed through. The
  codebase does not reference them.
- `src/mcla_app.cpp` (`OnPreSetup`): on every platform, if
  `SDL_GAMECONTROLLER_ALLOW_STEAM_VIRTUAL_GAMEPAD` is absent, the game logs one input line:
  `Steam virtual gamepad not allowed by environment; controllers through Steam Input will be invisible`.
  A normal Windows start without Steam also logs this line; it is informational only.

## 2. KI-053: D3D12 through vkd3d instead of native Vulkan on Proton (deferred)

**Status: deferred.** A first version passed `--gpu_backend=vulkan` under Wine and made the host
treat `RunningUnderWine()` as a Proton trigger. That version was reverted before any package was
made. The packaging check found that every SDK install in this project, `private/l48-sdk-install`
included, is configured with `REXGLUE_USE_VULKAN=OFF`. With that SDK, `rexgpu-xenos.dll` logs
"requested backend 'vulkan' is not compiled into this plugin" and `ReXApp::SetupPresentation`
fails with a message box. Forcing Vulkan would therefore stop l49 at startup on the Deck.

**What remains in the code.**
- `src/mcla_launcher_gpu_policy.h`: `GpuBackendArgument(under_wine)` returns
  `--gpu_backend=d3d12` on every platform. The helper, its call site and its tests stay, so turning
  KI-053 on later is a one-line change. The launch command line is byte-identical to l48.
- `src/mcla_app.cpp`: the backend switch is exactly as before. It fires only for `gpu_backend == "any"`
  together with one of the variables `STEAM_COMPAT_DATA_PATH`, `WINEPREFIX` or `SteamDeck`. There
  is no `RunningUnderWine()` trigger. The host no longer uses `RunningUnderWine()` at all.
- **Interaction with KI-050 (checked).** Through the launcher (on Windows too), the pass-through now delivers
  `STEAM_COMPAT_DATA_PATH`, `WINEPREFIX` and `SteamDeck` to the game. Even so, the old switch cannot
  fire there. In the SDK (`src/ui/rex_app.cpp`, `SetupPresentation`), `config_.gpu_backend` is set
  from the `gpu_backend` cvar before `OnPreSetup`. The launcher passes an explicit
  `--gpu_backend=d3d12`, so the value is `"d3d12"`, not `"any"`, and the explicit D3D12 wins. No
  extra guard was needed.
- A direct (non-launcher) Proton start with the default `any` and Steam variables would still
  select Vulkan and fail with this SDK. That behaviour is unchanged from earlier builds.

**What a Vulkan-enabled build needs.**
1. An SDK build and install with `REXGLUE_USE_VULKAN=ON`, with its own SDK test pass.
2. A Deck A/B check: the plugin loads `backend='vulkan'`, the title renders, the `vulkan_*`
   counters are non-zero, and there is no regression against D3D12 through vkd3d.
3. Then `GpuBackendArgument` returns `--gpu_backend=vulkan` under Wine, with the matching test
   expectation, and optionally the `RunningUnderWine()` host trigger.

## 3. KI-051: GPU choice empty although one adapter exists

- `Adapter` now records `DXGI_ADAPTER_DESC1.DedicatedVideoMemory`.
- `DefaultAdapterName(span<const AdapterInfo>)` picks the default:
  - no adapters: none;
  - one adapter: that adapter;
  - several: the largest dedicated memory, with ties going to the first enumerated.

  `InitialGpuName(saved, adapters)` keeps a saved name exactly. Only an empty name gets the
  default.
- `View()` uses `InitialGpuName`. A saved GPU that no longer exists stays an empty selection in
  the UI. The existing test "removed draft GPU never falls back to another adapter" still passes.

## What the owner must verify on the Steam Deck (next package)

1. **Controls at PRESS START.** Use the Steam Input layout as before. The Deck controls must work.
   The session `mcla.log` must show `SDL OnControllerDeviceAdded ... VendorID(0x28DE), ProductID(0x11FF)`
   and `SDL_ACTIVE_CONTROLLER ... reason=first-connected`. It must not show the line
   `Steam virtual gamepad not allowed by environment`.
2. **GPU preselected.** On a fresh setup, or with the GPU never chosen, the GPU field shows the APU
   (`AMD Custom GPU 0932 (RADV VANGOGH)`) without picking it by hand.
3. **Launcher status after START GAME** contains `Steam/SDL environment passed through: N variables.`
   N should be at least 1. If the line is missing (N = 0), Steam set none of the variables for the
   launcher, and the pad will still be missing.
4. **Backend (unchanged, KI-053 deferred).** The log still shows `backend='d3d12'`, which runs
   through vkd3d-proton as in l48. It must not show a "Selected native Vulkan backend" line or a
   Vulkan plugin error.

## Limits and risks

- The pass-through now also runs on Windows. When the launcher is not started through Steam, none
  of the names is set and nothing changes. When it is started through Steam, the game also gets
  `SteamAppId`/`SteamGameId`, as any Steam-launched game does. The SDK backend switch cannot fire
  through the launcher (see section 2).
- No device test yet. The analysis estimate for KI-050 is about 85%. If the pad is still dead with
  N >= 1 and the allow variable present, the remaining causes in the analysis (Steam Input delivery
  or admission) apply.
- The pass-through keeps the existing size rule. A very large `SDL_GAMECONTROLLERCONFIG` (more than
  about 32 KB together with the other variables) would make START GAME fail with "Child environment
  exceeds the bounded size". It is not truncated or dropped silently.
- KI-053 stays open. The Deck keeps D3D12 through vkd3d-proton until a Vulkan-enabled SDK exists
  (see section 2).
- Steam Deck on-screen keyboard (KI-052) is unchanged.
- DGX Spark: not used. The work was bounded source edits plus deterministic builds and tests, and
  no part suited a separate extraction.
