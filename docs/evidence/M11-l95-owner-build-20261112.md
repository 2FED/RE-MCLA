  start-up defaults, before the guest runs): with `mcla_fma_bench` the host times 1e5 `fma` calls
  through the CRT (`&::fma`, the UCRT function, through a volatile pointer) and, only when CPUID
  leaf 1 reports FMA3 and OSXSAVE + AVX with XCR0 bits 1-2 set, 1e5 calls of a
  `target("fma")` `__builtin_fma` function, on 4096 fixed operand triples (finite random values plus
  cancellations, zeros, a subnormal, signed zeros); counts bitwise result differences over the 4096
  triples and logs once `MCLA_FMA_BENCH v=1 crt_ns= hw_ns= cpu_fma3= os_ymm= mismatch=
  nan_mismatch= calls=100000 operand_sets=4096 hw=ran|skipped`. Nothing is interposed. No unit test
  of its own (no new test suite; the key is covered by both key tests).
- **Brightness fields (scope addition for KI-077)**, `src/mcla_tod.{h,cpp}`, always on, read-only,
  appended fields only. Every `MCLA_TOD` line ends with ` adapt_lum=<float|na> adapt_lum_bits=0x...
  lum4_raw=<32 hex|na> bp_obj=0x... bp_preset=<u> bp=<11 floats> bp284=0x...` (or
  ` bp_preset=-1` when the post-fx pointer is not usable), and the F10 `time_of_day` object gains a
  `"brightness"` member with the same data read fresh at F10. A change of the +340 byte, compared at
  the existing 1-in-16 clock tick (one byte read), writes an immediate line with `why=bp_preset`.
  Cost: nothing per frame beyond that byte; the rest is read only when a line or F10 is written.
  Sources and verification (each checked in `mcla_tod_test` against the generated code, like the
  l93 offsets):
  - post-fx object pointer `0x829054A0`: `sub_823076E8` (TU16) `lis r11,-32112` / `lwz
    r11,21664(r11)` / `stb r4,340(r11)` (verified; the setter has exactly two callers in the whole
    tree, both in TU16: `sub_82304680` and `sub_82305080`, verified);
  - the fields: the bright-pass builder `sub_8260DA68` (TU47) reads from its argument (`mr r31,r3`)
    `lbz +340`, the two presets `+256,+260,+264,+308` and `+268,+272,+276,+280`, `+304`, `+348`
    (verified in order) and `lwz +284` (a word, logged as hex, not as a float) and `lfs +288`
    (verified). **Not verified:** that the builder's argument is the object at `0x829054A0` (the
    research's inference; its only caller passes its own `r31`).
  - adapted luminance `0x03098000` (1x1 `k_32_FLOAT`) and `0x03099000` (4x4): **these guest-physical
    addresses come from the research's resolve log of one session, not from generated code**, so
    they cannot be verified against it. They are read through the physical alias `0xA0000000` only
    when every host page of the range is committed and readable (`VirtualQuery`; a page armed by the
    l92 read watch or uncommitted is skipped), as big-endian; the raw bits are logged too. The 4x4
    target's tiled layout is not verified, so its first 16 bytes are logged as hex (`lum4_raw=`)
    instead of min/max/mean.
  - The post-fx pointer is checked like the manager pointer (`PointerPlausible`, non-null) plus the
    `VirtualQuery` check of the 352 bytes read.
