## 2. Direct runs versus the broken 1440p launcher session

**Frames.** `live-20261031T100934Z-43848-1` (`full`): a police Caprice side-on at about 10 m, with
the normal black and white split and seal; no streaks. `live-20261031T101136Z-280-1` (`some`):
the police car fills the frame at about 4 m; black nose, rear and roof edge, clean white doors,
crisp seal, "POLICE", "19350" and motto; no blue, no columns. The owner's "normal in both" is
confirmed. For contrast, `29760-1` at the same scale shows dense blue/black/white column
blocks over the doors, rear quarter and fender, with the seal and the POLICE/19350 decals intact
and crisp on top.

**Logs.** I masked timestamps, thread ids, numbers and paths, then compared the first 120 lines
(startup to in-world) of session 2 against session 6 line by line. The only differences:

1. The F10 root path (`<profile>/diagnostics/<session>/live` versus `<run>/diagnostics/live`). This
   difference is intended.
2. **`MCLA graphics: enabled light render-to-texture CPU readback for photo mode` is present only
   in the launcher sessions.** This is expected. `MclaApp::OnPostLoadGraphicsPlugin` sets
   `readback_resolve=some` only when the value was not given explicitly. The SDK reads the cvar on
   every resolve (`GetReadbackResolveMode` in `IssueCopy`), so a host-set `some` and a command-line
   `some` are the same mode. The submissions/min (5,043 versus 5,090) and the GPU time agree.
3. Two lines in a different order (persisted unlocks, invalidation widening) and the controller-
   attach lines in a different place. This is thread timing.

Steam virtual gamepad, signin, vblank 60/240 switching, budget/cache limits, sentinel, adapter
and guest mode are the same. **There is no startup cvar dump in either log**, so a full cvar
comparison is not possible from the evidence. The direct `command.txt` matches the launcher
argument set reconstructed in part 2. The `full` run differs only in the expected way: 8x more
submissions (each readback ends a submission), 22.6 fps.

**Verdict:** apart from the readback mode in run 5, nothing distinguishes the direct runs from
the broken launcher session. The launcher environment is also excluded directly: launcher
sessions 3 and 4 were clean.

## 3. Hypotheses against the table

The one variable that separates broken from clean is **session order on the l49 build cache**.
The cache root is per build hash, so l49 started with an empty `cache/2E4BB9F3.../shaders`
directory. Session 0 never reached gameplay and stored nothing. Session 1 (2160p) started with
**no shader/pipeline storage at all** (it is the only gameplay session without a "Translated N
shaders from the storage" line), and its second F10 audit window still recorded `pso_count=29`
(pipelines being created more than a minute into play). Session 2 started with session 1's
392/694 and added +8 shaders and +94 PSOs. Clean sessions 3-6 started with 400/788 to 426/975.
The two broken sessions are exactly the **first two gameplay sessions on a fresh cache**, and all
four later sessions are clean across three scales, two guest modes, two readback modes and both
launch paths. If the order were random, this has a probability of 1/15 (about 7%). The
correlation is suggestive, not proof. Session length, garage, photo, race and warp history do
not separate the groups (1-2 minutes, the same script in all six).

Ranked:

1. **H5 (new): a draw skipped while its pipeline is still being created in the one-shot livery
   composite. Rank 1, medium.** Source: with `async_shader_compilation=true` (default),
   `D3D12CommandProcessor::IssueDraw` **returns without drawing** when the pipeline is still pending
   (`GetD3D12PipelineByHandle(...) == nullptr && !WaitForPendingPipeline(...)`). The bounded wait
   (`d3d12_async_pipeline_wait`) is off by default, and the host turns it on only around the
   Photo Mode capture (`mcla_photo_capture.cpp`), not at car spawn. A livery is composited **once**
   when a car spawns (KI-033 path: 32bpp composite, resolve, CPU readback, CPU BC3 into the car's
   1024 atlas). If a layer or clear draw of that composite is skipped, the target keeps whatever
   the EDRAM/render target held before (another car's or pass's content). That content is then
   resolved, read back and baked into the car's atlas. It persists for the car's life, so
   leaving Photo Mode does not fix it (29760-3). The decals stay crisp because their pipelines
   were ready or they are a separate texture. Different content per session fits as well. Once
   the pipelines are in storage, they are created synchronously at startup ("Created N graphics
   pipelines from the storage"), so later sessions do not skip them. This explains broken in
   sessions 1-2 and clean in 3-6 independently of scale and readback mode. Weak point: session 2
   already had session 1's pipelines, so a different police/traffic composite permutation must
   have been new in session 2. Its +94 PSOs make that plausible but do not prove it. Earlier
   build consistent but weak: the original KI-047 report (l41, session fce31190) was the second
   gameplay session on its fresh build cache.
2. **H2 stale or sparse `some` readback (any scale). Rank 2, low-medium.** It is mechanically
   real: two-slot ping-pong per (address, length) key, the read slot is not fenced, and only a
   miss or every 4th same-key resolve is copied to guest memory, so the copy phase depends on
   history. But `some` was clean in three of four `some` sessions, including a direct 1440p run
   with a similar time in world. It does not explain the clustering in the first two sessions. If
   the decals are part of the same composite, a whole-surface stale copy would also replace them,
   yet they are intact.
3. **H1 shifted scaled CPU copy (`written_address = copy_dest_extent_start`, while the downscale
   reads from the scaled range start at `copy_dest_base`). Rank 3, low.** The mechanism is present
   in the source. As a deterministic cause it is **falsified**: three clean scale-2 sessions,
   including the identical-configuration direct 1440p `some` run. A slot-dependent variant (only
   atlas slots whose extent starts after the base) survives, but it cannot explain why the first
   two sessions were broken. `full` and `some` use the same copy here, so the A/B does not test it.
4. **Texture-cache entry not invalidated after a guest rewrite (write-watch gap). Rank 4, low.**
   There is no supporting signal. Watch calls, invalidations and distinct pages in broken
   session 2 equal those in clean session 6 within 3%.
5. **EDRAM/render-target reuse.** Not an independent cause here. It is the most likely **source**
   of the foreign content under H5 (or H2): whatever was last in the composite's EDRAM tiles or
   the reused scratch target.
6. **Excluded:** resolution or scale alone (clean at 2x, broken at 2x); readback mode alone (both
   clean); the launcher-only environment (launcher sessions 3 and 4 clean; log-equivalent);
   VRAM pressure/KI-048 (session 2 had none); session length or garage/photo/race history (same
   script everywhere).

## 4. Next decisive experiment (no build, about two 2-minute runs)

Use the existing direct-run script pattern (`private/ki047-readback-*-1440p.cmd`) with one
change: **`--cache_root=<run>\cache-empty`, a new empty directory per run**, instead of the
profile's build cache. This is non-destructive. It does not touch MAIN's cache or saves beyond the
usual autosave, and the scripts already copy the user tree before and after. Keep the default
`readback_resolve` (`some`), and follow the same script as sessions 1-6: load, drive about 60 s,
Photo Mode on a police car side-on, F10 twice.

- **Run A: fresh cache, 1440p, defaults.** This reproduces session 2's only distinguishing
  condition. H5 predicts **broken**. If it is clean, H5 is much weaker (repeat once, since content
  depends on what spawns).
- **Run B (only if A is broken): fresh cache, 1440p, `--async_shader_compilation=false`.**
  Pipelines then compile synchronously (expect long hitches the first time), and no draws are
  skipped. H5 predicts **clean**. That would confirm H5. H1 and H2 would not change, because the
  readback mode and scale are the same.
- **Optional Run C: fresh cache at 720p, defaults.** If it is broken, scale is irrelevant and H1 is
  closed for good.

Add `--gpu_render_audit=true` to A and B. The l49 `rexgpu-xenos.dll` has it, and its
`XENOS_AUDIT_CP_SUMMARY` reports `pso_pending_skip`. This is a bonus only: the summary is emitted
at a host checkpoint (probe-only) or at shutdown, and the title hard-exits, so it may not appear.
The next normal launch's "Translated N / Created M from the storage" line also shows how many
pipelines each fresh run had to create.

If A is clean twice, fall back to the diagnostic build from part 2: log every scaled readback in
`IssueCopy_ReadbackResolvePath` (`copy_dest_base`, `copy_dest_extent_start`, length, format,
`is_cache_miss`, `should_copy`), plus every pipeline-pending skip with the bound RT base/format.
Run it once on a fresh cache.

If H5 is confirmed, the fix options are to enable the bounded `d3d12_async_pipeline_wait` (or
synchronous creation) whenever a resolve feeds a CPU read, or permanently for this title. The
cost would be measured with the existing pacing lines. Shipping a pre-warmed pipeline storage with
volunteer builds is a mitigation.

## Unresolved risks

- There is one session per condition and 6 sessions in total. The order correlation is a 1/15
  coincidence under random order. Each clean session saw a different police car instance and place.
- The livery composite's exact draw/resolve sequence and whether decals are in the same
  composite are inferred, not traced.
- The skip counters are not in the existing logs. Under H5, `async_placeholder_skips=0` means
  nothing (it is not the D3D12 pending-skip counter).
- The SDK source is the l48 clone. Cvar presence in l49 was checked only by string search of the
  staged DLL.
