- **Run A (default):**
  - the `cad_unfenced` / `cad_copies` share in the minutes with flicker (the design expects >= ~20 %),

  - `lead2_frames`.
- **Run B (fenced), every minute:**
  - `cad_unfenced_served=0` and `fence_before_data=0`;
  - `done_delivered + done_superseded + done_already + done_dropped` against the tracked copies;
  - small `done_dropped` and `done_overflow=0`;
  - `cad_deferred` about `cad_unfenced`.
- **Performance:**
  - fps B >= A - 3 %; p99 not > A + 5 %; CP busy <= A + 0.5 ms/f;
  - `memcpy_ms` similar; subm/frame unchanged;
  - 0 frames > 100 ms; no hang.
- **Falsifier:** if B still flickers with served=0, the cause is not the read-back path.

## 7. Not done / risks

- Not committed in the main repository (the primary commits exactly the s.2 diff). The SDK commit is
  local only and not pushed. `docs/known-issues.md`, `docs/M11-priorities.md` and
  `docs/current-state.md` were not updated.
- Not signed: no ticket, no `private\l88-internal`, no admission row.
- No runtime: no PC or Deck run, no physical PASS, no performance numbers.
- Risks of the fenced arm, all untested in the game:
  - Copies of non-exempt keys reach guest memory at GPU completion instead of at the key's next
    cadence resolve. This is earlier for a lagging GPU, but it is a new write time into guest RAM.
  - A key whose previous slot stays unfenced longer than about 4 of its resolves gets its deferred
    copy superseded. Guest RAM then waits for the next completed copy; there is no torn read.
  - Fast mode is not covered.
  - The always-on counters add a fence poll per due cadence copy and a FIFO push per recorded
    non-exempt copy (under the existing table lock) in both arms.
