## B. KI-060 zero-delay backoff (`rex/system/zero_delay.h`, `src/system/xthread.cpp` `XThread::Delay`)

New cvars (all restart):

| cvar | default | meaning |
|---|---|---|
| `ke_delay_zero_mode` | backoff under Wine/Proton, native on Windows (`platform_defaults.h`) | native / backoff |
| `ke_delay_zero_backoff_after` | 32 (1..1048576) | zero delays of a streak that stay native |
| `ke_delay_zero_backoff_max_us` | 500 (50..2000) | longest backoff sleep |
| `ke_delay_zero_gap_us` | 200 (1..100000) | a zero delay continues the streak only if the previous delay of the same thread ended less than this ago |

How it works:
- Per-XThread state `zero_delay_streak_` (no locks; only the thread touches it).
- Every guest delay calls the pure `PlanZeroDelay`.
  - Eligible = zero relative interval (after scaling), not alertable, and no pending APC.
  - A non-eligible delay (non-zero, absolute, alertable, APC pending) resets the streak.
  - An eligible delay continues the streak if the previous eligible delay ended less than `gap_us` ago. Otherwise the streak restarts at 1.
  - Streak <= after: native, as before.
  - Beyond that: sleep on the existing per-thread high-resolution timer (`rex::thread::HighResolutionSleep`, non-alertable). It starts at 50 us and doubles up to max.
- The end time is recorded after the delay returns, so the backoff sleep does not count as a gap.
- If the timer is unavailable, the delay goes native and counts in `fallbacks`.
- Startup line: `KI-060: repeated zero guest delays mode=... after=... max_us=... gap_us=... (ke_delay_zero_mode)`.

`MCLA_SLEEP` minute line: appended fields (existing fields unchanged, still v=1):
- `zero_mode`;
- `zero_backoffs` and `zero_backoff_us` (measured wall time of the backoff sleeps);
- `zero_streak_max` (longest streak of any thread in the minute);
- `top_site` and `top_site_zero`: the guest call site with the most zero delays, and its count. It is counted for every zero delay, in either mode.

How `top_site` is found:
- From the frame of KeDelayExecutionThread's guest caller: back chain at 0(r1), saved LR at back_chain - 8. For the title's SleepEx (sub_82460270, frame 112) this is r1+104, as the analysis describes.
- Sleep wrappers sub_8244FEC0 / sub_821C91B8 / sub_821C91B0 are tail calls (`b`), so the value is the Sleep(0) call site itself. Expected: 0x821449D0 (tick end) or 0x82136738 (bank-lock spin).
- Reads are limited to the thread's guest stack [stack_limit, stack_base) (the stack is translated once). If an address falls outside it, the site is 0 and nothing is counted.

## C. Guest XAudio thread priority

- `guest_audio_thread_priority` (normal / above_normal / highest). Default above_normal under Wine, normal on Windows.
- `guest_thread_priority_boost_start` (hex list). Default `823EC8C8,823EC990`.
- It is applied in `XThread::Create` (guest threads only), after the creation-flag priority. Log line: `KI-060: guest thread <handle> ('<name>', start <addr>) host priority <p> (guest_audio_thread_priority)`, plus one config line at the first thread creation.

Identification:
- Only three guest call sites of `ExCreateThread` exist in generated/default. One is `sub_823ECC60` in the title's audio library range (`mcla_recomp.25.cpp:38721`).
- After `KeInitializeSemaphore` and `ExRegisterTitleTerminateNotification`, it loops over 6 hardware threads (a per-thread kind byte filled by `sub_823EB2D0`). For each thread with a non-zero kind it calls:
  - `ExCreateThread(&h, 0, 0, xapi_startup=0, start=r7, ctx=0, flags = 1 | (1 << hw) << 24)`, where r7 = 0x823EC8C8 for kind 1 and 0x823EC990 otherwise;
  - then `KeSetBasePriorityThread(thread, 15)` and `KeResumeThread`.
- So the console runs these threads at guest base priority 15. The SDK ignores that: `ignore_thread_priorities`, and `SetPriority(15)` maps to normal anyway, because only increments > 0x11 map to above normal.
- `sub_823EC8C8`: waits (KeWaitForSingleObject), runs `sub_823EC160` / `sub_823EC248`, signals KeSetEvent. This matches F8000534's sampled imports (KeWaitForSingleObject, KeSetEvent, XAudio calls).
- `sub_823EC990` is the helper variant (waits and runs `sub_823EC248`).
- Confidence: high that these are the title's XAudio engine threads, and medium-high that F8000534 is the 823EC8C8 instance. The handle-to-start mapping was not checked at runtime; the new log line will show it.
- Both entries are listed, which matches the console, where both get priority 15.
- In another title these addresses match no thread, so nothing changes.

`apu_worker_priority` is left as it was (still above_normal under Wine). The analysis suggests making it neutral; that is the owner's or primary's call.
