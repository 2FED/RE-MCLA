## 2. KI-050: no gamepad input (S1 Deck blocker)

### Verdict (high confidence): the launcher strips the Steam environment, so SDL filters the Steam virtual gamepad

1. Under Steam Input the game sees only the **Steam Virtual Gamepad** (VID 0x28DE, PID 0x11FF);
   Steam hides the physical Deck controls from the game.
2. SDL 3.5 ignores that device unless the process environment says Steam launched it
   (`thirdparty/sdl3/src/joystick/SDL_gamepad.c:3266-3280`):

   ```c
   const char *hint = SDL_getenv_unsafe("SDL_GAMECONTROLLER_ALLOW_STEAM_VIRTUAL_GAMEPAD");
   bool allow_steam_virtual_gamepad = SDL_GetStringBoolean(hint, false);
   if (allow_steam_virtual_gamepad && WIN_IsWine()) return false;   /* accept everything */
   if (SDL_IsJoystickSteamVirtualGamepad(vendor_id, product_id, version))
       return !allow_steam_virtual_gamepad;                           /* ignore it */
   ```

   The check sits in `SDL_ShouldIgnoreJoystick`, used by the XInput (`SDL_xinputjoystick.c:192`),
   RawInput, DInput, WGI and HIDAPI backends alike, so no backend switch avoids it. Steam sets
   `SDL_GAMECONTROLLER_ALLOW_STEAM_VIRTUAL_GAMEPAD=1` for the launched game; Wine imports it into
   the launcher's Windows environment.
3. The launcher starts mcla.exe with an **allow-listed environment**
   (`src/mcla_launcher_process_win.cpp:18-20`, `MakeOwnedEnvironment`/`BuildOwnedEnvironment`,
   `CreateProcessW(..., CREATE_SUSPENDED|CREATE_UNICODE_ENVIRONMENT|CREATE_NO_WINDOW, environment->data(), ...)`):
   only LOCALAPPDATA, APPDATA, USERPROFILE, TEMP, TMP, ProgramData, HOMEDRIVE, HOMEPATH plus
   SystemRoot/WINDIR/PATH. The SDL/Steam variables (and SteamAppId, SteamDeck, STEAM_COMPAT_*,
   WINEPREFIX, SDL_GAMECONTROLLERCONFIG, SteamVirtualGamepadInfo) are dropped.
4. Difference from the working launches:
   - Old Deck bundles (`launch-v96.py`): `env=dict(os.environ)` (full Steam environment), `proton run mcla.exe`
     directly, `REX_GPU_BACKEND=vulkan`, `REX_INPUT_BACKEND=sdl`.
   - Older portable launcher (`src/mcla_portable_launcher_win.cpp:1439`): `CreateProcessW(..., 0, nullptr, ...)`,
     i.e. environment inherited.
   - Same `--input_backend=sdl`, `--mnk_mode=false`. The job object (KILL_ON_JOB_CLOSE only) and
     CREATE_NO_WINDOW are not the issue: Steam Input reaches every Wine process in the prefix via winebus.

  NUL/size bounds stay. Native Windows behaviour unchanged.
- Host diagnostic: under Wine, log one line when `SDL_GAMECONTROLLER_ALLOW_STEAM_VIRTUAL_GAMEPAD` is absent,
  so a future package names the cause directly.
- Tests: extend the `MakeOwnedEnvironment` test with a Wine-flagged source containing the SDL/Steam names
  (passed through, sorted, bounded) and a Windows-flagged source (dropped); duplicate/NUL still rejected.

## 3. KI-051: GPU choice empty with a single adapter

- `Adapters()` (`src/mcla_launcher_controller_win.cpp:179-193`) lists non-software DXGI adapters that can
  create a D3D12 device. `View()` (lines 775, 787) sets `ui.gpu_name = p.gpu_name` (empty for a new
  setup); `Render()` (`src/mcla_launcher_ui_win.cpp:545-551`) selects only an exact name match. The status
  text states the policy ("Nothing is selected automatically"); Start then fails in `AdapterIndex`.
- Minimal change: add `DedicatedVideoMemory` to `Adapter`, plus a pure helper
  `std::optional<std::wstring> DefaultAdapterName(span<const AdapterInfo>)`: 0 -> none; 1 -> it;
  several -> largest dedicated VRAM, ties -> lowest enumeration index. In `View()`:
  `if (p.gpu_name.empty()) ui.gpu_name = DefaultAdapterName(adapters)`. Only the never-chosen case is
  defaulted; a saved GPU that disappeared stays empty (keeps the existing UI test "removed draft GPU never
  falls back to another adapter", `tests/mcla_launcher_ui_win_test.cpp:696-701`).
- Tests (pure helper, no DXGI): single APU -> selected; {integrated 512 MiB, discrete 8 GiB} -> discrete in
  either order; equal VRAM -> first; empty -> none; UI test: empty saved name + one inventory entry ->
  CB_GETCURSEL 0 and the CHECK SETUP request carries that name.

## 4. Backend: D3D12 (vkd3d-proton) instead of native Vulkan

- The launcher hard-codes `--gpu_backend=d3d12` and `--d3d12_adapter=<index>`
  (`src/mcla_launcher_controller_win.cpp:889-894`). `MclaApp::OnPreSetup` switches to Vulkan only when
  `config.gpu_backend == "any"` and one of STEAM_COMPAT_DATA_PATH / WINEPREFIX / SteamDeck is set
  (`src/mcla_app.cpp:1231-1242`); through the launcher both fail (forced d3d12, env stripped).
- So this run was D3D12 -> vkd3d-proton -> RADV, not the M7/M8 intent ("native Vulkan for Proton").
  Earlier evidence (`docs/evidence/M7-016-deck-performance-diagnostic.md`) shows the backend is not the main
  perf factor (D3D12 7.34 vs Vulkan 8.86 unique outputs/s), but the Deck perf counters and KI-027
  baselines are Vulkan-only: every `vulkan_*` counter here is 0 and `graphics.backend` is 0.
- Proposal: under `platform::RunningUnderWine()` the launcher passes `--gpu_backend=vulkan`, and the host's
  Proton detection uses `RunningUnderWine()` instead of env vars. Short Deck A/B optional; not needed for KI-050.

## 5. KI-052: Steam on-screen keyboard in launcher text fields

Win32 EDIT controls under Proton do not open the Steam keyboard automatically; Steam opens it for
Steamworks/SDL text-input requests or by the STEAM+X chord. Options: document STEAM+X now; later use SDL
text input or the Steamworks floating keyboard API (no Steam API in the build). Mark as later (S3); folder
paths can be picked with the dialog, so only the profile-name field really needs typing.
