    `SDL_GetHapticEffectStatus` / `SDL_RunHapticEffect` through the helper.

      the slot type (logged before the destroy/create).
    - `action=start-suppressed slot=N type=T reason=status-playing` for the first
      suppressed infinite start per run (flag cleared by a successful

  - `tests/unit/input/sdl_wheel_ffb_rearm_test.cpp` (new, registered in

  resume, start suppression rule and update path are otherwise unchanged.
- All new lines contain `SDL_WHEEL_FFB` or `SDL wheel FFB`, so the host's L2

  without a host change. The `XINPUTD_FF_AUDIT ... action=batch` line is only in
  the main log.

### Deviations from the proposal diff

1. Update-path re-arm is limited to the updated slot (the proposal re-armed all
   slots on every update), as the task brief specified.
2. Per-slot re-arm budget (10 per minute, `rearm-limit` line) added; the
   proposal had no bound.
3. Policy moved into a header with injectable status/run callables so it is
   unit tested; the driver passes SDL lambdas.
4. Retype detection also requires an existing host effect (`effect_id >= 0`);
   the proposal compared against stale slot state.
5. The batch audit line also records raw r5/r7 and the first word of entries
   0 and 1.
6. The watchdog also requires `is_wheel` and input-active (not only `haptic`).

## 4. Wheel tester / owner check (T300)

1. Start l47 with the wheel active; drive normally (centering and engine
   vibration as on l46).
2. Reproduce the head-on collision that triggers the slow-motion crash camera.
3. Expected with the fix: if centering or vibration drop, they come back
   within about a second, and the log has
   `SDL_WHEEL_FFB_EFFECT v=2 action=rearm ... reason=watchdog` (or
   `reason=update`) for the spring / periodic slots.
4. Press **L2** once just after the crash and again a few seconds later
   (also once before the crash as a baseline); the FFB array should show the
   rearm, stop/start, retype or start-suppressed lines.
5. Note whether `XINPUTD_FF_AUDIT v=1 export=EffectOperation action=batch`
   appears in the main log, and its count/entry words.
6. Any `rearm-limit` or `rearm failed` line: report it with the log.
7. If force is still lost with **no** rearm line: say whether pad -> wheel or
   Alt-Tab restores it (that points to a T300 status that keeps reading
   "playing", or a title-side stop).

## 5. Limits and risks

- Unverified physically. Unit tests exercise the policy with a fake haptic
  layer, not the SDL/DirectInput calls or a T300.
- If the T300 driver reports a device-stopped infinite effect as playing, the
  watchdog cannot see it (status is the only signal); a bounded unconditional
  re-start on triggers would be the next step and needs physical evidence.
- The batch path trusts r5 as the entry count with a two-word stride
  (documented in the hook comment, not yet seen in a real batched call). If a
  title passes count > 1 with another layout, extra entries would be decoded
  from the following words; invalid indices are rejected
  (`X_ERROR_BAD_ARGUMENTS` / slot without effect), but a valid-looking word
  could start/stop a wrong slot. The audit line exists to confirm this.
- Update-path re-arm queries `SDL_GetHapticEffectStatus` once per same-type
  update of a running infinite effect (possibly per frame). The start path
  already does the same per infinite start; the cost on the T300 driver is not
  measured.
- A re-armed effect restarts from its beginning (envelope attack); for
  spring/damper/periodic this is expected to be imperceptible.
- Dev SDK (unpinned, `0.20.0.1-dev.g28ac239`); the host was configured with an
  empty `REXSDK_VERSION`. Not suitable for volunteers until the SDK change is
  published and pinned.
