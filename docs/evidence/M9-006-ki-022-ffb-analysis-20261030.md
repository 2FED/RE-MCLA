# KI-022 (S2) wheel centering lost during play: source analysis and L2 reading map

Read-only source analysis by an Opus subagent on 2026-10-30 (SDK f519dd5 and its SDL 3.5.0 DirectInput haptics), reviewed and accepted as evidence by the primary agent, prompted by a wheel tester's report that centering and wheel vibration vanished at a head-on collision slow-motion camera while impact forces kept working. The fix in [M9-006-ki-022-proposal-20261030.diff](M9-006-ki-022-proposal-20261030.diff) is not applied; a tester L2 report is still awaited.

Status: read-only analysis, 2026-10-30. Nothing built, run or changed.
Source: ReXGlue SDK at pinned `f519dd5` (`private/l39-sdk-src`). Paths below are
relative to that tree unless they start with `src/mcla_`. The SDL3 copy is
`thirdparty/sdl3` (3.5.0), Windows DirectInput haptic backend.

Tester's new fact (2026-10-30): the centering force **and** the wheel's
continuous vibration disappeared together at the moment of a head-on
collision, when the slow-motion crash camera started. Collision/impact forces
**kept working** afterwards.

Labels used: **[V]** verified in source; **[D]** documented DirectInput or
Windows behaviour, not visible in this source; **[H]** hypothesis that the L2
dump has to confirm.

---

## 0. Correction to the brief: there is no rumble-derived wheel vibration

- **[V]** `SetState` (the XInput motor vibration call) returns success and does
  nothing for a wheel: `src/input/sdl/sdl_input_driver.cpp:437-441` ("Basic
  XInput motor vibration is not the Xbox 360 wheel force-feedback API").
  `config/wheel-input-reference.json` records `wheel_basic_rumble_suppressed: true`.
- So nothing that the guest does to `XInputSetState` (zeroing the motors in
  slow motion, for example) can reach the T300. Every force the tester feels
  comes from the title's **XInputdFF** effect API (`XInputdFFSetEffect`,
  `UpdateEffect`, `EffectOperation`, `DeviceControl`), hooked in
  `src/kernel/xboxkrnl/xboxkrnl_hid.cpp:102-169`.
- The "vibration" that disappeared is therefore an **infinite-duration periodic**
  effect (engine/road texture; host gain 40% by
  `GetWheelEffectGainPercent`, `include/rex/input/sdl/wheel_force_feedback.h:96-114`).
  The centering is an **infinite-duration spring** (condition) effect created by
  the title. The SDK owns no centering of its own and turns DirectInput
  autocenter **off** at open (`thirdparty/sdl3/src/haptic/windows/SDL_dinputhaptic.c:379-381`).
- Collision forces are **finite** effects (square/constant with a duration,
  raised to the 75% transient floor).

**The observation is an exact split along the SDK's own infinite/finite line.**
Both effects that vanished are infinite; the effect class that survived is
finite. The SDK treats these two classes differently in several places (section 1).

## 1. FFB lifecycle as implemented

### 1.1 Ownership and routing

- Guest slot 0 is routed to the **active** physical controller.
  `GetControllerState(user_index)` -> `ResolveControllerIndex`
  (`sdl_input_driver.cpp:1384-1406`). Every FFB call made while a gamepad is
  active returns `X_ERROR_DEVICE_NOT_CONNECTED` (`:494-496`, `:589-591`) and logs nothing.
- Per wheel there are 64 `WheelEffectState` slots (`include/rex/input/sdl/sdl_input_driver.h:56-64`):
  `effect_id`, `type`, `update_count`, `iterations`, `duration_ms`,
  `running`, `resume_pending`. **`running` is the host's belief only.** Nothing
  ever clears it when an effect stops by itself, expires, or is stopped by
  the driver or device. **[V]**
- No timer, watchdog or time-scale input exists anywhere in the FFB path. Effects
  change only on guest calls, focus changes, active-controller changes and
  device add/remove. **[V]** The game's time-scale (`+84`) and the M8 raw timer
  (`src/mcla_raw_timer.cpp`) cannot change a host effect directly. They can
  only change what the guest submits.

### 1.2 Create / update (`SetForceFeedbackEffect`, `sdl_input_driver.cpp:482-573`)

- `XInputdFFSetEffect` -> `update=false`; `XInputdFFUpdateEffect` -> `update=true`.
- Same slot, same type, `update=true`: `SDL_UpdateHapticEffect` (`:528-529`) ->
  DirectInput `SetParameters` with only the changed `DIEP_*` flags, **never
  `DIEP_START`** (`SDL_dinputhaptic.c:1046-1090`). **[V]** An update therefore
  does not restart a stopped effect. **[D]**
- Otherwise (create, or update with a **different type**): destroy, create,
  and re-run only if `running && has_focus_` (`:530-548`). **[V]**
- Logging: `create` logs `SDL_WHEEL_FFB_PARAMS ... action=create` + `SDL_WHEEL_FFB_EFFECT v=2 action=create`
  (`:568-570`). An update logs only the **first** update of a slot
  (`first-update`, `:558-566`). `update_count` is never reset, so **later
  updates, including a type-changing re-create through UpdateEffect, are
  silent.** **[V]**
- Failure: `SDL wheel FFB create|update failed for slot N type T: <SDL error>` (`:549-552`).
  After a failed re-create, `effect_id=-1`. Every later start of that slot then returns
  `X_ERROR_FUNCTION_FAILED` at `:592-594` **without a log line**. **[V]**
- `SDL_UpdateHapticEffect` re-acquires and retries on `DIERR_INPUTLOST /
  DIERR_NOTACQUIRED / DIERR_NOTEXCLUSIVEACQUIRED` (`SDL_dinputhaptic.c:1063-1074`).
  `SDL_RunHapticEffect` does **not** retry (`:1092-1110`). **[V]**

### 1.3 Start / stop (`SetForceFeedbackEffectRunning`, `:575-645`)

- The hook decodes **only entry 0** of the guest's `{effect_index, iterations}`
  array. `r5` (documented in the hook's own comment as the entry count) is
  ignored (`xboxkrnl_hid.cpp:138-150`). **[V]** If the title stops or starts
  several effects in one call, every entry after the first is silently dropped.
- Without focus: a finite start is dropped (`action=drop-start ... reason=focus-finite`).
  An infinite start is deferred (`action=defer-start ... reason=focus`) (`:600-616`).
- **Status-based suppression (infinite effects only):** if `running` is
  already true and `SDL_GetHapticEffectStatus` reports playing, the start is
  skipped and `X_ERROR_SUCCESS` is returned **with no log line** (`:618-627`,
  rule `ShouldSubmitWheelEffectStart`, `wheel_force_feedback.h:129-135`). A
  finite start is **always** submitted. The code's own comment says that some
  DirectInput wheel drivers keep reporting an expired effect as playing. **[V]**
- Success logs `SDL_WHEEL_FFB_EFFECT v=2 action=start|stop slot=N type=T` (`:642-643`).
  Failure logs `SDL wheel FFB start|stop failed for slot N type T: <err>` (`:632-635`).

### 1.4 Focus and active-controller changes

- Focus lost: `StopControllerFeedback(c, true)` stops **all** effects
  (`SDL_StopHapticEffects`). It marks infinite effects `resume_pending` only if
  `running && (!status_supported || status_playing)` (`:1301-1333`,
  `ShouldPreserveWheelForceFeedback`, `wheel_force_feedback.h:116-121`).
  Focus gained: `ResumeControllerFeedback(active, "focus")` re-runs only the
  `resume_pending` effects (`:317-329`, `:1335-1355`). Logs `action=resume ... reason=focus`
  or `SDL wheel FFB focus resume failed for slot N: <err>`. **[V]**
- Active-controller change: the previous controller is stopped the same way, and
  the new one is resumed with `reason=active-controller` (`:1417-1444`). Logs
  `SDL_ACTIVE_CONTROLLER v=1 guest_slot=0 previous_physical_slot=P physical_slot=Q reason=R activity_sequence=S`. **[V]**
- **Consequence [V]:** the documented workaround (pad -> wheel) restores
  centering **only if the effect status still read "playing"** at the switch.
  An infinite effect that the device really stopped and reports as stopped
  is not marked `resume_pending` and is not restored by the switch or by Alt-Tab.

### 1.5 Device add / remove

- Wheel add: `SDL_OpenJoystick` + `SDL_OpenHapticFromJoystick` (`:882-945`).
  The haptic **shares the joystick's `IDirectInputDevice8`** (`is_joystick=true`,
  `SDL_dinputhaptic.c:457-479`). Open sends `DISFFC_RESET`,
  `DISFFC_SETACTUATORSON`, gain 10000, autocenter off. Logs `SDL_WHEEL_CONNECTED v=1 ... haptic=0|1`.
- Remove: `CloseController` destroys all effects, logs `SDL_WHEEL_FFB_SUMMARY v=2 created_effects=...`
  and `SDL wheel removed from physical slot N.`. A re-added wheel starts with
  empty slot state, so a stale effect id cannot be reused across a re-add. **[V]**
  The title must recreate its effects. It does so only if it notices the
  disconnect.
- **Silent re-acquire [V]:** the DirectInput joystick poll re-acquires on
  `DIERR_INPUTLOST/DIERR_NOTACQUIRED` with no event and no log
  (`thirdparty/sdl3/src/joystick/windows/SDL_dinputjoystick.c:1020-1021, 1092-1093, 1145-1147`).
  When an exclusive FF device loses acquisition, DirectInput stops its
  effects, and re-acquiring does not restart them **[D]**. The SDK never
  learns about it: `running` stays true.

### 1.6 Other facts relevant to a crash burst

- `SDL_GetMaxHapticEffects` on Windows is a fixed 128 ("not actually supported",
  `SDL_dinputhaptic.c:389-394`). The title is told 64 slots
  (`SDL_WHEEL_FFB_DEVICE_INFO v=2 guest_slots=64 host_effects=128 host_playing=128`).
  The real T300 effect memory and concurrency are much smaller and unknown to the host. **[V]** (number) / **[D]** (T300 limit)
- `XInputdFFDeviceControl` is a **logged no-op** (`:647-659`, `SDL_WHEEL_FFB_DEVICE_CONTROL v=1 command=N`).
  It can never stop an effect itself. Its command number does show what the title intended
  (HID PID convention: 1 enable actuators, 2 disable, 3 stop all, 4 reset,
  5 pause, 6 continue; mapping not verified for this title). `XInputdFFSetDeviceGain` is a no-op logged once.

## 2. Which paths leave an infinite effect stopped with no restart

| # | Path | Verified? | What the log leaves |
|---|------|-----------|---------------------|
| P1 | Title stops spring + periodic at crash-cam start; its later restart is batched in one `EffectOperation` with count >= 2, so only entry 0 runs | Hook drops entries [V]; title batching [H] | `action=stop slot=A type=spring`, `action=stop slot=B type=<periodic>`; later `action=start slot=X` for only one slot, or none for A/B |
| P2 | Title stops them and never restarts them itself (it expected a device-level pause/continue, or re-creates without a start) | SDK side [V]; title intent [H] | `action=stop` for A and B with no later start; possibly `SDL_WHEEL_FFB_DEVICE_CONTROL v=1 command=5/6/3` around it |
| P3 | Device stops effects behind the host's back (silent DI re-acquire after `DIERR_INPUTLOST`, or T300 driver eviction under the crash burst of finite effects). `running` stays true, later updates do not restart, finite starts still work | Host blindness and asymmetry [V]; device event [D/H] | **Nothing** about A/B: only finite `action=start slot=C type=square/constant`. No errors. If the title re-sends a start and status lies "playing": still silent (suppression has no log) |
| P4 | Title reuses the spring/periodic slot for a crash effect through **UpdateEffect** with another type, then the spring is not restored | SDK silent re-create [V]; title behaviour [H] | Silent for UpdateEffect. Through SetEffect: `action=create slot=A type=square` where A was the spring slot |
| P5 | Re-create or start fails | [V] | `SDL wheel FFB create|update|start failed for slot N type T: <DirectInput error text>`; afterwards silence for that slot |
| P6 | Title updates the infinite effect with a finite duration (for example scaled by slow motion), the effect expires on the device, and a later update back to infinite does not restart it | Update never restarts [V]; title behaviour [H] | Silent (only the first update is logged). `SDL_WHEEL_FFB_PARAMS` lines show only create and first-update parameters |
| P7 | Active controller handed to a pad/mirror | [V] | `SDL_ACTIVE_CONTROLLER ... physical_slot=<pad> reason=analog|button-down` |
| P8 | Focus loss (overlay, Alt-Tab, Steam popup) | [V] | `action=defer-start` / `drop-start`; on return `action=resume ... reason=focus` or `focus resume failed` |
| P9 | Wheel re-enumerated | [V] | `SDL wheel removed from physical slot N.`, `SDL_WHEEL_FFB_SUMMARY`, `SDL_WHEEL_CONNECTED` |

Ruled out by source for this scenario: zero XInput motor vibration (P0: no
effect on a wheel), host autocenter toggles (only set off once at open), a
time-scale or envelope rule in the host (none exists), stale effect ids
after a re-add (state is reset).

## 3. "If you see X then Y" map for the L2 `mcla-wheel-state-v1` report

The three SDK log arrays keep the **newest 32 lines** of each kind
(`src/mcla_diagnostic_trigger.h:331-372`). A crash produces several finite
`action=start` lines, so press L2 **soon after** the loss. Otherwise the stop lines may already have scrolled out.
The full runtime log in the same package has everything.

| If the report shows | Then |
|---|---|
| `active_controller` history ends on the wheel, with no new `SDL_ACTIVE_CONTROLLER` near the crash | P7 excluded (matches the M6-014 10-minute regression) |
| `SDL_ACTIVE_CONTROLLER ... physical_slot=<not the wheel>` near the crash | P7: routing handoff (mirror/pad). Check `reason=` and whether it returned |
| `SDL_WHEEL_FFB_EFFECT v=2 action=stop slot=A type=spring` (and `slot=B type=sine/square/...`) near the crash, **no later `action=start slot=A`** | P2 (title never restarted) or P1 (restart dropped). The main log line `XINPUTD_FF_AUDIT ... action=batch` exists only with the proposal |
| stop for A and B, then a single `action=start` for some other slot right after the slow-motion | P1 is strongly indicated: batched restart, only entry 0 applied |
| `SDL_WHEEL_FFB_DEVICE_CONTROL v=1 command=N` at the crash | The title asked for a device-level operation that the SDK ignores. N=5/6 (pause/continue) with no start afterwards supports P2 |
| Only finite `action=start ... type=square/constant` lines, **no stop for A/B, no errors** | P3 (device-side loss, host still thinks "running") or P6/P4 via silent updates. Ask the tester whether pad -> wheel or Alt-Tab restores it (section 5) |
| `action=create slot=A type=<not spring>` where `slot=A` was created earlier as `type=spring` | P4: slot reuse; check for a later `create slot=A type=spring` |
| `SDL wheel FFB update failed ... Unable to update effect` / `start failed ... Running the effect` / `create failed` | P5: DirectInput error. The text after the colon is the SDL/DI error (e.g. `DIERR_INPUTLOST`-class text). Later silence for that slot is expected |
| `action=defer-start`, `drop-start`, `action=resume reason=focus` | P8: focus changed (overlay/Steam/Windows popup) |
| `resume failed for slot N` | Resume after focus or controller switch failed at DirectInput |
| `SDL wheel removed from physical slot`, `SDL_WHEEL_FFB_SUMMARY`, `SDL_WHEEL_CONNECTED` in the device array | P9: USB re-enumeration. Check whether the title re-created effects (`action=create`) afterwards |
| Device array has `SDL_WHEEL_CONNECTED ... haptic=0` | Haptic never opened on that wheel: no FFB at all, so a different issue |
| `SDL_WHEEL_FFB_DEVICE_INFO v=2 ... host_effects=128 host_playing=128` | Expected (SDL fixed value). Confirms the host cannot see the real T300 limit (supports P3-eviction plausibility) |
| raw axes in the report keep moving with the wheel | Input is fine. Only output is affected (confirms an FFB-only failure) |

Note: `SDL_WHEEL_FFB_PARAMS` lines show create and first-update parameters
(spring coefficients, saturation, deadband). Use them to identify which slot is
the centering spring (`type=spring`, non-zero coefficients, `duration=4294967295`)
and which is the continuous periodic (`duration=4294967295`, periodic type).

## 4. Ranked root-cause hypotheses (crash slow-motion scenario)

1. **P3, device-side stop not seen by the host, plus no re-arm.** Confidence:
   medium (about 40%). Verified: the host can never notice a stopped infinite
   effect. Updates cannot restart it. Finite starts bypass every suppression, so
   collisions keep working while spring and periodic stay dead. That matches the
   observation exactly. DI re-acquire is silent. The crash moment is the
   largest burst of strong finite forces (75% floor) and of effect downloads
   against a T300 whose capacity the host overstates (128 vs. a small hardware
   pool). Dump must show: no `action=stop` for the spring/periodic slots, no
   errors, and (tester) the switch workaround **not** restoring it if status is honest.
2. **P1/P2, the title stops the infinite effects for the crash camera and the
   restart is lost.** Confidence: medium (about 35%). Verified: the hook drops
   every `EffectOperation` entry after the first. A crash-camera "stop
   centering + engine, then restart" in one batched call would lose exactly the
   second effect, or both if entry 0 is another slot. A title that relies
   on DeviceControl pause/continue would get no-ops (harmless by themselves).
   Dump must show: `action=stop` for both slots near the crash and no matching start.
3. **P6/P4, slow-motion re-parameterisation through UpdateEffect** (finite
   duration or slot type swap) that the host applies silently and never
   restarts. Confidence: low (about 15%). Needs the main log (silent in the
   32-line window). The proposal's `action=retype` line would expose P4.
4. **P5, DirectInput errors** (`Running the effect` without re-acquire). Low
   (about 7%). Self-identifying in the dump.
5. **P7/P8/P9, routing, focus or re-enumeration.** Very low for this
   report (about 3%): the M6-014 regression already showed loss with the wheel
   active, and the tester describes no device or pause event. Self-identifying.

What is not yet known and only the dump can settle: whether the title issues
stop/start or DeviceControl at the crash camera, whether `r5 > 1` ever occurs,
and whether the T300 reports `GetEffectStatus` honestly for an infinite effect
that the device stopped.

## 5. Fix direction (proposal, not applied): `ki-022-proposal.diff`

No single hypothesis is proven, but two host defects are verified and both
explain "infinite lost, finite fine". The proposal is minimal and adds
diagnostics so the next report can tell the cases apart:

1. `xboxkrnl_hid.cpp`: apply **every** `EffectOperation` entry (`r5` count,
   bounded 1..64, 2-word stride). Log `XINPUTD_FF_AUDIT v=1 export=EffectOperation action=batch count=N op=O`
   once when a batch occurs. Fixes P1 directly. Before relying on the stride,
   confirm it on a real batched call (the audit line).
2. `sdl_input_driver.cpp`: `RearmStoppedWheelEffectsLocked`. For the active
   wheel with focus, every **infinite** effect the host believes `running` whose
   `SDL_GetHapticEffectStatus` reads **not playing** is re-run, with
   `SDL_WHEEL_FFB_EFFECT v=2 action=rearm slot=N type=T reason=watchdog|update`
   (or `SDL wheel FFB <reason> rearm failed ...`). It is called (a) after
   every successful same-type guest update, and (b) at most once per second
   from the guest's `GetState` on the active wheel. Fixes P3 when the status is
   honest, and P6 once the duration returns to infinite. Finite effects are never touched.
   A genuinely running spring is not re-articulated: status playing means no-op.
3. Diagnostics: log a type-changing re-create through UpdateEffect
   (`action=retype slot= from= to= restart=`), and log the first suppressed infinite start per run
   (`action=start-suppressed ... reason=status-playing`). P4 and the status-lies case are then visible.

Limits: if the T300 driver keeps reporting a stopped infinite effect as
playing (the driver quirk the existing comment describes for finite
effects), the watchdog cannot see it. The next step would then be a
bounded unconditional re-`Start` of the centering spring on specific triggers
(DIERR from any call, end of a finite burst). That needs physical evidence first.
The proposal is untested: no build, no unit tests were run. Hunks were
produced with `diff -ru` against the pinned files.

## 6. What the tester should note when it happens

- Lost **all** infinite forces (centering **and** engine/road vibration) but
  collisions still felt? (Already reported once. Confirm it repeats.)
  Damper/heaviness at low speed still present?
- Exactly when: entry into the slow-motion crash camera, during it, or on
  return to driving? Did it ever come back by itself later (next crash, next
  race, restart from the menu)?
- After the loss: does **pad -> wheel** (touch the gamepad, then turn the wheel)
  restore centering? Does **Alt-Tab out and back** restore it? (Yes means the
  device stopped the effect but status still read "playing". No means honest
  status or a title-side stop. This splits P3 from P1/P2.)
- Did any other pad, Steam Controller or mirror light up or vibrate? Any
  Windows device-connect/disconnect sound, Steam overlay or notification popup?
- Did the game show a pause or menu, a replay, or a camera change other than the crash camera?
- Time since game start and since race start; session length before it happened.
- Press **L2 within a few seconds** of noticing (the FFB array keeps only 32
  lines and crash effects fill it quickly). If possible, press L2 **again** after
  trying pad -> wheel.
- Thrustmaster Control Panel open? Its gain/autocenter settings, firmware/driver
  version, and whether the T300 was in PC or PS mode.
