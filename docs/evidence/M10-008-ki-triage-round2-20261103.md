## 1. KI-057: Steam Deck window 1280x720 on the 1280x800 panel

**Evidence.**
- The launcher passes `--fullscreen=<preference>` (`mcla_launcher_controller_win.cpp`, session
  arguments) and the preference defaults to `false` (`mcla_launcher_preferences.h`). The guest
  mode is the render-target's 16:9 size (1280x720 at scale 1). So the l48 Deck run (first run,
  checkbox never ticked) got a 1280x720 window; the swapchain size is the window's client size,
  not an SDL display-mode choice.
- All 11 owner Deck sessions since l56 (`private/owner-deck-20261101`, `-20261103`, `-20261103b`)
  have `fullscreen 1` in `launch-receipt.txt` and log
  `D3D12 guest present ... source=1280x720 swapchain=1280x800`. The SDK presenter letterboxes by
  default (`present_letterbox=true`, `src/ui/presenter.cpp:32`); 1280x720 in 1280x800 is a 1:1
  copy with 40-pixel bars, no scaling. So the presentation itself is right once Fullscreen is on.
- Every one of those 11 sessions ends with `REX_WINDOW_FULLSCREEN_TOGGLE ... source=left-double-click
  fullscreen=false` 1.8-3.4 s before `Window closing`: the owner leaves fullscreen with a double
  tap to reach the window's close button. Not a defect; worth a line in the tester guide.
- A 16:10 guest mode (1280x800) is not proposed: the game renders 16:9, and a non-16:9 guest mode
  belongs to the ultrawide work (M8-005, deferred).

**Change (l67b, launcher).** `FirstRunPreferences(bool under_wine)` in
`src/mcla_launcher_preferences.h`: the first run (no `preferences.dat`) under Wine/Proton starts
with Fullscreen ticked; real Windows keeps the windowed default; saved preferences are never
changed (a Deck user who saved "windowed" keeps it). `OpenPreferenceStore` uses it with the
existing `platform::RunningUnderWine()` probe. Nothing is written until the user saves or starts.

**Tests.** `mcla_launcher_preferences_test`: `FirstRunPreferences(false) == Preferences{}`; the
Wine variant differs only in `fullscreen`, is valid and round-trips through the codec.
`mcla_launcher_store_win_test`: with the Wine override forced on, a first run opens fullscreen,
writes only the writer lock, and a saved windowed choice is reopened unchanged; forced Windows
first run stays windowed; the existing first-run check runs with the Windows override.

**Owner/tester action.** None required (the owner already runs fullscreen). Tester guide, Deck
line: "tick Fullscreen in the launcher; double-tap the game to leave fullscreen before closing".

## 2. KI-065: "storage device was removed" after an F10 during a save (Deck, l66)

**Evidence.** The l66 Deck analysis ([l66 Deck A/B](M10-l66-deck-ab-20261103.md)) puts fine 2's
pull-over inside the F10 #4 export (17:26:03.2-17:26:05.1), which copies the live save tree with
`std::filesystem::copy_file`. Source facts checked for this triage:
- `copy_file` (CopyFile2 -> CopyFileExW) keeps the source open for the whole copy with sharing
  chosen by the platform. **Measured on Windows (new unit test, info lines):** it grants write and
  delete sharing, so on the PC the F10 copy cannot block the game. Wine's CopyFileExW is believed
  to open the source with read/write sharing only (no `FILE_SHARE_DELETE`); this is from memory of
  the Wine source and **not verified**. Running the same test executable under Proton prints it.
- The SDK opens guest save files with read/write(/delete) sharing
  (`src/core/filesystem_win.cpp:200`), writes through `_wfopen` "wb" in `host_path_entry.cpp`,
  renames with `std::filesystem::rename`, and its content transaction
  (`src/system/xam/content_manager.cpp`) copies the package to `<name>.rexbackup`,
  `remove_all`s it, writes a `.rexpending` marker and removes backup and marker at commit. Any of
  those steps fails with a sharing violation while the F10 copier holds that file, and every
  failure becomes a silent `X_ERROR_ACCESS_DENIED`.
- The new unit test shows the mechanism with explicit handles: a reader without write sharing
  makes the game-style write open fail, and a reader without delete sharing makes the game's
  rename and delete fail, each with `ERROR_SHARING_VIOLATION`.
- So on Windows the mitigation below is neutral; on the Deck it removes the only F10-side way to
  break a save if Wine's copy omits delete sharing. Hypothesis 2 of the l66 analysis (a silent
  content-layer failure unrelated to F10) stays open until the SDK logs those failures.

**Change (l67b, host, `src/mcla_diagnostics.cpp` + new `src/mcla_shared_read_copy_win.h`).**
- `CopyStableFile` copies through `CopyFileSharedRead`: the source is opened with read, write and
  delete sharing, read into memory (bounded by the existing 16 MiB per-file cap), closed, and only
  then is the destination written. The existing size/time stability check and three attempts stay.
- Content-transaction scratch entries (`*.rexbackup`, `*.rexpending`) are left out of the F10
  copy (recursion into a `.rexbackup` package directory is disabled); counted as
  `transaction_entries`, not as `skipped`. `save-metadata.json` is unchanged (no schema change).
- Log lines: `MCLA diagnostics: save copy start`, `... save copy end files= bytes= skipped=
  transaction_entries= ms=`, and one WARN per file given up after three attempts (file name and
  last Win32 error; the leaf name only, no profile path).

**Residual risk.** A delete of a file the copier has open still leaves it delete-pending until the
handle closes (milliseconds now: the read is in memory and the handle is closed before the
write); a create of the same name in that window can still fail on Wine. The complete fix is
SDK-side (below).

**Tests.** New `mcla_shared_read_copy_win_test`: scratch-name rules; byte-identical copy over
several chunks, replace, empty file, oversized source refused with nothing written, missing source
and missing destination folder; while the copier's handle is open the game-style write open,
truncate, two renames and a delete all succeed; controls: a reader without write sharing blocks the
write open, and a reader without delete sharing blocks rename and delete (`ERROR_SHARING_VIOLATION`);
the copier reads a save the game holds open for write and one held with delete access. Two info
lines print the sharing `std::filesystem::copy_file` grants on this platform (Windows 11: write
ok, delete ok). 34 checks.

**SDK proposals (not implemented, SDK owned by the primary).**
1. WARN line per non-success in `xeXamContentCreate` (stage, X_RESULT, `std::error_code`,
   relative path), `XamContentClose`/`CommitContentTransaction`/`RollbackContentTransaction`, and on
   NtWriteFile/NtSetInformationFile failures for the content device.
2. A `rex::system::ContentTransactionActive()` query (or a scoped lock the host can take) so the
   F10 export can wait up to about 2 s for an active transaction and otherwise skip the save copy
   with a recorded reason.

**Owner/primary action.**
1. Decisive and cheap (non-destructive, no game): run `mcla_shared_read_copy_win_test.exe` from
   `private/l67b-host-build` on the Deck under Proton (for example as a non-Steam shortcut with a
   Proton compatibility tool, output to a file). The two `info:` lines say whether Wine's
   `copy_file` grants write and delete sharing. "delete: failed" makes hypothesis 1 the
   mechanism; "ok" on both moves the weight to hypothesis 2 (SDK logging needed).
2. On the next Deck build carrying l67b: one F10 exactly when a pull-over starts (the l66
   pattern). Expected: no dialog; `save copy start/end` lines bracketing the export; no `save copy
   skipped` WARN.

## 3. KI-056: album "Choose a slot" preview shows the placeholder

**Evidence.**
- The only package (`live-20261031T142517Z-21084-1`, l52 stock 1080p) has a fresh frame
  (`guest-output-readback`, `presented-guest-output` in its manifest). It shows the slot grid with
  the **first empty slot highlighted** (camera icon) and the left panel showing the empty-slot
  placeholder (grey MIDNIGHT CLUB logo). 13 of the 16 slots were already occupied (several with
  the old KI-037 stripes).
- KI-037 analysis (section 1): the album has separate `SetPreviewPicture` and `PhotoSlotChosen`
  script functions; the decoded JPEG preview is bound to texture +1132. The earlier symptom
  "preview shows the previous photo" and this one ("placeholder for the first photo of a
  session") are both what a panel that previews **the highlighted slot's current content** would
  show, which is a common design for "overwrite this slot?" choosers.
- Session log: `photo capture: window open` at 16:24:56.995 and `timed out after 120 frames
  (4000 ms)`: the freeze stays on while the chooser is open; no read-back or texture error.
- Read-back side at v0.20.0.7: a one-off capture key is a miss and is copied synchronously; the
  CPU decode into +1144 faults through the protected view and re-uploads the texture
  (KI-037 analysis 4.2). Nothing found that would show the placeholder for valid data.

**Disposition.** Probably not a defect. One owner check decides it (no build): on the chooser,
move the cursor from the empty slot to an occupied one and back. If the panel follows the cursor
(that slot's photo, placeholder on empty slots), it previews slots by design: close KI-056 (and
retire KI-037's preview sub-symptom). If the panel never shows any slot photo, or shows the new
photo only on some slots, save the photo and reopen the album to check the stored image; then a
direct run with `--d3d12_readback_sync_scope=1` (every read-back resolve fenced) separates a
read-back cause. No counter exists for this path; none is proposed before the check.

## 4. KI-052: Steam on-screen keyboard in the launcher (Proton)

**Facts.** The launcher is a plain Win32 dialog (EDIT controls, no D3D/GL/Vulkan surface), so the
Steam overlay (which hooks a graphics API) never attaches to it. The Steamworks text-input calls
(`ShowGamepadTextInput` / `ShowFloatingGamepadTextInput`) need `steam_api` initialised for an App
ID, which a non-Steam shortcut does not have, plus redistributing the Steamworks DLL. Every path
field already has a Browse button (`PickFolder`, IFileOpenDialog); the only fields that need typing
are the profile name (create/rename dialog) and the in-game name.

**Disposition.** Defer to M11. Feasible later option without Steam: prefill both texts (profile
"Deck" or "Profile N"; in-game name kept from the profile) so the Deck flow needs no typing; an
SDL-based launcher UI would be a larger rewrite. Not possible to verify the "presses do nothing"
part without the Deck.

**Owner action (optional, 2 min).** Separate "does not appear" from "typing does nothing": in Game
Mode open the keyboard by hand (STEAM + X) with the cursor in a field and type; in Desktop Mode try
the same. Workaround stays: Browse buttons, an attached keyboard, or prepare profiles on a PC.

## 5. KI-041 and KI-043: unlocked-only rendering

**What the rows say.** KI-041: (a) night lights and bushes under the headlights flicker at 2K on
l34-sunc (not at 720p, not on l34-s30); (b) world light blinks periodically during a race at 720p
on l34-sunc (72-82 fps, audit clean). KI-043: after the finish slow motion (time scale 0.73 to 0.1
and back over about 1 s) lighting and shadows stay wrong for the whole victory scene, unlocked
only (the same finish at 30 FPS is correct). No GPU error in either.

**Could M10 have changed them?**
- Always-on pipeline wait (l51+): removes skipped draws while pipelines compile. A skipped light
  or shadow draw would give a one-frame blink, so KI-041 (b) could be affected; but its audit
  window had no shader or PSO compiles. Unlikely to change KI-043.
- Composite read-back sync and targeted wait (l56/l63+): scope 0 = the livery composite family
  only; not the light/exposure path.
- Read-back elision (`d3d12_readback_elide_unread`): elides only copies no one can read
  (`guard_misses=0` in the owner runs); no behaviour change by design.
- Perf split, upload-ahead, disarm bridging, hot blocks: timing/upload paths; hot blocks are
  owner-internal arms only. None changes per-frame game logic.
- So the leading explanation stays frame-rate-dependent game logic (light animation, shadow
  cascade round robin, exposure adaptation with tiny or zero time steps after slow motion).
- Owner data since: 19 Unlocked launcher sessions on Oct 31-Nov 3 (720p, 1080p, 1440p) with no flicker or
  victory-lighting report, but they were BENCH routes, not night drives or race finishes.

**Proposed targeted diagnostic (no code; direct-run arms on l65 or later, 720p Unlocked):**
1. Night route from KI-041 and one race to the finish: default arm. F10 at a blink and at the
   victory screen.
2. Same with `--mcla_guest_vblank_hz=120`, then `=60`: the rate where it stops.
3. Same default rate with `--d3d12_readback_sync_scope=1` (SDK v0.20.0.7: every read-back resolve
   fenced and synchronous): if it disappears, a stale read-back (exposure/luminance) is involved.
If (2) moves it and (3) does not, it is game logic and goes to the unlocked limits for good.
