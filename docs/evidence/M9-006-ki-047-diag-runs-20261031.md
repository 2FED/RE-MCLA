## Coverage caveat (read this first)

The 64 lines per minute limit is shared by all resolve lines, and it is too small. Both runs
**used up the first-minute resolve budget inside world-load frame 692.** Run 1's last first-window
line is at 14:20:02.138 and run 2's at 14:24:47.537. As a result, **the hand-off and the first
~35 s of driving have no detail lines in either run** (195 and 115 resolve lines suppressed). In

there was no fresh range and no skip into a resolve source up to the F10. Most of the budget goes to

whenever a skipped draw used depth at EDRAM base 0, and every depth-tile resolve has `src_base=0`.
`skips_same_base` is also capped at 64 (`kLiveryDiagSkipBaseLimit`), so values of 64 are
saturated.

Every livery-sized candidate in both runs is a **cache miss, so it is read synchronously from its own
slot** (`miss=1 read=this decision=now prev_known_complete=1 prev_len_ok=1`). The source shows
why: on a miss, `AwaitAllQueueOperationsCompletion()` ends the open submission and waits on the
fence, then the CPU copies from `write_index`. The first resolve of any new (address, length)
range is therefore fully fenced and always copied. Readback buffers are evicted 60 frames after
last use (`kReadbackBufferEvictionAgeFrames`), so a range that a car re-composites more than about
2 s later is a miss again.

## 4. H2 (`reads_prev_slot_unfenced`)

Source semantics (`IssueCopy_ReadbackResolvePath`, `some` mode):

- Each (address, length) key has two readback-heap slots. The GPU copy of this resolve goes
  into `write_index`. The CPU reads `read_index = 1 - write_index`, the slot the **previous**
  same-key resolve wrote, unless it is a miss.
- `reads_prev_slot` counts every non-miss resolve, **whether or not anything is copied**. 65,047
  of 65,200 means all but 153 cache misses. `copies_deferred` (48,839) were not copied at all
  (`some_interval`: only every 4th same-key resolve is copied), so guest memory keeps whatever
  the last copy wrote. Only about 16,208 resolves (16,361 now minus about 153 misses) actually
  memcpy'd from the previous slot.
- "unfenced" = `previous_slot_complete` false = the previous slot's submission is greater than
  `submission_completed_`. That value is refreshed only in `CheckSubmissionFence`, so "not known
  complete" includes slots that were in fact finished. With about 2.7 submissions per frame and
  `prev_age` 2-6 in the kept lines, the previous slot is about one frame old and usually still in
  flight on a GPU that is ~1 frame behind. 37,658 / 65,047 = 58 % (run 2: 58 %).
- Kept lines: run 1 had 38 `read=prev` lines, 26 not known complete, and **8 of them actually
  copied** (`decision=now read=prev`, `prev_age` 2-6). Run 2 had 12 / 5 / 4, plus two `prev_age=0`
  (the same open submission, so not even submitted) on the depth tile scratch at f2184. Those were
  `deferred`, so nothing was copied. **Every one of them is a per-frame main-scene, shadow or Photo
  Mode tile resolve. None is livery-sized or a one-shot.**

Could an unfenced read make the column garbage? Only if a livery range is **re-resolved to the same
(address, length) within 60 frames** (then it is not a miss). The CPU copy then gets the previous
composite of that range. That is either the previous car's content (in-flight slot, prev_age ≥ 1)
or, with prev_age = 0, the slot from two resolves back. Three-in-four of those resolves are not
copied at all. That gives *foreign but coherent* content (another car's livery). Torn content is
also possible: a memcpy of a buffer that the GPU copy is filling at that moment. That gives a
contiguous prefix or suffix of new data, which in the tiled guest layout shows up as bands of 32-row
tile rows, not regular columns. The observed regular column structure and blue streaks fit a stale
**render-target** content (H1: foreign EDRAM tiles), or a format or layout mismatch, better than a
torn readback. No livery-size range was a non-miss in either run, so H2 had no opportunity here.

## 5. Performance note (proposed for M10)

About 35-37 read-back resolves per frame (1,090-1,170 per second) at 1440p `some`, each costing a
downscale dispatch and a GPU copy into a readback heap, plus about 270-290 CPU memcpys per second
of up to 5 MB each. The main scene tiles alone are about 2.6 + 1.1 MB color, 2.6 + 1.1 MB depth and
HDR 5 MB, so an estimated 0.5-1 GB/s of CPU-side memcpy at 30 fps. The GPU-side downscale and
copy run for all of the ~65-70k resolves per minute, including the deferred ones. 65k
resolves need 5,072 submissions per minute. This is the per-frame main scene and shadows, which
the CPU never needs. The game needs readback only for the render-to-texture results that it reads
on the CPU (the livery/vinyl path, KI-033). Worth an M10 note: restrict the readback path to
non-per-frame ranges (for example, skip keys resolved in each of the last N frames, or restrict it
by size or EDRAM base). Measure it with the existing `replay/min`, `gpu busy/min` and pacing lines.
Not a KI-047 fix. Run 2's fps (31.4) is the vsync-limited 30 fps target, so the cost is hidden here,
but it matters for the KI-048 VRAM and low-end GPU budgets.

## 6. Conclusion and next steps

- **H3: excluded** (0 shifted resolves in about 135k).
- **H2: not exercised** for any one-shot or livery-sized range. All such resolves were fenced
  synchronous misses. The unfenced reads are all per-frame tiles. Weakened, but not excluded for a
  range that is re-composited within 60 frames.
- **H1: mechanism confirmed live.** In the cold run, nearly every one-shot render-to-texture at
  world load lost draws to pending pipelines before being read back. In the warm run, a one-shot 2D
  channel-masked 256x256 composite lost 8 draws. Both liveries were clean, so the police livery was
  not among the damaged targets, or the damaged target is not visible on the police car. H1 stays
  the leading hypothesis. These runs show that the "cold store" condition is not needed (skips also
  happen warm, on newly seen content). What matters is whether a car's livery composite happens to
  hit a pending pipeline.

What to look for:

- **Next run (any store):** the logging budget is the blocker, because frame 692 uses up minute 1.
  Without a rebuild, open the cvar later: `d3d12_livery_diag` is hot-reload. If the owner can
  toggle it, enable it only after the hand-off (start of free roam) so the budget covers driving and
  Photo Mode. Otherwise a small SDK change: exclude per-frame keys from the line budget (log only
  `key_fresh=1` or skips into fresh keys), use separate budgets for skip and resolve lines, and
  match skips on (base, pitch, msaa) rather than the bare base.
- **A broken run:** find one-shot RGBA8 resolves after the police car appears (A: 512x512 mip
  chain; B: 256x256 at EDRAM 0, pitch 320; or a new size) and read `skips_same_base` / the preceding
  `pso_skip` lines with `rt0_base` equal to the resolve's `src_base`, `vp` equal to the size,
  `depth_used=0`, `msaa=0`. If they are present, H1 is confirmed. If the livery resolve shows
  `miss=0 read=prev` with `prev_known_complete=0` or `decision=deferred`, that is H2. Note the
  pipeline hashes of skipped composite draws. If the same hashes recur in broken runs, pre-warming
  those pipelines or arming `d3d12_async_pipeline_wait` for one-shot (non-per-frame) render-to-texture
  passes would be the fix to test.
