## 6. What to read in the owner runs

- Run B (lead1), every driving minute: `lead_limit=1`; `lead_open2_frames=0` and
  `lead_open_frames_max<=1` (the bound works); `lead_cap_timeouts=0`; `lead_cap_waits` and
  `lead_cap_wait_ms_total` per frame (the cost). `lead2_frames` / `cp_lead_frames_max` (the frame-end
  gauge, the frame just closed included) may stay above 0 / at 2: that is expected, not a failure.
  `fence_late_f2p` should fall.
- Run A (default): `lead_open2_frames` against the l88 `lead2_frames` (both should be high in the
  flicker minutes); `rb_release_inflight` (does the early slot-buffer release ever happen).
- Run C (lead1-rel): `rb_release_inflight=0`, `rb_release_deferred` about A's `rb_release`.
- Performance: fps B within 2 fps of A (the target; model estimate +0.5-1.7 % frame time), p99 not
  worse, 0 frames > 100 ms, no hang.
- Falsifier: if B has `lead_open2_frames=0` in every minute and still flickers, the open lead is not
  the cause; C then tests the release hazard, and the stricter bound (frame F waits for F-1, frame-end
  gauge 1) is the remaining lead variant, not built in l90.

## 7. Not done / risks

- Not committed in the main repository (the primary commits exactly the s.2 diff). The SDK commit is
  local only and not pushed. `docs/known-issues.md`, `docs/M11-priorities.md`,
  `docs/current-state.md` and README-AI were not updated.
- Not signed: no ticket, no `private\l90-internal`, no admission row.
- No runtime: no PC or Deck run, no physical PASS, no performance numbers.
- Risks, untested in the game:
  - lead1 makes the CP thread wait at frame open while the GPU finishes frame F-2; the guest may
    then stall on ring space or on fences sooner. Cost measured only in a model.
  - lead1 bounds the open lead, not the frame-end gauge; if the flicker follows the gauge itself,
    lead1 will not remove it (see the falsifier).
  - The deferred release keeps released read-back buffers alive until the current submission
    completes (more memory briefly at slot growth and eviction).
  - The always-on counters add one counter update per frame open and a fence poll per release of a
    slot buffer whose last copy is not known complete (releases are rare).
