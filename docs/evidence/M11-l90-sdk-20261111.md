### A. `d3d12_frame_lead_limit` (int, default 0, range 0..2, GPU/D3D12, hot reload)

- Today a guest frame F opens once the closing submission of frame F-3 has completed
  (`kQueueFrames = 3`), so up to two earlier frames (F-1, F-2) can still be on the GPU while F is
  recorded.
- With N = 1, `BeginSubmission` also waits, when it opens frame F, for the closing submission of
  frame F-2 (`FrameLeadLimitAwaitFrame`, pure). The wait is fence only, through the existing bounded
  helper `AwaitReadbackSubmissionBounded`, at most 100 ms (`kFrameLeadLimitWaitTimeoutMs`), in the
  `kFenceWait` perf region. On a timeout the frame opens as without the limit and the timeout is
  counted. It never waits when the device is removed (the function returns before), when the target
  is already complete (polled), or for a submission that has not been ended.
- The wait sits directly before the existing `CheckSubmissionFence(closed_frame_submissions_[F % 3])`.
  That call then observes the fence, delivers completed read-backs (fenced arm), flushes the due
  deferred guest fence writes and reclaims, exactly as after its own wait. `frame_completed_` is then
  computed as before and picks up the earlier completion.
- 0 and 2 add no wait (2 is the F-3 queue rule itself); the frame open is then the 7cbfe3b code path
  plus one counter update.
- Bounded quantity: earlier frames in flight while a frame is recorded (`lead_open_frames_max`). The
  l78 frame-end gauge (`cp_lead_frames_*`, `lead2_frames`) counts the frame just closed too, so with
  N = 1 it can still read 2 (F and F-1 on the GPU when F ends; always so when the GPU is the
  bottleneck). Read `lead_open2_frames`, not `lead2_frames`, for the bound.

### B. `d3d12_readback_deferred_release` (bool, default false, GPU/D3D12, hot reload)

- The two places that released read-back slot buffers immediately while the GPU may still copy into
  them (slot growth in `IssueCopy_ReadbackResolvePath`; `EvictOldReadbackBuffers`, both the > 256
  keys and the 60-frame age eviction, for the resolve and memexport maps) now go through
  `ReleaseReadbackSlotBuffer`. With the cvar on, every such release goes into
  `resources_for_deletion_` with the current submission (the existing deferred deletion); off,
  `Release()` as before.
- New per-slot `submission_last_gpu[2]` in `ReadbackBuffer`: the submission of the last GPU copy
  into the slot. Unlike `submission_written` it is not cleared by an elided resolve, so it is the
  real last GPU use.
- Always on: `rb_release_inflight` counts immediate releases whose last copy had not completed (the
  fence is polled only for such a release). The default arm thus shows whether the hazard ever
  happens.

### C. Counters (always on; end of every `MCLA_READBACK v=1` minute and mark line, reset per minute)

`rb_release`, `rb_release_inflight`, `rb_release_deferred`, `rb_release_deferred_inflight`.
`cp_lead_frames_max`, `lead2_frames` and `fence_late_f2p` are unchanged.

## 2. Tests (SDK ctest, tag `[frame_lead_limit]`, 5 new cases)

- Await frame: off, negative, 2 and larger limits never wait; 1 waits for F-2 from frame 3 on; the
  awaited frame is always inside the 3-entry closing-submission ring.
- Release decision and its counters; the exact line fields.
- A model of the CP/GPU pipeline (frame open with both waits, 4 submissions per frame, in-order
  GPU, rare 250 ms GPU stalls), 40 seeds x 3-4 load shapes (balanced, GPU bound, stalls, high
  jitter):
  - limit 0 and 2: frame open times and end time identical to a reference that implements only the
    7cbfe3b F-3 rule (no limit code);
  - limit 1: at every open whose wait did not time out, at most 1 earlier frame is in flight; the
    frame-end gauge is at most 2 (3 without the limit); timeouts happen only in the stall shape,
    every frame still opens, no limit wait exceeds 100 ms; GPU-bound end time within 1 %, every
    shape within 5 %; the frame-end gauge still reaches 2 in the GPU-bound shape (documented).
- Model cost of limit 1 (driver `model_driver.cpp`, same model; a model, not the game): balanced
  +0.48 % time (max +0.79 %), GPU bound 0.00 %, stalls +0.27 %, high jitter +1.68 % (max +2.27 %).
  Open lead 2 without the limit: 52 %, 99 %, 85 %, 56 % of frames.
