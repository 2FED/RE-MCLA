## 1. Why strict

- All-runs table (l86, l88 x4, the three l88 runs reported as l90): the only quantity that separates
  flicker runs from clean runs without exception is the frame-end lead gauge reaching 2
  (`lead2_frames > 0`) together with guest fences stored 2+ frames late (`fence_late_f2p > 0`).
  - It was 0 over 28 clean driving minutes (steady-off, cap44).
  - It was above 0 in every flicker run and in every interval between flicker presses.
- The owner's real l90 lead1 run (reported by the primary agent):
  - build D6AF6995 confirmed, and `frame_lead_limit_1` applied;
  - `lead_cap_waits=0` in every minute, `lead_open_frames_max=1` and `lead_open2_frames=0` (the open
    lead never exceeded 1, so limit 1 never had to wait: it was a no-op);
  - `rb_release_inflight=0` in all 23 minutes;
  - the frame-end `lead2_frames` still reached 91-94 per minute;
  - the owner still saw flicker.

  So the open lead is ruled out and the frame-end lead is not. The l90 model had already shown this
  (frame-end gauge 2 in 99.7 % of GPU-bound frames with limit 1).
- Strict reproduces the clean-run condition by construction: frame F waits at its open for the
  closing submission of F-1.

### A. `d3d12_frame_lead_strict` (int, default 0, range 0..2, GPU/D3D12, hot reload)

This is a new cvar. `d3d12_frame_lead_limit` 0 and 1 keep the 4ec7abd code path.

**1 (strict).**
- When `BeginSubmission` opens frame F (F >= 2), it waits for the closing submission of F-1
  (`FrameLeadStrictAwaitFrame`, pure).
  - The wait is fence only, through the existing `AwaitReadbackSubmissionBounded`, at most 100 ms
    (`kFrameLeadLimitWaitTimeoutMs`), in the `kFenceWait` perf region.
  - On a timeout the frame opens as it would without the bound, and the timeout is counted.
  - It never waits with the device removed (`BeginSubmission` returns before), nor when the target
    has already completed (the cached `submission_completed_` is checked first, then one poll).
- The wait sits after the l90 limit wait and before the existing
  `CheckSubmissionFence(closed_frame_submissions_[F % 3])`. That call then observes the fence,
  flushes the deferred guest fence writes that are due, delivers completed read-backs (fenced arm)
  and reclaims.
- Why the frame-end gauge is at most 1: submissions complete in order, so once F-1's closing
  submission has completed, every earlier frame has too. F is recorded after that, so when F ends
  the only frame whose closing submission can still be on the GPU is F.
- Why no guest fence is 2+ frames late:
  - a fence parsed in frame p waits for a submission no later than p's closing submission (the open
    one, or the last ended one); a fence parsed after p's swap is already tagged p+1;
  - the open of p+1 waits for exactly that submission, and the `CheckSubmissionFence` that follows
    flushes the queue with `frame_current_ = p+1`, so the fence is at most 1 frame late.
- Both properties hold for every open whose wait did not time out. Strict implies the l90 limit 1.

**2 (adaptive).** The same wait, but only while armed (`FrameLeadAdaptiveState`, pure):
- The trigger (`FrameLeadAdaptiveTrigger`, pure) reads only existing state, with no new submission
  or poll. It fires when either:
  - the frame-end gauge of F-1 read 2 or more (`last_frame_end_gauge_`, the value the l78 gauge
    already computes), or
  - the head of the deferred fence queue was parsed at frame F-2 or earlier.
- A trigger arms the hold for `kFrameLeadAdaptiveHoldFrames` = 30 opens. While armed, an open waits
  when F-1 has not completed. Only an armed open that finds F-1 already complete uses up a frame of
  the hold.
- Limits:
  - The trigger is reactive, so about one gauge-2 frame per arming gets through. A predictor of
    "F-1 still running when F ends" would need F-1's remaining GPU work, which the command processor
    does not know cheaply.
  - In the model the hold never ran down after the first trigger (see 3.): when the GPU is busy,
    F-1 is almost never complete at the next open. Adaptive therefore behaves almost like strict.

### B. Counters

They are always on, appended after the l90 fields of every `MCLA_READBACK v=1` minute and mark line,
and reset per minute:
- `lead_strict` (mode now), `lead_strict_waits` (opens that blocked), `lead_strict_wait_ms_total`,
  `lead_strict_wait_ms_max`, `lead_strict_timeouts`;
- adaptive only: `lead_adaptive_triggers` and `lead_adaptive_skips` (F-1 not complete, not armed, no
  wait).

All `lead_open*` and `lead_cap*` fields, `cp_lead_frames_max`, `lead2_frames` and `fence_late_f2p`
are unchanged.

A strict run passes on these values: `cp_lead_frames_max=1`, `lead2_frames=0`, `fence_late_f2p=0`
and `lead_strict_timeouts=0` in every minute.

Notes on the table:
- Strict timeouts happen only in the stall shape (1198). There they leave gauge-2 frames and late
  fences (the timed-out opens), as designed.
- Adaptive fired once per run (40 triggers in 40 runs, outside the stall shape). It then stayed
  armed and saved 0.3-10 % of the waits.
- For comparison, limit 1 costs +0.0 to +1.7 %.

Reading for the game. The PC driving minutes run at GPU 85-96 %, which is closest to the GPU-bound
shape. The expected strict cost there is about +14 % frame time, roughly 6-7 fps at 45-48 fps. That
is of the same order as the clean steady-off run:
- steady-off waited 5.5-7.4 ms per frame in mid-frame and ran at 39-46 fps against the default
  41-52 fps, about 5 fps lower;
- strict instead drains the GPU at the frame boundary, and the GPU then idles while the command
  processor records F's first submission.

The balanced and jitter shapes show that strict is expensive when the CPU and GPU are evenly loaded
(+30-35 %). The model gives no reason to expect adaptive to be much cheaper in the game.
